# 엔지니어링 노트 — 왜 그렇게 정했는가

**`CLAUDE.md` 에서 떼어 낸 본문이다.** 그 파일이 900줄까지 자라 매 세션 통째로 읽히던
것을 100줄 아래로 줄이면서, **한 줄도 버리지 않고** 여기로 옮겼다.

- `CLAUDE.md` — 지켜야 할 **규칙과 값** (짧게 유지한다)
- **이 파일** — 그 값이 어디서 왔고 무엇에 데였는지 (길어도 된다)
- `docs/research-log.md` — 막힌 길과 재조사 안내 (**다시 찾기 전에 볼 것**)
- `frontend/CLAUDE.md` — 화면에서만 쓰는 규칙

숫자를 고칠 때는 **두 파일을 같이** 고친다. `etl/test_docs_match_code.py` 가
`CLAUDE.md` 쪽만 감시하므로, 이 파일이 조용히 낡을 수 있다.

## 왜 웹 전용인가

지도 설계와 결과 비교에 큰 화면이 필요하고, deck.gl 3D 가 모바일에서 불안정하며,
사용 맥락이 "앉아서 검토하는" 일이다. Kakao/Naver Map 은 주소 검색·좌표 변환 보조용.
**로드뷰 위에 3D 모델은 불가능**(파노라마라 깊이 정보가 없다).

## 디렉터리

`data/raw/` 는 **받은 원본이라 수정하지 않는다.** 나머지 구조는 `ls` 로 보면 된다 —
자동 생성 시드와 ERD 주의사항은 아래 「작업 규칙」·「스키마」에 있다.

## 실행

명령과 자주 밟는 함정(포트 3307, root 비밀번호, `package` 전에 백엔드 끄기, `JWT_SECRET`,
`SET NAMES utf8mb4`)은 **루트 `CLAUDE.md`** 에 있다. 여기엔 **거기 안 들어간 사정과 나머지
함정**을 둔다.

- **포트 3307 인 까닭** — 개발 PC 의 로컬 MySQL 이 3306 을 쓰고 있다. `DB_PORT` 가 빠지면
  `application.yml` 기본값 `localhost:3306` 으로 붙어 `Access denied for user 'root'` 가
  나는데, 실제로 `.env` 가 `.env.example` 보다 뒤처져 이 키가 빠져 있었다
- **테스트로 바꾼 기준값을 되돌릴 때는 시드를 통째로 넣는다.** 관리자 API 로 바꿔 보고
  그대로 두면 DB 와 시드 파일이 어긋난 채 계산에 쓰인다 (실제로 `discount_rate` 근거가
  `stale check` 로 남아 있었다). 볼륨은 안 지워도 된다

  ```bash
  PW=$(grep '^DB_PASSWORD=' .env | cut -d= -f2-)
  docker compose exec -T -e MYSQL_PWD="$PW" db mysql -uroot railfeas < db/seed/S7__benefit_parameter.sql
  ```
- **시드 파일 자체를 고쳤으면 `down -v`** — initdb 는 볼륨이 빈 경우에만 돈다
- **`./mvnw` 가 조용히 아무것도 안 할 수 있다** — 배포본을 받으려다 `wget: Failed to fetch`
  로 끝나는데 `-q` 를 붙이면 그 한 줄도 안 보이고, `target/surefire-reports` 에는 **예전
  결과가 그대로 남아** 통과한 것처럼 읽힌다(실제로 그렇게 잘못 보고했다). 받아 둔 배포본을
  직접 쓰고, 보고서는 **시각까지** 본다
  `$(ls -d ~/.m2/wrapper/dists/apache-maven-3.9.9/*/bin/mvn) -o test`
- **SQL 파일 첫 줄에 `SET NAMES utf8mb4;`** — initdb가 latin1로 읽어 한글이 이중 인코딩된다
  (`복선전철` → `ë³µì„ ì „ì² `). 자동 생성 SQL은 생성기에도 넣을 것
- **`cost_standard`는 TRUNCATE 불가** — `scenario_result`가 FK로 참조. `DELETE`를 쓴다
- **엔티티 타입이 DDL과 어긋나면 기동 실패** — `data_grade CHAR(1)`은 `columnDefinition="char(1)"`
- **소셜 로그인 설정은 `application-social.yml`** — 키가 비면 기동이 막혀 기본 프로파일에서 뺐다
- **`JWT_SECRET` 은 기본값이 없다 — 없으면 기동이 막힌다.** `application.yml` 은 공개
  저장소에 올라가므로 거기 적은 키는 누구나 읽어 **토큰을 위조**할 수 있다. 실제로
  47바이트 기본값이 들어 있었다. `.env` 에 32바이트 이상으로 넣는다(HS256, RFC 7518 3.2).
  `JwtTokenProvider` 가 없음·짧음·치환 안 됨(`${...}`)을 가려 무엇을 어디에 넣을지 말해 준다 —
  그러지 않으면 jjwt 가 "key byte array is 104 bits" 라고만 해서 원인을 알 수 없다
  (104비트 = 치환되지 않은 `${JWT_SECRET}` 13글자). **키를 바꾸면 발급된 토큰이 전부 무효**다
- **JDK 23+는 애너테이션 처리가 기본 비활성** — `pom.xml` `annotationProcessorPaths`에 Lombok 명시
  (1.18.38). `mvnw spring-boot:run`은 클래스패스 오류라 `package` 후 `java -jar` (원인 미파악)
- `initdb.d`는 하위 폴더를 안 읽어 compose에서 `01_`~`07_` 접두사로 파일 단위 마운트
- **MapLibre 지도에는 `ResizeObserver` 가 필요하다.** 컨테이너 크기를 못 재면 400×300 으로
  잡아 두고 그대로 둔다 — 지도 일부만 그려지고 **빈 영역을 클릭하면 좌표까지 어긋난다**
  (684×716 컨테이너에 캔버스가 400×300 으로 남아 있었다). 노선 찍기가 첫 동작이라 치명적
- **화면은 직접 열어 봐야 한다.** 빌드·API 만으로는 안 나오는 결함이 실제로 여럿 나왔다
  (캔버스 크기, 비교표 강조, 관리자 오류 위치·칸 너비, 패널 폭). 단 **데이터 로딩 전에 찍은
  화면으로 단정하지 말 것** — 3D·관리자 표를 "비었다"고 잘못 보고한 적이 두 번 있다

**시나리오 수정은 `PUT /api/scenarios/{id}`**다. 프론트는 불러온 id를 `editingId`로 들고 있다가
덮어쓴다. 노선을 고치면 계산 결과는 지우되 **`editingId`는 남긴다** — 같이 지우면 저장할 때
같은 제목이 하나 더 생긴다. 별개로 남기려면 "새 시나리오로 저장"을 쓴다.

**스키마는 JPA가 만들지 않는다.** `ddl-auto=validate` 고정, `db/schema/*.sql`이 만든다.
인증은 JWT (`@AuthenticationPrincipal Long userId`). 소셜은 `/oauth2/authorization/{google|kakao}`
→ 성공 시 `OAUTH2_REDIRECT_URI`에 `?token=` 붙여 리다이렉트.

## 데이터 파이프라인

원본 3종은 포맷·단위·구조가 모두 다르다. `etl.py`가 블록 헤더를 감지해 파서를 분기시킨다.

| 출처 | 포맷 | 연장 | 금액 | 비고 |
|---|---|---|---|---|
| 도시철도노선정보 | xlsx | **미터** | 없음 | 역수는 `정거장구성` 문자열 split |
| 철도건설현황 | csv (**cp949**) | 없음 | **백만원** | 연장 없어 대부분 D등급 |
| 데이터.txt | txt (탭) | km | 억원 | 사업계획·도시철도/광역철도 운영현황 3종 혼재 |

**파싱 시 처리** 합계·소계 행 제외 / 병합셀로 빈 구분 열은 직전 지역명 이어받기(`서울 3호선`) /
줄바꿈 조각 행 폐기 / 물결·중점 변형 통일(`~∼〜～`, `․·ㆍ`) / 어절 중복 제거(`경부고속철도철도`) /
노선명 접미사 분리(`신안산선 복선전철`) / 두 자리 연도(`'74`→1974, `'24`→2024)

**조용히 그럴듯한 값을 내던 파싱 함정 셋** (고쳤다, 자세한 것은 `docs/research-log.md`)

- **`정거장구성` 구분자가 쉼표만이 아니다** — 47개 중 둘이 `+` 를 쓴다. 쉼표로만 쪼개
  신분당선 16역이 **1역**으로 읽혀 역간격이 33.5km 였다. 이상치 목록에 "정거장구성
  미기재로 추정" 으로 적혀 있었는데 미기재가 아니었다 — **진단이 틀린 이상치는 제외가
  아니라 파싱을 고쳐야 한다.** `·` 로는 쪼개지 말 것(`전대·에버랜드`)
- **두 자리 날짜를 `pd.to_datetime` 에 맡기면 뒤집어 읽는다** — `22.05.28` 을 DD.MM.YY 로
  보고 2028년을 준다. `parse_opened_year` 가 `parse_short_year` 로 보낸다
- **역이 하나면 역간격이 없다** — 가덕도신공항(16.5km/1역)이 복선전철 중앙값을
  4.30 → 4.97 로 밀어 올렸다. `spacing_stats` 가 `station_count >= 2` 를 요구한다

**등급 체계 — 381건 (A 42 / B 28 / C 69 / D 242)**
A = 연장+역수+금액(비용 회귀 + 역간격) / B = 연장+금액(회귀만) / C = 연장+역수(역간격만) / D = 보류

- 파생값(`cost_per_km`, `avg_spacing_km`, `data_grade`)은 DB 생성 컬럼 — 직접 INSERT 금지
- 이상치는 지우지 않고 `is_outlier=TRUE`로 제외만 (사유를 보고서에 써야 한다)
- 추정치는 `cost_status='ESTIMATED'` — 회귀 학습엔 `DISCLOSED`만 (순환 오류 방지)
- 원문 표기는 `raw_type_text`에 보존
- 출처 간 동일 사업은 등급 낮은 행 삭제 — `etl.py`의 `SAME_PROJECT`에 명시하고 남는 행
  `note`에 지운 행 원문을 남긴다. 매칭이 어긋나거나 등급이 역전되면 ETL이 멈춘다
- 역수 보강은 `rail_station_seed.csv` (사업계획엔 역수 열이 없어 광역철도가 전부 B등급이었다)

## 비용 모델 (`cost_model.py` → S5)

① log-log 회귀로 규모의 경제를 잡고 ② 연장 5~40km × 역수 0.6~1.4배 격자에서 직선 근사해
`고정비 + 연장×단가 + 역수×역당단가`로 바꾼다. 연장만 훑으면 역수가 연장에 묶여 분리되지 않는다.

`log(사업비) = 6.867 + 0.650·log(연장) + 0.575·지하비율 + 0.272·log(역수) + 수단더미`
(A등급 38건, R² 0.889, 교차검증 1.25배, 기준 수단 = 복선전철)

**수단×구조별 단가는 `db/seed/S5__cost_standard.sql` 이 원본이다** (2025년 환산 억원,
`source` 에 표본 수). A등급 2건 미만인 수단만 전체 표본 모델 + 구조·역수 보정을 쓴다.

- **역수는 log로 넣어야 분리된다.** 선형이면 연장과 겹쳐 음수(-223±225)로 튄다.
  표본의 역수/표준역수 비가 0.21~1.91로 퍼져 있어 log로는 0.272±0.086로 유의하다
- 복선전철 역당 1,176억은 표본이 GTX 대심도 위주여서다 (역간격도 4.98km로 넓다)
- **기준연도가 2025 를 넘는 행이 A등급 38건 중 19건이다 — 물가 환산이 아예 안 된다.**
  `price_index.csv` 가 1990~2025 뿐이라 `base_year` 가 2029·2032 같은 미래면 그냥 통과한다
  (`base_year_status='ASSUMED'` — 종료연도로 대신한 값이다). **"효과는 미미"를 검정했고
  참이었다**: 미래/과거 두 집단의 잔차 차이가 0.98배(t=−0.22, 검출 한계 1.17배)다.
  다만 미래 집단 **안에서는 연 +4.1% 기울기**(r=0.33, t≈1.4)가 보인다 — 경상가격이라면
  나올 모양이지만 유의하지 않다. 표본이 늘면 다시 볼 것 (`test_cost_model.py` 가 감시한다)
- **`underground_ratio` 40건이 전부 추정치인데(공식 미공표), 재 보니 생각만큼 위험하지 않다.**
  계수가 0.575 로 가장 크지만, 추정이 틀리면 **계수가 그만큼 흡수해** 예측이 덜 흔들린다.
  표본에 표준편차 0.15 짜리 잡음을 넣고 200번 다시 적합한 결과, 지하 20km 중전철 비용이
  **97.9~107.2%** (5~95%) 범위에 머물렀다. 전 표본을 한쪽으로 0.2 씩 밀어도 −2.3~+13.7% 다.
  다만 **표본 38건 중 23건이 이미 1.00 이라** 위로 미는 교란은 잘려서 표현되지 않는다 —
  위쪽 수치는 과소평가로 읽을 것.
  변수를 아예 빼면 교차검증이 1.25 → 1.28배, R² 0.889 → 0.845 로 나빠진다.
  **쓸 값어치는 있으나 없어도 치명적이지 않은 변수**다 (`etl/cost_model.py` 로 재현 가능)
- 트램 2건·BRT 저급형 3건은 표본 부족 — SQL `source`에 표시

**정확도** 연장+수단 1.45배 → +지하비율 1.29배 → +역수 **1.25배**(현재).
실제 38개 노선 대비 평균 **21% 오차**(중앙값 비율 1.03). 큰 오차는 광주 2호선 1단계(저심도)
1.93배, 대구 1호선 하양연장(기존선 병행) 1.65배, 7호선 청라연장 0.54배, GTX-B 0.60배 —
공법이 변수에 없어서다. **결과는 단일 값이 아니라 범위로 보여주고 이 오차를 보고서에 명시한다.**

**공법을 변수로 만들 수는 없다 — 표본이 없다** (다음 할 일 ⑤ 의 답). 저심도 1건 ·
기존선 병행 0건 · 지상 위주 2건이다. 급행 비용 더미도 n=4 라 과적합으로 뺐는데
n=1~2 는 말할 것도 없다. `python cost_model.py --candidates` 가 후보 변수들을 한꺼번에
가려 준다 — **넣고 싶은 변수가 생기면 넣기 전에 여기 먼저 넣어 볼 것.**

| 후보 | n | 비율 | t | 검출 한계 |
|---|---|---|---|---|
| 저심도 / 지상 위주 / 계획 사업비 | 1·2·2 | — | — | **표본 부족, 잴 수 없다** |
| 고무차륜·모노레일 | 3 | 1.13 | +0.91 | 1.31배 |
| 민자 사업 | 3 | 0.95 | −0.34 | 1.37배 |
| 차량기지 포함 | 6 | 1.09 | +1.53 | 1.13배 |
| 역간격 ≥ 4.5km | 7 | 1.04 | +0.31 | 1.28배 |
| 기준연도가 미래 | 19 | 0.98 | −0.22 | 1.17배 |
| 수도권 | 24 | 1.11 | +1.32 | 1.18배 |

**`MIN_SPLIT_N = 3` 이 작은 표본을 막는다 — 막기 전에 실제로 속았다.** `계획 사업비` 가
붙은 두 노선(7호선 청라연장·송파하남선)의 잔차가 **소수점 5자리까지 같아서**(둘 다
1.3243배, 사업비는 15,828 / 18,356 으로 서로 다른데 비율이 우연히 겹쳤다) 분산이 정확히
0 이 되고 **t 가 7.75** 로 튀었다. 두 값이 log 0.4 만 벌어져도 t 는 1.46 이다 —
"유의함"의 전부가 그 우연이었다. **작은 n 에서는 t 가 아니라 검출 한계를 볼 것.**

**물가 환산** World Bank 한국 GDP 디플레이터(2020=100, 1990~2025). `price_index.csv`가 단일
출처이고 ETL이 S4와 `total_cost_2025`를 만든다. 기준연도는 명시값 → 종료연도 → 개통연도 →
착공연도 순으로 대체하고 `base_year_status='ASSUMED'`로 구분(대부분 ASSUMED라 효과는 미미).
건설공사비지수가 더 적합하나 미적용.

## 수요 모델 (`etl/demand_model.py` → S6)

`log(일이용객) = 2.608 + 0.437·log(인구) + 0.283·log(종사자) + 1.080·log(환승노선) − 0.012·도심거리km`
(서울·수도권 514개 역, R² 0.551, **교차검증 1.75배**)

입력은 `seoul_ridership.py`(승하차 621역·좌표 784)와 `sgis_population.py`(집계구 52,584개 인구 +
행정동 종사자, 응답은 `data/cache/sgis` 캐싱). 첨두율은 `seoul_peak.py`(월 단위 613역)와
`seoul_weekday_peak.py`(일별로 평일 분리), 단면 환산계수는 `seoul_congestion.py`(혼잡도 1,671행).

**API 함정**
- **시간대별 API(`CardSubwayTime`)는 월 합계만 준다.** 비중 계산엔 지장 없다
- **같은 역이 두 번 오는 달이 있다** — 2026-07 은 621역이 두 번씩 실려 1242건으로 왔다(값은 동일).
  그대로 더하면 그 달만 두 배 가중되므로 중복을 지운다. 값이 다른 중복이면 멈춘다
- 이용객이 거의 없는 12개 행(7호선 까치산 1명 등 노선 오배정)은 자료 오류로 제외
- **일별 시간대별은 `subwSttn`** — 날짜가 있어 평일/주말을 가른다. 2024년(1~199,423행)과
  2023년이 각각 날짜 오름차순으로 붙어 있고 **날짜로 거를 수 없다** — 이분 탐색으로 원하는
  달의 시작 위치를 찾는다. **공휴일 없는 달을 골라야 한다**(기본 2024-11)
- **혼잡도는 `subwConfusion`** (같은 키). 평일/토/일 · 상하선 · 30분 단위. **1~8호선만** 있어
  9호선·경전철·광역철도는 없다
- 1량 정원 160명은 혼잡도 100% 기준. 좌석 54석 → 54/160 = 33.75% 가 데이터셋 정의
  ("좌석만 차면 34%")와 맞는 것으로 교차검증했다
- `train_operation.csv` 의 편성당칸수는 `보유칸수 ÷ 편성수` 와 맞는지 ETL 이 검사한다
  (베껴 적다 틀리는 것을 막는다). **퇴근 시격 열이 없어** 출근 시격을 대신 쓴다
- **수집 범위는 역 위치가 정한다.** `station_ridership.csv`(수도권)에 `regional_station.csv`
  (지방)를 더해 집계구 52,584 → **70,840**개로 넓혔다. 이게 없으면 지방 노선은
  "인구 자료 없음"으로 수요·B/C 가 안 나오고 정차역 이름도 번호로 떨어진다
- **환승 노선 수는 이름이 아니라 위치로 센다.** 이름만으로 묶었더니 지방 역이 들어오면서
  서울 `시청` 이 부산·대전 `시청` 과 묶여 환승이 2 → 4 로 뛰었다. 400km 떨어진 역은
  환승이 아니다. 하필 **기여가 가장 큰 변수**(계수 1.08)라 회귀가 바로 흔들렸다
  (R² 0.551 → 0.555). 같은 이름이면서 **1km 안**인 노선만 센다
- **도심거리의 기준점은 가장 가까운 광역시 도심이다** (`CBDS` — 서울·부산·대구·광주·대전).
  서울시청 하나로 고정했더니 부산 역이 326km 로 잡혀 표본 범위(0.1~88.7km)를 3.7배
  외삽했고, 도심거리 항만으로 예측이 **0.02배**로 깎여 부산 B/C 가 0.019 처럼 **숫자는
  나오지만 뜻이 없는 값**이 됐다. 고친 뒤 부산 이용객이 2,202 → 96,480명/일이 됐다.
  천안·아산 11개 역은 대전시청이 더 가까워 값이 줄지만(서울 통근권이라 논란의 여지가 있다)
  R² 0.551 → 0.552, 교차검증 1.7454 → 1.7450 으로 모델 품질은 그대로다.
  **`CostCalculator.CBDS` 와 같은 목록이어야 한다** — 어긋나면 학습과 예측이 다른 기준을 쓴다
- SGIS 는 자체 행정구역 코드를 쓴다 (11110 = 노원구). 인구·종사자 API 가 같은 체계라 이어 붙는다
- 인구가 적은 집계구는 `N/A` 로 가려서 온다. 0 으로 채우지 말고 제외해야 합산이 왜곡되지 않는다

**모델 한계**
- **인구만으로는 못 맞춘다** (R² 0.32, 1.97배). 서울역·을지로입구처럼 낮에만 붐비는 역이
  1/10 로 과소추정됐다. 종사자(주간인구 대리)와 환승 노선 수를 넣어 0.551까지 올렸다
- 기여가 가장 큰 변수는 **환승 노선 수**(계수 1.08). 종사자는 행정동 단위라 해상도가 낮아
  을지로입구는 여전히 1/6 수준으로 빗나간다
- **배차 간격이 변수에 없다.** 달월 30배, 도림천 10배처럼 한적한 지선 역을 과대추정한다
- **1.75배 오차를 안고 쓴다.** 수단 비교에서는 같은 수요를 모든 수단에 똑같이 적용하므로
  수단 선택 결과는 바뀌지 않는다. 영향받는 것은 B/C 절대값이다 — 보고서에 명시할 것

## B/C 산출 (`backend/.../calc`)

`PopulationIndex`가 집계구 인구·행정동 종사자 CSV를 0.01° 버킷에 올려 노선 반경 1km를 합산하고,
`BenefitCalculator`가 수요 모델로 일이용객 → 첨두 수요 → 통행시간 절감편익을 매긴다.
`CostCalculator`가 수단×구조 전부를 돌려 비교표(`scenario_result`)를 만들고 B/C 최대안을 추천한다.

**원단위는 「교통시설 투자평가지침」 제7판**(국토교통부 지침 2022-500호). S7 참고.

| 값 | 적용 | 근거 |
|---|---|---|
| 시간가치 7,231원/인·시 | 2025년 기준 | 표 4-44 **광역도시철도** 5,768원(2013) × CPI 1.2537 |
| 할인율 4.5% / 3.5% | 개통 후 ~30년 / 31~40년 | 6.2.1 — 철도사업 예외 |
| 분석기간 40년 | 철도 (일반 교통시설은 30년) | 6.2.2 |
| 공사기간 5년 | 투입비율 10·20·30·30·10% | 6.2.2, 표 6-1 |

- **시간가치는 등급을 맞춰 골라야 한다.** 광역도시철도는 업무통행이 4.14%뿐이라 비업무
  5,033원이 값을 지배한다. 고속철도(10,197)·일반철도(6,830)를 쓰면 과대계상이다
- **환산 지수는 CPI다**(6.2.3 (4)) — 건설비의 GDP 디플레이터와 다른 계열이다. 지침이
  2013→2020에 쓴 107.5가 World Bank 한국 CPI 비와 정확히 일치해 환산을 검증했다
- **B/C는 편익·비용 모두 현재가치**(6.3.1). 기준시점이 공사 착수 직전이라 편익은 5년 뒤부터
  시작하고 사업비는 5년에 나눠 투입된다(명목 총액의 0.874배). 화면의 건설비는 명목값이라
  표에서 편익÷건설비로 B/C가 나오지 않는다 — 각주로 안내한다
- 지침값 적용으로 B/C가 자리표시자 대비 **0.84배**가 됐다
  (시간가치 0.80 × 할인 0.91 ÷ 비용 현재가치 0.87)
- **전환 전 수단 속도는 시내버스 21.3km/h** — 국가지표체계「광역시별 승용차 및 시내버스
  평균 통행속도」(승인통계 제20109호) 2025년 6대 광역시 중앙값(`road_speed.csv`).
  서울만 보면 17.1로 느려 편익이 커지고, 승용차 기준(27.2)이면 크게 줄어든다
- **기준 속도보다 느린 수단은 편익 0이다.** BRT 저급형(18)이 시내버스 21.3보다 느려 B/C 0으로
  찍힌다. 오류가 아니라 "시내버스보다 느리면 시간을 절감하지 못한다"는 결과지만 **BRT 속도가
  아직 가정값**이라 확정할 수 없다 — 숫자를 맞추려고 올리지 말 것. 트램은 실측 22.06으로
  기준을 겨우 넘어 편익이 양수지만 km당 절감이 경전철의 13% 수준이라 B/C 가 매우 낮다
- 비교표에서 **B/C 0.00 은 계산 실패처럼 보인다** — "기준 속도 이하 — 절감 시간 없음"을 단다
- **BRT 고급형 B/C가 15배까지 튄다**(실사업은 10을 넘지 않는다). 도로 용량 잠식을 빼지 않고
  철도 시간가치를 그대로 쓰기 때문이다. 수단 간 **순위**는 의미가 있어도 절대값은 아니다
- 수요는 모든 수단에 동일하게 적용한다 (수단별 수요 탄성 모델이 없다)
- 인구 CSV 경로는 `app.census-file`·`app.worker-file`. 없으면 기동은 되고 경고만 남는다

### 첨두 단면 — 세 번 보정한다

수요 모델이 내놓는 것은 **주말이 섞인 일 평균**이라 평일 설계 첨두까지 세 단계가 필요하고,
**셋을 따로 재 둬야** 하나만 고쳐도 나머지가 조용히 어긋나지 않는다.

| 계수 | 값 | 근거 |
|---|---|---|
| `weekday_factor` | 1.1041 | 평일 일수요 ÷ 전체 평균 (주말이 평일의 68.6%) |
| `peak_hour_ratio` | 0.1159 | 평일 첨두 1시간 비중 (주말은 0.0834) |
| `peak_direction_coef` | 10.06 | K = 이 값 ÷ 연장km (아래) |
| `peak_direction_max` | 0.395 | K 의 상한 = 0.5 × 0.79(방향 쏠림 실측) |

- 앞의 둘은 `seoul_weekday_peak.py`(서울 1~8호선 평일 21일, 2024-11) 실측이다.
  **첨두 시각이 평일 8시·18시, 주말 16시로 갈린다** — 월 단위 자료로는 이게 안 보인다
- **`peak_direction_ratio` 는 방향 비중이 아니라 환산계수**다. 혼잡도는 교통카드 O/D 기반
  **재차인원**이라 역 승하차가 아니라 단면 통행량이다 (`seoul_congestion.py` → `line_congestion.csv`).
  `pphpd = 혼잡도/100 × 160 × 편성당칸수 × (60÷출근 시격)`, `K = pphpd 최대 ÷ (일 승하차 × 첨두율)`
- **직결 운행 노선(1·3·4·7호선)은 K 산출에서 뺀다** — 다른 기관 역에서 승차한 승객이 단면에
  실리지만 분모에 없어 과대로 나온다. 남은 4개(2·5·6·8호선)의 중앙값이 0.2441 이다
- **K 는 상수가 아니라 연장의 함수다** — `K = min(0.395, 10.06 ÷ 연장km)`.
  통행이 노선보다 짧으면 한 지점을 지나는 통행의 비율이 대략 (평균 통행거리 ÷ 연장)이다.
  상수로 두면 **30~60km 노선에서 잰 값을 5~35km 노선에 적용**해 짧은 노선을 과소 추정한다.
  교차검증(LOO) 오차가 상수 0.0784 → 0.0437 로 낮아졌다. 계수 둘짜리(`a + b/L`)는
  표본 4개에 과적합이라 교차검증이 오히려 나빴다(0.0737) — 한 개짜리를 쓴다
- **노선별 첨두율을 써야 관계가 보인다.** 공통 첨두율을 쓰면 노선마다 다른 첨두 쏠림
  (0.1035~0.1298)이 K 에 섞여 r=0.775 에 그친다. `seoul_weekday_peak.py` 가 노선별로
  내놓는 `line_weekday_peak.csv` 를 쓰면 **r=0.865** 로 또렷해진다
- **25.5km 아래는 전부 상한에 걸리는 외삽이다.** 표본이 30.6~59.8km 네 개뿐이라 그보다
  짧은 구간을 실측으로 받치지 못한다. 상한 0.395 는 모든 통행이 최대 단면을 지날 때의
  이론값이라 물리적으로 넘을 수 없어, 1/L 이 발산하지 않게 잡아 주는 뚜껑이 된다
- 노선별 K 값과 분해 과정(이론값 0.395 대비 단면 집중 0.62)은 `docs/research-log.md` 참고
- **실측 최대 단면은 20,403(8호선)~57,754(2호선)명/시다.** 상한 80,000 은 2호선 57,754 가
  안에 들어와 타당성을 확인했다

## 추천 기준값

**국토부 운영현황은 낡을 수 있다 — 세어 봤더니 스물한 줄 중 하나였다.** 인천 1호선이
30.3km/30역로 들어 있는데 검단연장(6.825km·3개소)이 2025-06-28 개통해 지금은 37.1km/33역이다.
같은 방식으로 여덟 노선을 의심해 봤지만 나머지는 **역수가 이미 연장분을 세고 있거나
(부산1·대구1) 아직 미개통(서울3)** 이었다. **고치지 않았다** — 중앙값이 1.065 → 1.068 로
0.003km 움직일 뿐이고, 우연히 확인한 한 줄만 바꾸면 나머지 스무 줄과 섞여 더 고르지 않다.
**여럿을 묶어 중앙값을 낼 때는 한 출처만 쓰고, 하나를 콕 집어 쓸 때는 최신을 쓴다** —
역간격·속도 자가 그래서 `rail_speed.csv` 의 운영사 값을 쓰고
`crosscheck_spacing()` 이 두 출처가 다른 노선을 매번 보고한다.

**역간격(중앙값)** 중전철 1.06km(표본 21) / 경전철 1.06km(7) / 트램 0.45~0.86km(2) /
복선전철 **2.62km**(6) / 광역급행 **6.92km**(4). **복선전철 하나였던 것을 둘로 갈랐다** —
분포가 쌍봉이라 전체 중앙값 4.30km 가 아무 노선도 없는 틈이었다(아래 「급행 분리」).
운영현황 **한 출처만** 쓴다 — 같은 노선이
여러 출처에 중복돼 전체로 집계하면 2~6번 잡힌다(`spacing_stats`). 평균이 아니라 중앙값을
쓴다(공항철도 63.8km/14역 같은 특수 노선에 끌려감).

**수송능력 상한(`pphpd_max`)** 지하철 8만 / 경전철 6.6만 / BRT 3.5만. 넘으면 탈락한다.

**수요 하한(`pphpd_min`)은 수송능력이 아니라 실제 운영 노선의 최저 단면이다.**
수송능력 범위의 하한을 "이 수단을 지을 최소 수요"로 쓰는 것은 **범주가 다른 값**이었다.
실측해 보니 6호선 21,677 · 8호선 20,403명/시로 운영 중인 중전철이 옛 하한 40,000에 못 미쳤다 —
서울 6·8호선이 "지하철을 지을 이유가 없는 노선"으로 판정됐던 셈이다.

| 수단 | 하한 | 근거 |
|---|---|---|
| 중전철 | 20,000 | 실측 — 8호선 20,403 |
| 경전철 | 4,700 | 추정 — 우이신설 4,735 / 신림 4,821. 짧아서 K 상한 구간이라 **외삽**이다 |
| 복선전철·단선전철 | NULL | 단면을 세울 근거가 없다 (아래) |
| 트램·BRT | NULL | 더 싼 철도 대안이 없어 경고가 무의미하고 국내 실측도 없다 |

NULL 이면 경고를 띄우지 않는다. **근거 없이 경고하지 않는다.**

**복선전철 하한을 세우려면 상하행 승하차가 필요하다.** 공식 자료 3종을 모두 확인했고 전부
막혔다 — **재조사 전 `docs/research-log.md` 를 볼 것.** `K` 환산은 연장에 반비례해 100km 넘는
광역철도의 단면을 과대평가하므로 쓰지 않는다. 경고 남발보다 NULL 이 낫다.

**BRT와 경전철의 구간이 겹치는데 건설비는 10~20배 차이난다** — "이 구간은 BRT면 충분한데
지하철을 지으면 B/C가 0.4로 떨어진다"를 보여주는 것이 이 프로젝트의 핵심 가치다.

**노선 길이 상한** 지하철 35km / 경전철 30 / 트램 25 / BRT 30 (`max_length_km`). 넘으면
복선전철을 후보에 추가하고 도시 수단은 "권장 연장 초과"로 표시만 한다. 대전 2호선(트램 38.8km)
처럼 상한을 넘는 실제 노선도 있다 — **상한은 금지선이 아니라 경고선**이다.

**표정속도(`speed_kmh`)** 중전철 32.4 / 경전철 29.3 / 트램 22.1 / 복선전철 47.6 /
광역급행 91.8.
노선별 표본·출처·중앙값 포함 여부는 **`data/seed/rail_speed.csv` 가 원본**이다. 평균이 아니라
중앙값을 쓴다. **트램 22.1 은 대전 2호선 설계값**이다 — 국내 운영 노선이 없다.
출처는 서울·부산교통공사 공공데이터(표정속도 직접 공표)와 각 운영사 공식 페이지다. 국토교통부
운영현황에는 속도 열이 없다. 소요시간이 있는 노선은 연장÷소요시간이 공표값과 ±0.05 안에서 맞았다.
**급행(GTX)은 이제 별도 수단이다** — 아래 「급행 분리」 참고.

**역간격이 표정속도를 설명한다** — `속도 = 18.56 + 12.65 × 역간격` (노선 18개, **R² 0.925**).
역간격 0.71~2.36km 에서 수단을 구분하지 않아도 93% 가 설명된다. **기술이 아니라 정차 횟수가
속도를 정한다.** 자는 `mode_speed_check.py` 가 만들고, **실측만** 쓴다(`FIT_BASIS`) —
설계값을 넣으면 자가 가정을 재게 된다.

**복선전철 2.62 를 운영 중 광역철도로 교차검증했다.** 한국철도공사 광역열차 운영정보
(기준일 25.1.1) 12개 노선의 역간격 중앙값이 **2.21km** 다(1.35~8.84). 우리 2.62 는
**사업계획** 6건 중앙값이라 19% 넓은데, 신설 노선이 기존선 전환보다 역을 띄엄띄엄 놓는
것으로 설명된다. **값은 바꾸지 않았다** — 두 집단은 성격이 다르다.

**역간격 2.36~4.98km 는 여전히 비어 있다 — 찾아봤고 막혔다.** 그 구간에 중앙선(2.579)·
경춘선(4.035)·경강선(4.750)·대경선(8.843)이 있지만 **코레일은 소요시간을 공표하지 않는다**
(국토부 운영현황에 속도 열이 없는 것과 같다). 2차 자료에는 있으나 기준에 못 미친다.
**재조사 전 `docs/research-log.md` 를 볼 것** — 어디를 보면 되는지 값어치 순으로 적어 뒀다.
특히 **중앙선(2.579)은 S1 의 2.62 와 거의 같아 47.6 을 직접 검증할 수 있다.**

**구간 위쪽 두 점이 어긋난다 — 설명하지 못했다.** 김포 골드라인(2.36km)이 신분당선
(2.09km)보다 **역간격이 넓은데 더 느리다**(45.08 vs 47.60). 차량 한계인가 찾아봤더니
**둘 다 운행 최고속도 80km/h** 로 같아 가설이 틀렸다. 전에 적었던 R² 0.958 은 노선 16개
짜리였고, **구간이 2.09km 에서 끊겨 있어서 나온 값**이다. 넓히니 0.925 로 내려갔다.

**신분당선 검증은 표본 밖에서 해야 뜻이 있다.** 전에 "직선에서 0.04km/h 벗어났다"고 적은
것은 **표본 안 잔차**였다 — 자기를 포함해 그은 선과의 거리다. 제대로 **빼고 적합해 예측**하면
16개 자에서 47.71 vs 실측 47.60(**+0.2%**)으로 오히려 더 강한 검증이었다. 다만 18개 자에서는
−7.9% 다 — 위 어긋남 때문이고, 검증이 **좁은 구간에서만 성립했다**는 뜻이다.

**단 포화한다 — 급행은 이 직선 위에 없다.** 역간격 6.92km 에서 예측 106.2 vs 실측 91.8
(**0.86배**). BRT 기울기(+10.6)가 철도(+12.7)보다 완만한 것도 같은 방향으로 읽힌다.
다만 **차량 최고속도로 설명하려던 시도는 실패했다**(위 참고) — 포화의 기제는 아직 모른다. **급행을 적합 표본에 넣지 말 것** — 포화를 보이려면 포화한 점이
표본 **밖**에 있어야 한다. `mode_speed_check.load_pairs` 가 `SATURATED_MODES` 로 빼고
`express_speed()`/`express_spacing()` 이 따로 내놓는다(테스트가 감시한다).

### 급행 분리 — 복선전철을 둘로 갈랐다 (다음 할 일 ②·⑧ 완료)

**복선전철 한 행이 세 곳에서 온 값을 갖고 있었다.** 역간격은 10개 노선 전체 중앙값
4.30km, 속도는 신분당선 하나(47.6, 그 노선 역간격 **2.09km**), 비용은 A등급 11건 회귀.
역을 4.30km 간격으로 놓고 2.09km 간격 노선의 속도를 쓴 셈이라 회귀식과 **−35%** 어긋났다.
뿌리는 **쌍봉 분포**다 — 중앙값은 "가운데 값"이지 "대표값"이 아니다. 봉우리가 둘이면
가운데는 골짜기이고, 4.30 자리에는 **아무 노선도 없었다**.

| | 역간격 | 속도 | 회귀와 | 근거 |
|---|---|---|---|---|
| 복선전철(일반 광역) | 2.62 | 47.6 | **−8%** (전 −35%) | 신분당선 — 이제 같은 집단 |
| 광역급행(`EXPRESS_RAIL`) | 6.92 | 91.8 | −14% (포화 구간) | GTX-A 두 구간 중앙값 |

**전체 이야기는 `db/seed/S1__mode_capacity.sql` 주석에 있다** — 쌍봉 분포 그림, 비용을
가르지 않은 이유, `EXPRESS_RAIL` 이 `reference_line` ENUM 에 없는 까닭, 급행 속도 n=2 의
기준이 섞인 사정까지. **값을 고칠 사람이 실제로 여는 파일이 거기다.** 요약하면 —
비용은 안 갈랐고(잔차 1.02배, t=+0.12), **검출 한계가 1.50배라 이 검정은 어느 쪽도 가리지
못한다.** 안 가른 진짜 이유는 표본 4개에 더미를 붙이는 과적합이다. 역간격 2.1~4.9km 에
실측 속도가 없어 "봉우리가 둘뿐"임은 확인할 수 없다.
검사·재현 `cd etl && python mode_speed_check.py` (값은 고치지 않는다).

**`cost_model.SPACING` 은 S1 의 `spacing_km` 과 같아야 한다 — ETL 이 검사해 멈춘다.**
실제로 4.98 vs 4.30 으로 어긋나 있었다. 막는 이유는 정확도가 아니라(직선 근사 오차가
0.79% vs 0.95% 로 둘 다 1% 안이었다) **같은 값이 두 곳에서 다르면 어느 쪽이 맞는지 알 수
없기 때문**이다.

**S5 는 지우지 않고 내린다**(`is_active=FALSE`). `scenario_result.standard_id` 가 FK 로
참조해 `DELETE` 도 `TRUNCATE` 도 막히고, 내려 두면 **저장된 B/C 가 어느 기준값으로
계산됐는지** 남는다. 백엔드는 `findByActiveTrue()` 로 읽으므로 계산에는 안 쓰인다.

### BRT 표정속도 — 아직 가정값이다

고급형 25.0 / 저급형 18.0 이 **가정값**이고, 저급형이 기준 수단(시내버스 21.3)보다 느려
**편익이 항상 0** 으로 찍힌다. 공식 실측을 6곳에서 찾아 전부 막혔고, 세종시 시간표는
기점 출발시각만 있고 정류장별 도착시각이 없다 — **옮겨 적을 소요시간 자체가 없다**
(전에 "이미지라 못 읽는다"고만 적고 될 것처럼 남겨 뒀던 길이다).

그래서 **실시간 차량 추적으로 직접 재고 있다**(`etl/sejong_brt_speed.py`). 세종 BIS 가
차량 위치와 노선 선형을 줘서 연장까지 직접 계산된다(B1 편도 51.9km 가 `brt_seed.csv` 의
53.0km 와 2% 안에서 맞았다). **측정 방법·함정·바꿀 기준은 `docs/research-log.md` 에 있다 —
재조사 전에 볼 것.**

- **바꿀 조건 넷을 결과 보기 전에 정해 뒀다** — 대표성(평일 첨두 대조군이 공표 대전 21.6
  의 ±20% 안) / 표준오차 3% 이하 / 평일 첨두·보통 채움 / 구간 표본을 묶을 수 있음.
  **넷을 모두** 만족해야 바꾼다. 핵심은 **모델이 필요한 것은 연평균인데 이 측정은 시간대
  조각**이라는 것이고, 대조군이 공표 연평균으로 달리는 시간대가 곧 평균적 교통 조건이다
- **아직 `speed_kmh` 에 넣지 않았다.** 가정값을 실측값으로 바꿔 적으면 출처가 "실측" 이
  되어 다음 사람이 의심하지 않는다 — 가정값으로 남겨 두는 것보다 나쁘다
- **"측정 BRT ÷ 일반버스 치우침" 보정은 쓸 수 없다.** 그러려면 둘이 혼잡에 똑같이 민감해야
  하는데 그건 BRT 의 존재 이유를 부정한다. 빈 도로에서는 전용차로가 아무것도 사 주지
  않는다 — **BRT 편익은 혼잡 구간에서만 나온다. 이것 자체가 보고서에 쓸 발견이다**
- **같은 전용도로에서 역간격이 표정속도를 지배한다** — 1km 늘 때 **+10.6km/h**
  (B5 0.63km→28.2 … B3 2.73km→56.3). 노선마다 신호·차로가 달라 상한으로 읽을 것.
  **이 발견을 철도에 옮겨 보다가** `rail_speed.csv` 가 역간격으로 거의 완전히 설명된다는
  것(R² 0.925)과 복선전철의 역간격·속도가 서로 다른 노선 집합에서 왔다는 것을 찾았다 —
  BRT 를 재려다 모델의 더 큰 문제를 찾은 셈이다
- **수집을 걸기 전에 `--preflight` 를 돌릴 것.** 수집은 2~3시간짜리 예약 작업이라
  **API 나 선형이 바뀐 것을 새벽 6시 50분에 알면 그날을 날린다.** `--report` 는 요일 ×
  시간대 격자의 빈 칸을 보여 준다. **대조군(1005)은 BRT 와 같은 시간대에 함께 돌릴 것**
- 남은 길은 **운영기관 문의**(세종도시교통공사 044-850-0125)다 — 공표값이 있으면 특정
  시점 실측보다 그쪽이 낫다. **숫자를 맞추려고 추정값을 넣지 말 것.**

**구조 형식(지하/고가/지상)** 수단보다 비용을 더 크게 가르는 변수다(같은 경전철이 고가 401억,
지하 637~836억/km). `cost_standard`는 "수단 × 구조" 조합. 기본값은 수도권 도심 지하, 그 외
고가(`preferred_structure`). 트램은 지상 전용. **어떤 구조도 막지 않는다** — 지방에서 지하를
골라도 고가 대비 얼마가 더 드는지 보여준다. **선택을 막는 대신 대가를 보여주는 것**이
이 서비스의 방식이다.

**규제 구역(`restricted_zone` 12건)** 문화재·상수원 `REVIEW`, 군사 통제보호구역 `BLOCKED`.
**좌표·반경 모두 근사치**라 단정하지 않고 "확인 필요"로만 안내한다. 철도보호지구는 넣지
않는다 — 신고·협의 대상이지 금지가 아니고, 넣으면 도심 대부분이 막힌다. 정식 경계는
국가문화유산포털·물환경정보시스템·국토정보플랫폼에서 받아 교체할 것.

**경고 문구(`scenario_result.warning`)** 경고는 계산을 막지 않는다. 유일한 탈락 조건은
수송능력 초과(`is_feasible=FALSE`)이며 이때도 행은 남긴다.

| 상황 | 문구 |
|---|---|
| 연장 > `max_length_km` | 권장 연장 초과 — 복선전철 대안 참고 |
| 첨두 수요 > `pphpd_max` | 수송능력 초과 (`is_feasible=FALSE`) |
| 첨두 단면 < `pphpd_min` | 과잉 투자 검토 — 실제 운영 노선 최저 수준 미달 |
| 지하 선택 | 고가 대비 +N억 / B/C 변화 |
| 규제 구역 반경 내 | 규제구역 인접 — 확인 필요 |

### 정차역 자동 배치 (`StationPlanner`)

**반경 500m 안에 한 명도 없으면 역으로 세지 않는다 — 강·호수·바다가 그렇다.**
집계구가 없어 **이름도 못 짓고**(`name` 이 null) **이용객도 0** 인데, 창 안 모든 후보가
0 점이라 "동점이면 이상 위치" 규칙이 걸려 **수면 한가운데 이름 없는 역**이 그대로 찍혔다.
송도~영종도(바다 14km)를 그리면 15역 중 **8역**이 그랬고, 좌표가 완벽히 균등한 것
(37.42193 → 37.42971 → 37.43750)이 "한 번도 안 움직였다"는 증거였다.

- **옮기는 게 아니라 빼는 것이 맞다.** 창이 역간격의 ±35%(중전철 ±370m)뿐이라
  넓은 수면에서는 **밀어낼 뭍이 창 안에 없다.** 실제 교량·하저터널에도 중간역이 없다.
  고친 뒤 송도~영종도 15 → **7역**, 춘천~양구(소양호) 32 → **8역**이 됐다
- **종점은 뺄 수 없다.** 사용자가 찍은 설계 의도이고 양 끝이 사라지면 노선이 아니다.
  그래서 양구 쪽 종점은 인구 0·이름 없음인 채로 남는다 — 이건 결함이 아니다
- **"인구 0" 과 "인구를 모름" 은 다르다** (`PopulationIndex.hasCensus()`). 집계구 파일이
  없으면 모든 자리가 0 이라, 가드가 없으면 **종점 둘만 남고 역이 전부 사라진다.**
  변이로 확인했다 — 이 가드를 빼면 테스트 4개가 깨진다
- **비용은 추정 역 수가 아니라 실제로 놓인 역 수로 매긴다.** 짓지도 않을 역의 값을 물리면
  안 되고 화면의 역수와도 어긋난다. 무인 구간도 같이 걸러지는데 그 역시 역 자리가 아니다
- **왜 역이 적은지 화면에 적는다** — `N곳은 인구가 없어 역을 놓지 않았습니다 (수면·무인
  구간)`. 33km 노선에 역이 8개뿐인 결과가 실제로 나오는데, 말해 주지 않으면 "계산이
  덜 됐나" 로 읽힌다. `warning` 이 **VARCHAR(200)** 이라 짧게 쓴다(최악 168자)
- **못 하는 것 둘** — 교량·하저터널 **할증이 없다**(`cost_standard` 는 수단 × 구조뿐이라
  한강을 건너는 지상 1km 와 평지 1km 가 같은 값이다). 그래서 **"다리 vs 우회" 중 어느 쪽이
  싼지 견줄 수 없다.** 그리고 **우리는 선형을 바꾸지 않는다** — 그린 선이 설계 의도이고,
  우회할지는 사용자가 정할 일이다. "이 구간은 물 위입니다" 를 말하려면 물 폴리곤 자료가
  따로 있어야 한다(OSM `natural=water`·`waterway=riverbank` 로 받을 수 있는 것은 확인했다)

① 역수만큼 노선을 균등 분할해 이상 위치를 잡고 ② 그 주변 창에서 **반경 500m 인구가 가장 많은
지점**으로 옮긴다. 균등 분할만 하면 역이 논밭 한가운데 놓인다. 창은 역간격의 ±35%이고 앞 역과
최소 50% 간격을 지킨다 — 풀면 역이 한 덩어리로 뭉친다. 실제 간격은 0.6~1.9km로 퍼진다.
인구는 **고정 반경 안의 합**으로 센다(집계구 크기가 제각각이라 밀도 비교가 되게).

- **역수는 `연장 ÷ 역간격`이다.** 역간격 자체가 `연장÷역수`로 측정됐으므로 같은 정의를 뒤집어
  쓴다. `+1`(간격 수 기준) 공식도 시험했으나 실제 역수를 더 잘 맞히지 못했다
  (중전철 평균오차 9.55 vs 10.07). 배치 간격은 `연장÷(역수-1)`이라 명목보다 조금 넓다
- **역명은 집계구의 행정동명**이다. 경계 응답(`adm_nm`)에 이미 있어 추가 호출 없이
  `census_population.csv`에 담았다. 같은 동에 역이 둘이면 뒤에 번호를 붙인다
- 예상 이용객은 노선 전체 이용객을 **역세권 인구 비율로 나눈** 근사다 (역별 회귀가 아니다)
- **종점은 사용자가 찍은 점에 고정**한다. 출발·도착은 설계 의도라 옮기지 않는다
- 역 배치는 역간격이 같으면 같으므로 **수단당 한 번만 계산**해 지하·고가가 함께 쓴다
- **인구 점수는 계단 함수다.** 봉우리가 이미 반경에 들어와 있으면 더 다가가도 점수가 같고,
  그때는 이상 위치에 머문다. 창 안을 0.1km 간격으로 훑되 **이상 위치를 먼저 재 둔다** —
  그러지 않으면 격자가 이상 위치를 비껴가 인구가 없는 구간에서도 역이 수십 m 밀린다(테스트 고정)
- 한계: 환승·지형·용지를 보지 않는다. 인구 자료가 없으면 균등 분할 그대로다.
  업무지구 종점(시청 등)은 거주 인구가 적어 이용객이 낮게 배분된다

### 기존 노선 활용 (`ExistingLineFinder`)

예타도 신설안만 보지 않고 기존 시설 활용안과 비교한다. 이미 전철이 다니는 길에 또 짓는 안이
비교표 1위로 올라오면 그 결과는 쓸모가 없다.

**좌표 출처가 둘이고 섞지 않는다.** 신뢰도와 갱신 주기가 달라 파일을 따로 두고 각각 읽는다
(`app.station-file`, `app.regional-station-file`). 한쪽이 없어도 나머지 범위는 그대로 동작한다.

| 범위 | 파일 | 출처 |
|---|---|---|
| 수도권 39개 노선·784역 | `station_master.csv` | 서울 열린데이터광장 (`seoul_ridership.py`) |
| 지방 10종·271역 | `regional_station.csv` | **OpenStreetMap** (`osm_regional_stations.py`) |

**OSM 은 집단 편집 자료라 그대로 믿지 않는다.** 국토교통부 운영현황 역수와 대조해
±2 를 넘게 어긋나는 노선은 **저장하지 않는다**. 실제로 첫 수집본은 10개 노선 전부가
미달이었다(99역 / 공식 271역) — 관계 멤버만 긁어서 생긴 일이고, 검증이 없었다면
반쪽짜리 좌표가 들어가 판정이 조용히 빗나갔을 것이다. 수집에서 밟은 함정 네 가지는
`etl/osm_regional_stations.py` 머리말에 적어 뒀다.

공공데이터포털·국가철도공단의 전국 역사 정보는 **서비스키가 필요**해 쓰지 못했다
(`.env` 의 `KAKAO_REST_KEY` 도 비어 있다). 키가 생기면 OSM 보다 그쪽이 낫다.

**Overpass 본진이 자주 504 를 낸다.** 슬롯이 비어 있어도 나므로 속도 제한이 아니라 질의
비용 문제다. 그래서 검증을 통과한 노선을 `data/cache/osm` 에 노선별로 캐싱하고, 다시
돌리면 못 받은 노선만 묻는다 — **한 번에 안 끝날 수 있고, 여러 번 돌려 캐시를 채우는 것이
정상 사용법이다.** 산출물(`regional_station.csv`)은 저장소에 넣는다. 받기만 하면 자료는
정확한데 받는 과정이 불안정해서, 쓰는 사람이 이 고생을 다시 할 이유가 없다.

판정은 **두 가지를 모두** 만족해야 한다 — 출발·도착이 그 노선 역에서 1km 안이고,
노선을 0.5km 간격으로 훑은 점의 **80% 이상**이 역 1km 안.
양 끝만 보면 전혀 다른 경로로 돌아가는 노선까지 걸리고, 겹침 비율만 보면 일부만 스치는 노선이
걸린다. **겹침 기준을 0.6 으로 뒀다가 테스트에서 걸렸다** — 반경 1km 역 무리가 양 끝에만
있어도 4km 노선의 67%가 덮인다. 실제로 겹치는 노선은 0.9를 넘어 0.8이면 둘을 가른다.

단정하지 않고 "활용 검토"까지만 안내한다 — 선형이 아니라 역 위치로만 재고, 지방 좌표는
집단 편집 자료에서 왔기 때문이다. 지방 신설 노선과 미개통 노선은 범위 밖이다
(운영현황 명단에 없으면 받지 않는다 — 없는 노선을 활용하라고 할 수는 없다). 버스는 범위 밖. 검증: 2호선 강남~잠실 위에 그리면 "기존 2호선 활용 검토(100%)",
시청~삼성~강남 대각선(여러 노선 가로지름)은 안내가 뜨지 않는다.

**수정 저장(`PUT`)이 늘 500 이었다.** `route_point` 에 `uk_point_seq(scenario_id, sequence)`
가 있는데 Hibernate 는 한 flush 에서 **INSERT 를 DELETE 보다 먼저** 보낸다 — 옛 0번 점이
남은 채 새 0번을 넣어 1062 가 났다. 재계산(`uk_result_mode`)과 같은 함정이라 같은 방법
(지우기 → `flush` → 넣기, `Scenario.clearPoints()`)으로 푼다. **자식 컬렉션을 통째로 바꾸고
그 자식에 유니크 키가 있으면 언제나 이 함정이다.**

### 도시 간 거리 — 기존 KTX (`IntercityRailFinder`)

`ExistingLineFinder` 는 역간격 1km 안팎의 도시철도 판정이라 KTX 에는 절대 안 걸린다.
인천~세종(120km)을 그리면 지하철 역 60개를 찍어 놓고 광명~오송 KTX 가 이미 있다는 말을
못 했다. 노선이 **도시철도 권장 연장 최댓값(`max_length_km`, 지금 35km)** 을 넘으면
같은 KTX 노선의 두 역을 찾는다 — 출발·도착에서 각각 **20km 안**이고, 두 역 사이가 출발~도착
직선거리의 **절반 이상**. 인천~세종은 "기존 KTX 경부선·경전선·전라선·호남선 활용 검토 —
광명역(출발에서 16km) ~ 오송역(도착에서 16km)". 도시철도 안내가 걸리면 그쪽이 우선이다.

**기존 수단은 비교표의 한 줄이다 (`ExistingOptions`).** 전에는 이 둘의 결과가 **표 위
경고 문구**로만 떠 있었다. 서울~부산(340km)을 그려 보면 그게 왜 모자란지 바로 보인다 —
추천이 **340km BRT 고급형(B/C 7.83)** 이고 그 아래로 트램 396역·지하철 42조가 늘어서는데,
정작 **이미 KTX 가 있고 추가 건설비가 0** 이라는 가장 중요한 비교 대상만 표 밖에 있었다.
**비교는 표에서 일어난다.** `tfoot` 의 참조 행으로 붙이고, 시나리오 비교 화면에는
「이미 있는 수단」 행으로 넣는다.

- **`scenario_result` 에는 넣지 않는다.** `structure_type` 이 `NOT NULL ENUM` 이라
  기존 KTX 에 지하/고가/지상 중 하나를 억지로 붙여야 하고, 건설비 0 이라 수요를 못 구한
  노선에서는 그 행이 **"가장 싼 안"으로 강조**된다. 정렬·행 클릭(정차역 그리기)에도
  끼어든다 — 계산 결과가 아닌 것을 계산 결과 표에 넣으면 생기는 일이다
- **저장하지 않고 응답할 때마다 다시 찾는다.** 구조를 컬럼으로 늘리려면 스키마를 고쳐야
  하고 그러면 `down -v` 가 필요해 **가입 계정과 시나리오가 사라진다.** 판정은 노선 좌표와
  역 좌표 CSV 만으로 정해지는 순수 함수이고 역이 1,124개뿐이라 매번 찾는 편이 싸다.
  `scenario.existing_line`(VARCHAR 150)은 계산 시점 기록으로 그대로 남긴다
- **계산 전에도 나온다** — 저장하자마자 "이미 KTX 가 있다"가 보여야 한다. 계산을 눌러야
  알게 되면 그 전에 이미 수단을 고르고 있다
- **소요시간 칸은 지금 비어 있다 — 구할 수 없어서가 아니라 아직 안 받아서다.**
  파일 데이터에는 시간표가 없다(「열차정보」는 차량 연결 순서, 「KTX 운임표」는 운임).
  한 열차의 시각을 "KTX 소요시간"으로 적으면 안 된다 — 서울~부산이 열차마다 2시간
  18분~2시간 40분이고 무정차는 2시간 10분대라, 출처만 "공표값"이 되고 기준은 뒤섞인다
  (세종 S-BRT 의 35km/h 를 쓰지 않은 것과 같은 이유)
- **B/C 도 비운다.** 이미 지어진 시설에 B/C 를 매기는 것은 신설안과 범주가 다르다
- **거의 같은 거리면 고속선 역을 고른다 (`HIGH_SPEED_SLACK_KM = 2.0`).** 전에는
  서울시청~부산시청의 종점이 **부산역이 아니라 구포역**이었다 — 부산시청에서 구포
  7.67km, 부산역 7.73km 로 구포가 **60m** 더 가깝다. 틀린 답은 아니지만(구포도 KTX
  정차역이다) 좌표가 OSM 에서 와서 **편집 한 번에 답이 뒤집힌다.**
  가장 가까운 역보다 2km 안에 고속선 역이 있으면 그쪽을 쓴다
  - **"무조건 고속선" 이면 안 된다 — 고치기 전보다 나빠진다.** 서울역은 선로 계통이
    `경부선`(재래선)이고 광명역이 `경부고속` 이라, 여유를 없애면 서울시청에서
    **1.5km 떨어진 서울역을 두고 17km 떨어진 광명역**을 안내한다. "가까움" 을 이기지
    않는 **동점 처리**로만 쓴다 (테스트 둘이 양쪽을 다 막는다 — 여유를 없애면
    두 개가 깨진다)
  - 2km 는 판단값이다. 막으려는 것은 정확도가 아니라 **좌표 잡음이 답을 정하는 것**이다
  - 확인: 서울~부산 `부산역` / 서울~광주 `광주송정역` / 서울~대구 `동대구역` /
    인천~세종 `광명~오송`(그대로)
- **소요시간은 이 자료로 못 채운다 — 「열차운행정보」 API (15125762) 가 필요하다.** 응답에
  `역명·정차구분명·열차출발일시·열차도착일시` 가 있어 **열차별 구간 소요시간**을
  한 열차의 값이 아니라 **분포(중앙값·범위)로** 적을 수 있다. 역별 정차 횟수도 함께
  나오므로 위 고속선 우선 규칙을 운행 편수로 바꿔 받칠 수도 있다. **활용신청은 자동승인**
  이다 — 이 파일의 "서비스키가 필요해 쓰지 못했다"(전국 역사 정보)를 보고 인증키를
  막힌 길로 읽었던 것이 틀렸다. **"자료가 없다"와 "내가 키를 안 받았다"는 다른 말이다.**
  다만 중간 정차역마다 시각이 붙는지는 **아직 호출해 보지 않았다** — `research-log.md` 참고

**노선-역은 공식, 좌표는 OSM 이다** (`etl/korail_ktx_stations.py` → `ktx_station.csv`).

- 노선-역 관계는 「한국철도공사_KTX 노선별 역정보」(공공데이터포털 15127571). **순번을 선형
  순서로 읽지 말 것** — 경부선이 `동대구 > 포항 > 경주 > 울산 > 경산` 처럼 지선을 오간다.
  "그 노선 열차가 서는 역의 모음"으로만 쓴다
- **공식 좌표(「역 위치 정보」 15127532)는 검증용이다 — 품질이 낮다.** 69역 중 51역은 OSM 과
  1km 안에서 맞지만 8역이 크게 어긋나고 **틀린 쪽은 공식 값이다**(`행신` 이 인천 앞바다,
  `구례구` 35.0·127.0 자리표시자, `마산`·`창원` 25km 서쪽). 10역은 공식 좌표가 없다.
  어긋남은 `coord_check` 열에 남는다
- **OSM 운행 계통(`route=train`)은 쓰지 않는다** — 정차역이 크게 빠져 있다(`경부선 KTX
  서울 → 부산` 에 4역). 선로 관계(`route=railway`)에는 경부선·호남선 같은 간선이 아예 없다
- OSM 에서 도시철도 역은 빼되 **`train=yes` 면 남긴다** — Korail `동대구`·`경산` 이 대경선
  때문에 `station=subway` 로 찍혀 있어 처음엔 통째로 빠졌다. 같은 이름이 여럿이면(`판교`
  성남·서천) 같은 노선의 다른 역에 가까운 쪽을 고른다
- **선로 계통은 세 번째 출처에서 온다** — 「KTX 정차역 최초 개통일」(15126723). 역마다
  `선명` 이 `경부고속`/`경부선` 으로 갈려 있어, 노선별 역정보만으로는 안 보이던 **고속선
  13역 / 재래선 56역** 구분이 생긴다. `official_line` 열에 남긴다
  - **`line_name` 을 이걸로 바꾸면 안 된다.** 서울은 `경부선`, 부산은 `경부고속` 이라
    묶음이 갈려 "서울~부산을 잇는 KTX" 를 못 찾게 된다. 타고 갈 수 있는지를 묻는
    데 맞는 묶음은 ①의 "그 노선 열차가 서는 역의 모음" 이다 (테스트가 감시한다)
  - `간선열차` 는 저장하지 않고 **KTX 가 서는지 검사**하는 데만 쓴다. **대소문자를 가리지
    말 것** — `덕소` 한 곳만 소문자 `ktx` 라 처음에 "덕소에 KTX 가 없다" 고 잘못 봤다
  - **이 자료의 역명이 더 오래됐다**(2024-02). `신경주`·`물금역`·`판교` 로 적혀 있는데
    ①(2025-11)과 OSM 은 `경주`·`물금`·`판교(경기)` 다. **맞추기만 하고 이름은 ① 을 쓴다**
    (`OPENED_ALIASES`). 못 맞추면 ETL 이 멈춘다 — 조용히 비면 열은 남아 있어
    "전부 재래선" 처럼 읽힌다
  - **대표역 선택에 쓴다** — 아래 「고속선 우선」 참고
- 공공데이터포털 **파일 데이터라 인증키가 필요 없다**
- 한계: **SRT(수서·동탄·평택지제)와 일반철도(무궁화·ITX)는 없다.** 운행 횟수·소요시간도
  보지 않는다 — "활용 검토" 까지만 안내한다. 20km 는 판단값이다(인천 도심~광명역 16km)

**권장 연장을 넘는 수단의 정차역은 기본으로 그리지 않는다.** B/C 최고안을 그대로 그렸더니
인천~세종에서 권장 30km 인 BRT 가 뽑혀 역 60개가 지도를 덮었다. 기본은 **권장 연장 안**의
B/C 최고안이고, 없으면 선만 그린다. 표에는 그대로 남고 행을 누르면 그린다 — 선택을 막지
않는다. 표의 강조도 지도에 실제로 그린 안을 따른다(둘이 다른 안을 가리키면 안 된다).

## 화면

**화면에서만 쓰는 규칙은 `frontend/CLAUDE.md` 로 옮겼다** (선형 클릭, 패널 폭, `BcChart`,
인구밀도 3D 렌더링, `ComparePage`). 아래는 **백엔드와 공유하는 계약**이라 여기 둔다 —
화면 세션에서만 보이면 백엔드를 고칠 때 어긋난다.

**인구밀도 3D 범위 질의** `GET /api/reference/population?minLat..` 이 **화면 범위만** 준다.
집계구 5만 칸을 전부 보내면 수 MB 라, 객체가 아니라 `[위도, 경도, 인구]` 배열로 보낸다
(키 이름이 응답의 절반). 서울 범위 9,618칸 423KB, gzip 166KB (`server.compression`).

**관리자 기준값 CRUD(`/api/admin/**`, ROLE_ADMIN)** 편익 원단위(`benefit_parameter`)와 수단
기준값(`mode_capacity`)을 화면에서 고친다. 저장 즉시 다음 계산부터 적용된다.

- **근거(`source`)를 반드시 함께 받는다.** 비우면 400 이고 화면에서도 저장 버튼이 막힌다.
  이 프로젝트에서 값보다 중요한 것이 출처다 — 숫자만 바꾸면 어디서 온 값인지 모르게 된다
- 추가·삭제는 없다. 목록은 ETL·시드가 만들고, 행이 사라지면 계산이 바로 멈춘다
  (`Params` 가 없는 키에 예외). 바꿀 수 있는 건 값과 근거뿐이다
- **수단 기준값은 빈 칸이 "안 바꿈"이 아니라 "지움"이다** (`pphpd_min` 은 NULL 이 정상)
- `demand_*` 는 회귀 결과다. 손으로 고치면 모델과 어긋나므로 화면에 경고를 띄운다
- 하한 > 상한이면 400 으로 막는다
- **저장 실패는 실패한 행에 붙여 보여 준다.** 기준값이 25행(원단위 17 + 수단 8)이라 한 화면에
  안 들어간다. 맨 위에 띄우면 아래쪽 행을 저장했을 때 **화면 밖에 그려져 저장 버튼이 먹지 않는
  것처럼 보인다.** 불러오기 실패만 위에 띄운다
- **근거 칸이 값 칸보다 넓어야 한다.** 같은 폭을 주면 두 자리 숫자가 200px 를 쓰고 문장인
  근거가 잘린다. 값은 고정 폭, 남는 폭은 근거가 먹는다
- '저장함' 표시는 3초 뒤 지운다 — 계속 남으면 '지금 저장했다'는 말이 거짓이 된다

**낡은 결과 알림** 기준값을 고쳐도 **이미 계산해 둔 B/C 는 그대로 남는다** — 아무 말 없이
보여 주면 근거가 바뀐 숫자를 인용하게 된다. `scenario.calculated_at` 과 `mode_capacity`·
`benefit_parameter` 의 `updated_at` 최댓값(`GET /api/reference/updated-at`)을 견줘 기준값이 더
나중이면 "다시 계산해 주세요"를 띄운다. 비교 화면에서는 "기준값 변경됨".

## 프로젝트 한계 (보고서에 명시)

**한계를 적을 때는 "무엇을 모르는지"와 "그래서 결과를 어떻게 읽어야 하는지"를 함께 쓴다.**
"표본이 적다"만 적으면 읽는 사람이 결과를 얼마나 믿어야 할지 모른다.

**모델 구조**
- 통행배정모형·OD 설문 대신 인구밀도 기반 회귀 근사 → **상대 비교 지표**로만 의미
- 편익은 통행시간 절감 중심 (차량운행비·사고·환경비용 제외)
- 지역별 지가 보정계수 미적용 / 공법(저심도·기존선 병행) 변수 없음
- BRT의 도로 용량 잠식 효과 미반영 — BRT의 B/C가 유리하게 나오므로 결과 화면에 표시
- 수요는 모든 수단에 동일 적용 (수단별 수요 탄성 모델이 없다)

**오차 크기** — 비용 1.25배 / 수요 1.75배 (둘 다 교차검증). **절대값이 아니라 순위를 읽는다.**
수단 비교에서는 같은 수요를 모든 수단에 적용하므로 **수단 선택 결과는 이 오차에 안 흔들린다.**

**"없다"가 아니라 "못 본다"인 것들** — 이 구분이 보고서에서 중요하다
- **급행 비용을 복선전철과 가르지 않은 이유**는 차이가 없음을 보여서가 아니다.
  급행 n=4 라 **검출 한계가 1.50배**이고, 그보다 작은 차이는 이 표본에서 보이지 않는다.
  안 가른 진짜 이유는 표본 4개에 더미를 더 붙이는 것이 **과적합**이기 때문이다
- **공법 변수를 넣지 않은 이유**도 같다 — 저심도 1건·기존선 병행 0건·지상 위주 2건이라
  변수가 아니라 그 노선 한 줄이 된다 (`python etl/cost_model.py --candidates`)

**표본이 얇은 값** — 쓰되 얇다고 적는다
- **BRT 2종(고급 25.0 / 저급 18.0)은 가정값**이다. 저급형이 기준 수단(시내버스 21.3)보다
  느려 **편익이 항상 0** 으로 찍힌다 — 오류가 아니라 가정값의 결과다
- **트램 22.1 은 대전 2호선 설계값**이다. 국내 운영 노선이 없다
- **광역급행 91.8 은 n=2** 이고, 그중 운정중앙~서울역 90.14 는 발표 시점에
  **영업시운전 중**이라 운행 실적이 아니다 (둘이 3.6% 안에서 맞긴 한다)
- `underground_ratio` 40건이 **전부 추정치**(공식 미공표). 민감도를 재 보니 예측 흔들림은
  ±7% 수준이다

**물가 환산** — A등급 38건 중 **19건의 기준연도가 2025를 넘어**(종료연도로 대신한 `ASSUMED`)
물가지수 범위 밖이라 **환산이 일어나지 않는다.** 두 집단의 잔차가 갈리지 않는 것은 확인했다
(t=−0.22). 건설공사비지수가 더 적합하나 미적용.

**역간격-속도 관계의 유효 범위** — `속도 = 18.56 + 12.65 × 역간격` 은 **0.71~2.36km 에서만**
성립한다(R² 0.925). 그 밖은 포화해 예측이 과대하다(급행 0.86배). 구간 **위쪽 두 점끼리도
어긋나는데**(김포 2.36km 가 신분당선 2.09km 보다 느리다) 까닭을 설명하지 못했다 —
차량 최고속도는 둘 다 80km/h 로 같았다. **역간격 2.36~4.98km 에 실측이 없다.**

**자료 신선도** — 국토부 운영현황이 연장 개통을 늦게 반영한다(인천 1호선이 검단연장 전
기준이었다). 여럿을 묶어 중앙값을 낼 때는 **한 출처만** 쓰고, 하나를 콕 집어 쓸 때는 최신을
쓴다. 총사업비 미공개 노선은 역간격 산출에만 쓴다.
