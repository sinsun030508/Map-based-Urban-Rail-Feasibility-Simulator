# 엔지니어링 노트 — 왜 그렇게 정했는가

**`CLAUDE.md` 에서 떼어 낸 본문이다.** 그 파일이 900줄까지 자라 매 세션 통째로 읽히던
것을 100줄 아래로 줄이면서, **한 줄도 버리지 않고** 여기로 옮겼다.

- `CLAUDE.md` — 지켜야 할 **규칙과 값** (짧게 유지한다)
- **이 파일** — 그 값이 어디서 왔고 무엇에 데였는지 (길어도 된다)
- `docs/research-log.md` — 막힌 길과 재조사 안내 (**다시 찾기 전에 볼 것**)
- `frontend/CLAUDE.md` — 화면에서만 쓰는 규칙

숫자를 고칠 때는 **두 파일을 같이** 고친다. `etl/test_docs_match_code.py` 가
`CLAUDE.md` 쪽만 감시하므로, 이 파일이 조용히 낡을 수 있다.

---

## 왜 웹 전용인가

지도 설계와 결과 비교에 큰 화면이 필요하고, deck.gl 3D 가 모바일에서 불안정하며,
사용 맥락이 "앉아서 검토하는" 일이다. Kakao/Naver Map 은 주소 검색·좌표 변환 보조용.
**로드뷰 위에 3D 모델은 불가능**(파노라마라 깊이 정보가 없다).

## 디렉터리

`data/raw/` 는 **받은 원본이라 수정하지 않는다.** 나머지 구조는 `ls` 로 보면 된다 —
자동 생성 시드와 ERD 주의사항은 아래 「작업 규칙」·「스키마」에 있다.

## 실행

명령과 자주 밟는 함정(포트 3307, root 비밀번호, `package` 전에 백엔드 끄기, `JWT_SECRET`,
`SET NAMES utf8mb4`)은 **루트 `CLAUDE.md`** 에 있다. 여기엔 **거기 안 들어간 사정과 나머지
함정**을 둔다.

- **포트 3307 인 까닭** — 개발 PC 의 로컬 MySQL 이 3306 을 쓰고 있다. `DB_PORT` 가 빠지면
  `application.yml` 기본값 `localhost:3306` 으로 붙어 `Access denied for user 'root'` 가
  나는데, 실제로 `.env` 가 `.env.example` 보다 뒤처져 이 키가 빠져 있었다
- **테스트로 바꾼 기준값을 되돌릴 때는 시드를 통째로 넣는다.** 관리자 API 로 바꿔 보고
  그대로 두면 DB 와 시드 파일이 어긋난 채 계산에 쓰인다 (실제로 `discount_rate` 근거가
  `stale check` 로 남아 있었다). 볼륨은 안 지워도 된다

  ```bash
  PW=$(grep '^DB_PASSWORD=' .env | cut -d= -f2-)
  docker compose exec -T -e MYSQL_PWD="$PW" db mysql -uroot railfeas < db/seed/S7__benefit_parameter.sql
  ```
- **시드 파일 자체를 고쳤으면 `down -v`** — initdb 는 볼륨이 빈 경우에만 돈다
- **`./mvnw` 가 조용히 아무것도 안 할 수 있다** — 배포본을 받으려다 `wget: Failed to fetch`
  로 끝나는데 `-q` 를 붙이면 그 한 줄도 안 보이고, `target/surefire-reports` 에는 **예전
  결과가 그대로 남아** 통과한 것처럼 읽힌다(실제로 그렇게 잘못 보고했다). 받아 둔 배포본을
  직접 쓰고, 보고서는 **시각까지** 본다
  `$(ls -d ~/.m2/wrapper/dists/apache-maven-3.9.9/*/bin/mvn) -o test`
- **SQL 파일 첫 줄에 `SET NAMES utf8mb4;`** — initdb가 latin1로 읽어 한글이 이중 인코딩된다
  (`복선전철` → `ë³µì„ ì „ì² `). 자동 생성 SQL은 생성기에도 넣을 것
- **`cost_standard`는 TRUNCATE 불가** — `scenario_result`가 FK로 참조. `DELETE`를 쓴다
- **엔티티 타입이 DDL과 어긋나면 기동 실패** — `data_grade CHAR(1)`은 `columnDefinition="char(1)"`
- **소셜 로그인은 키가 있는 공급자만 등록한다**(`OAuth2ClientConfig`, 11-05). 전에는 `social` 프로파일이
  Google·카카오를 함께 등록해 **카카오 키만 넣으면 Google 의 빈 client-id 로 기동이 막혔다.** 카카오는
  시크릿이 없으면 보내지 않고(`NONE`), 범위는 닉네임뿐이다 — 이메일을 요청하면 개인 개발 앱은 KOE205 로 막힌다
- **`JWT_SECRET` 은 기본값이 없다 — 없으면 기동이 막힌다.** `application.yml` 은 공개
  저장소에 올라가므로 거기 적은 키는 누구나 읽어 **토큰을 위조**할 수 있다. 실제로
  47바이트 기본값이 들어 있었다. `.env` 에 32바이트 이상으로 넣는다(HS256, RFC 7518 3.2).
  `JwtTokenProvider` 가 없음·짧음·치환 안 됨(`${...}`)을 가려 무엇을 어디에 넣을지 말해 준다 —
  그러지 않으면 jjwt 가 "key byte array is 104 bits" 라고만 해서 원인을 알 수 없다
  (104비트 = 치환되지 않은 `${JWT_SECRET}` 13글자). **키를 바꾸면 발급된 토큰이 전부 무효**다
- **JDK 23+는 애너테이션 처리가 기본 비활성** — `pom.xml` `annotationProcessorPaths`에 Lombok 명시
  (1.18.38). `mvnw spring-boot:run`은 클래스패스 오류라 `package` 후 `java -jar` (원인 미파악)
- `initdb.d`는 하위 폴더를 안 읽어 compose에서 `01_`~`07_` 접두사로 파일 단위 마운트
- **MapLibre 지도에는 `ResizeObserver` 가 필요하다.** 컨테이너 크기를 못 재면 400×300 으로
  잡아 두고 그대로 둔다 — 지도 일부만 그려지고 **빈 영역을 클릭하면 좌표까지 어긋난다**
  (684×716 컨테이너에 캔버스가 400×300 으로 남아 있었다). 노선 찍기가 첫 동작이라 치명적
- **`/api/*` 의 500 이 백엔드 버그가 아닐 수 있다.** Vite 프록시는 대상에 못 닿으면 `502` 가
  아니라 **`500`** 을 만들어 돌려준다. 그래서 **백엔드 로그에는 에러가 한 줄도 안 남는다** —
  요청이 거기까지 가지도 않았다. 실제로 `POST /api/auth/login` 이 500 을 냈는데 양쪽 로그가
  모두 깨끗했다. 범인은 **고아 프로세스**였다: `.claude/launch.json` 의 `exec npm run dev` 는
  npm 이 vite 를 **자식으로** 낳아서, preview 를 멈추면 npm 만 죽고 **vite(node) 가 살아남아
  5173 을 계속 잡는다**. 백엔드 쪽 `exec java -jar` 는 bash 가 java 로 **대체**되므로 같이
  죽는다 — 그래서 한쪽만 고아가 됐고, 살아 있는 Vite 가 죽은 9090 으로 중계하다 500 을 냈다.
  `exec node node_modules/vite/bin/vite.js` 로 바꿔 **vite 가 직접 뜨게** 했다(멈춰 보고
  5173 이 비는 것까지 확인했다. 바꾸기 전에는 두 번 연속 살아남았다).
  **증상이 500 이면 코드를 읽기 전에 `netstat` 로 9090 이 듣는지부터 본다.**
- **화면은 직접 열어 봐야 한다.** 빌드·API 만으로는 안 나오는 결함이 실제로 여럿 나왔다
  (캔버스 크기, 비교표 강조, 관리자 오류 위치·칸 너비, 패널 폭). 단 **데이터 로딩 전에 찍은
  화면으로 단정하지 말 것** — 3D·관리자 표를 "비었다"고 잘못 보고한 적이 두 번 있다

**시나리오 수정은 `PUT /api/scenarios/{id}`**다. 프론트는 불러온 id를 `editingId`로 들고 있다가
덮어쓴다. 노선을 고치면 계산 결과는 지우되 **`editingId`는 남긴다** — 같이 지우면 저장할 때
같은 제목이 하나 더 생긴다. 별개로 남기려면 "새 시나리오로 저장"을 쓴다.

**스키마는 JPA가 만들지 않는다.** `ddl-auto=validate` 고정, `db/schema/*.sql`이 만든다.
인증은 JWT (`@AuthenticationPrincipal Long userId`). 소셜은 `/oauth2/authorization/{google|kakao}`
→ 성공 시 `OAUTH2_REDIRECT_URI`(`/oauth/callback`)에 **`#token=`** 을 붙여 리다이렉트, 실패는 `#error=`.
- **11-04 까지 소셜 로그인은 백엔드뿐이었다** — 제안서 기능 1 인데 버튼도, 돌아온 토큰을 받는 화면도 없었다.
  붙인 것: `/api/auth/providers`(켜진 공급자 — 화면이 버튼을 고른다, 키가 없으면 빈 목록) ·
  `/api/auth/me`(토큰만 들고 돌아온 화면이 닉네임·권한을 받는다) · 화면의 `/oauth/callback` 처리 ·
  Vite 프록시 `/oauth2`·`/login/oauth2`. **토큰은 `?` 가 아니라 `#` 뒤다** — `?` 면 방문 기록·Referer·
  서버 로그에 남는다. 화면은 읽자마자 `history.replaceState` 로 지운다
- 확인한 것 — 키 없으면 버튼 0개, 가짜 키 둘을 넣으면 버튼 2개와 공급자로의 리다이렉트,
  유효한 토큰으로 콜백에 들어오면 로그인되고 주소에서 토큰이 사라진다, `#error=`·엉터리 토큰은 안내만 뜬다.
  **Google 실제 왕복은 11-05 에 확인했다** — 동의 → 9090 콜백 → `#token=` → `/me` 로 「신선호」(GOOGLE·USER,
  password NULL, provider_uid 21자) 생성, 주소에 토큰 안 남음, 새로고침 유지, 관리자 API 403. 속성 해석(sub·
  email·name)도 맞았다. **함정** — Google 은 계정 로그인 뒤 **동의 화면(「계속」)** 이 한 번 더 있다. 그 전에는
  앱에 아무것도 오지 않는다(백엔드 로그·DB 모두 비어 있었다)
- **카카오 실제 왕복도 11-05 에 확인했다** — KAKAO·USER·password NULL, 이메일은 `kakao_{id}@social.local`
  (닉네임만 요청하므로). 콘솔에서 막힌 순서 — KOE004(카카오 로그인 꺼짐) → KOE205(닉네임 동의 없음) →
  KOE006(Redirect URI 미등록) → **토큰 교환 401**(Client Secret 이 켜져 있는데 안 보냄). 마지막은 로그인·동의가
  다 된 **뒤에** 나서 화면엔 「소셜 로그인에 실패했습니다」 뿐이었다 — 실패 처리기가 로그를 남기게 한 뒤에야
  `invalid_token_response: 401` 이 보였다. **가짜 코드로 토큰 주소에 직접 물어 가린다** — KOE010(앱 인증 실패)
  이면 시크릿 문제, KOE320(코드 없음)이면 앱 인증은 통과다
- **재시작할 때 9090 이 덜 비면 백엔드가 9091 로 뜬다**(미리보기 도구가 포트를 옮긴다). 소셜 로그인의 돌아올
  주소와 Vite 프록시가 9090 이라 그대로 두면 로그인이 실패한다 — 9090 이 빌 때까지 기다려 다시 띄운다
- **같은 이메일로 가입한 계정이 있으면 소셜 계정을 만들지 않는다**(`OAuth2UserService.upsert`, 11-05).
  이메일로 가입한 사람이 같은 Gmail 로 Google 로그인을 누르면 저장이 email UNIQUE 에 걸려 **500** 이었다 —
  그 예외는 인증 실패가 아니라 실패 처리기를 안 타고 백엔드 오류 화면이 떴다. 이제 `email_in_use` 인증
  실패로 화면에 「이메일과 비밀번호로 로그인해 주세요」 를 보낸다. **자동 병합은 하지 않는다** — 공급자가
  확인하지 않은 이메일이면 남의 계정에 들어가는 길이다. 실패 처리기는 이 이유만 그대로 전하고 나머지는 일반 문구다
- **공급자가 주는 값은 칸에 맞춘다** — 이메일 가입의 검증(닉네임 50자)을 거치지 않아 긴 Google 이름이면 같은
  500 이다. 닉네임은 50 **글자**(code point)로 자르고(char 로 자르면 이모지가 반으로 갈린다), 150자를 넘는
  이메일은 자르지 않고 `google_{번호}@social.local` 로 대신한다(자르면 남의 주소가 될 수 있다)
- **토큰은 「누구인지」 만 싣는다 — 권한은 매 요청 DB 에서 읽는다**(`JwtAuthenticationFilter`).
  전에는 토큰의 `role` 을 믿어, 관리자를 일반 사용자로 내려도 옛 토큰으로 **720분 동안 관리자 API 가
  열려 있었고**(점검에서 200), 지운 계정의 토큰도 로그인된 것으로 통했다. 지금은 403 · 401 이다
  (2026-11-04 서버 권한 점검 — 남의 시나리오 조회·수정·계산·삭제는 전부터 404, 일반 사용자의
  관리자 API 는 403 이었다). 화면의 「기준값 관리」 버튼은 로그인 응답의 role 을 따르므로 강등된
  사람에게는 다시 로그인할 때까지 보이지만, 눌러도 서버가 403 으로 막는다
- **그린 노선 전체 길이는 1,000km 까지다**(`ScenarioService.MAX_ROUTE_KM`, 판단값). 점 개수(50)·좌표
  범위는 막혀 있었지만 길이는 아니어서, 점 50개로 전국을 지그재그로 그린 18,528km 가 저장되고 계산
  한 번에 **137.8초 · 응답 14MB · 정차역 11만 7천 개**가 DB 에 들어갔다(11-04 부하 점검). 근거 —
  국내 최장 철도 경부선 441.7km 를 꺾어 그려도 두 배를 넘기 어렵고, 가장 긴 실제 시나리오는 349.6km.
  계산 시간은 길이에 거의 비례한다(1,000km 면 7초 안팎). 저장·수정에서 막고, 상한 전에 저장된 노선을
  위해 계산에서도 막는다. 수정이 거절되면 옛 노선이 그대로 남는다(지우기 전에 잰다)
- **계산은 트랜잭션 밖이다**(11-22 코드 점검, `ScenarioService.calculate`). 계산이 1~7초(서울~부산 3초)인데 메서드 전체가 한 트랜잭션이라 그동안 DB 연결 하나가 묶였고, `open-in-view: false` 라
  요청이 끝날 때까지가 아니라 **계산하는 동안** 묶였다 — 연결 풀(기본 10)을 계산 열 개가 차지하면 로그인·목록까지 막힌다. 그래서 읽기(읽기 전용) → 계산(트랜잭션 밖) → 쓰기 셋으로
  나눴다(`TransactionTemplate`, 나머지 메서드는 `@Transactional` 그대로). 계산기는 시나리오에서 점·길이만 읽고 점은 엔티티 그래프로 함께 읽혀 분리된 엔티티로도 안전하다.
  **계산하는 동안 노선이 바뀌면 409**(「계산하는 동안 노선이 바뀌었습니다」) — 낡은 결과를 새 노선에 붙이지 않는다(점 좌표·길이 지문 `routeKey` 로 견준다). 이전엔 한 트랜잭션이라
  같은 경주가 좁게 있었고, 이제는 계산 시간만큼 넓어서 막았다. **실측**(실제 서버, 서울~부산 12개 동시 계산): 계산하는 동안 목록 응답 **18~34ms**(기준선 약 20ms), 재계산(옛 결과 삭제 후
  삽입)도 200·B/C 같음. **측정 함정** — 브라우저는 한 주소에 연결을 6개까지만 열어 계산 12개를 같은 주소로 보내면 목록 요청이 7초 대기열에 선다(서버가 막은 게 아니다). 직접 주소(`:9090`)로
  보내야 서버를 잰다. 고치기 전 코드로는 비교 측정을 안 했다 — 이득은 트랜잭션이 활성이 아님을 보는 테스트(`ScenarioCalculateTransactionTest`)가 직접 고정한다
- **같은 시나리오를 바꾸는 쓰기는 줄을 선다 — 계산·수정·삭제**(11-22 동시 시험, `ScenarioRepository.lockOwned`). 위 「노선이 바뀌면 409」 만 보고 다른 경주는 없다고 봤는데, 실제 MySQL 로 동시에 보내 보니
  두 가지가 **500** 이었다(빈 500 화면 — 두 탭·더블클릭으로 닿는다. 데이터는 안 깨졌다: 결과 11행·중복 0). ① **같은 시나리오 동시 계산**: 쓰기 트랜잭션 둘이 서로 옛 결과 삭제·새 결과 삽입을 기다려

  `OptimisticLockException` — 4개 중 3개(3판 × 3 = 9/12). **세 쓰기 트랜잭션의 첫 문장으로 내 시나리오 행을 `SELECT … FOR UPDATE`** 로 잠가 나머지가 순서를 기다리게 했다. 소유자 조건(`id` + `user.id`)까지
  걸어 **남의 시나리오는 잠그지도 않고 바로 404** 다. **순서가 핵심이다** — 잠근 **뒤에** 읽어야 앞 요청이 커밋한 결과를 본다(REPEATABLE READ 스냅샷은 첫 일반 읽기에서 잡힌다).

  계산은 쓰기 트랜잭션 안, 수정·삭제는 `@Transactional`, 남의 시나리오는 읽지도 않음만 고정한다 — **교착·경주 자체는 실제 MySQL 에서만 나므로 증거는 동시 시험이다**(`tools/verify/concurrency.py`: 같은 시나리오 계산 8개 +

  못한다. 반경을 `nextDown(d)`·`d`·`nextUp(d)` 로 잡는 시험이 그 돌연변이를 잡는다(그 영역이 실제로 있다는 증거). **「통과만 하는 테스트는 못이 아니다」 — 가드를 꺼 보고서야 알았다.**

  (길이 0 구간 포함)·꼭짓점 누적 거리의 ulp 앞뒤·0·끝·음수·초과·꼭짓점 둘/길이 0 경로에서 **정확히 같음**을 본다. **돌연변이 점검:** `<=` → `<` 는 테스트가 못 잡는데 **정상이다**(동치 돌연변이 — 같은 누적 거리에서 앞 구간 비율 1 과 다음 구간 비율 0 이
  같은 꼭짓점을 돌려줘 출력이 같다). 탐색 상한을 한 칸 줄이는 돌연변이(`hi = last - 1`)는 두 시험이 잡는다. **더 줄일 수 있지만 안 했다:** `Haversine.within` 의 `sin`·`cos`(약 23%) — 셀마다 `cos(lat)` 을 미리 계산해 두면 되는데
  `Cell` 레코드를 건드려야 하고 이득이 작다(최악 입력 1.7초, 일반 장거리 1초 미만). 남은 시간은 그 삼각함수·`StationPlanner` 자체·`HashMap` 조회·도로 로드다.
  **재는 법(다음에):** JFR 은 서버에 옵션만 주면 된다 — `JAVA_TOOL_OPTIONS=-XX:FlightRecorderOptions=repository=<ASCII 경로> -XX:StartFlightRecording=settings=profile,filename=<ASCII 경로>` 후 `jcmd <pid> JFR.dump name=1 filename=…` 로 덤프,
  `jfr print --events jdk.ExecutionSample --stack-depth 40` 로 집계. **경로 함정 셋(겪은 것):** ① 저장소 경로의 **공백**("Map-based Urban Rail …")은 `JAVA_TOOL_OPTIONS` 에서 잘려 JVM 이 `Unrecognized option` 으로 못 뜬다
  ② 사용자 폴더의 **한글**(`C:\Users\신선호`)은 JFR 경로로 넘어가며 깨져 파일을 못 쓴다 ③ **JFR 저장소(`repository`) 기본값이 한글 임시 폴더라** 덤프가 0바이트다 — 저장소 폴더도 ASCII 경로(`C:/Users/Public/…`)로 지정할 것
- **오늘 변경 전체를 새 눈으로 코드 리뷰했다 — 두 결함이 나왔고 고쳤다**(11-22 `/code-review`, 범위 `4030e5c..HEAD`). 내가 혼자 쓴 변경은 같은 맹점을 공유해 단위 테스트·정답지·부하 시험이 놓친 것이 있었다. ① **`pointAt` 이분 탐색이 꼭짓점 1개짜리 경로에서
  `IndexOutOfBoundsException`** — 옛 선형 탐색은 구간이 없으면 마지막 꼭짓점을 돌려줬다. 동치 시험(무작위·경계·꼭짓점 둘)에 **꼭짓점 하나**를 안 넣어서 못 잡았다 — 재현 테스트를 먼저 써 실패를 보고(`singleVertexRoute`) 가드(`last < 1`)를 넣었다.
  ② **짧은 노선에서 지도가 비고 패널은 추천을 말한다** — 역간격 하한을 넣을 때 서버는 「범위 안이 하나도 없으면 범위를 무시」 하는데 화면의 `shown` 은 필터만 해 0.5km 노선(전부 범위 밖)에서 `undefined` 였다. 「지도·굵은 행·서버 추천이 같은 규칙」 이라는 규칙을 내가 어겼다.
  `defaultRow` 로 한 곳에 모으고 화면에서 확인했다(위 프론트 규칙). **교훈:** 규칙을 서버에 넣으면 같은 규칙이 화면에 몇 곳 있는지 **grep 으로 세어 본 뒤** 끝낼 것(이번엔 `overLength` 를 쓰는 곳만 보고 `shown` 의 필터를 놓쳤다).
  리뷰가 참고로 남긴 둘은 고치지 않았다 — `tools/verify/harness.py` 가 윈도우 전용(README 에 적혀 있다), `ScenarioResult.stations` 가 cascade 없는 점(주석이 경고한다)
- 우회(`/api/route/detour`)·인구(`/api/reference/population`)는 전부터 버틴다 — 점 50개로 호수 41곳을
  지나도 0.6~1.6초, 인구는 전국 범위도 2만 칸(0.9MB)에서 잘려 0.1초다

원본 3종은 포맷·단위·구조가 모두 다르다. `etl.py`가 블록 헤더를 감지해 파서를 분기시킨다.

| 출처 | 포맷 | 연장 | 금액 | 비고 |
|---|---|---|---|---|
| 도시철도노선정보 | xlsx | **미터** | 없음 | 역수는 `정거장구성` 문자열 split |
| 철도건설현황 | csv (**cp949**) | 없음 | **백만원** | 연장 없어 대부분 D등급 |
| 데이터.txt | txt (탭) | km | 억원 | 사업계획·도시철도/광역철도 운영현황 3종 혼재 |

**파싱 시 처리** 합계·소계 행 제외 / 병합셀로 빈 구분 열은 직전 지역명 이어받기(`서울 3호선`) /
줄바꿈 조각 행 폐기 / 물결·중점 변형 통일(`~∼〜～`, `․·ㆍ`) / 어절 중복 제거(`경부고속철도철도`) /
노선명 접미사 분리(`신안산선 복선전철`) / 두 자리 연도(`'74`→1974, `'24`→2024)

**조용히 그럴듯한 값을 내던 파싱 함정 셋** (고쳤다, 자세한 것은 `docs/research-log.md`)

- **`정거장구성` 구분자가 쉼표만이 아니다** — 47개 중 둘이 `+` 를 쓴다. 쉼표로만 쪼개
  신분당선 16역이 **1역**으로 읽혀 역간격이 33.5km 였다. 이상치 목록에 "정거장구성
  미기재로 추정" 으로 적혀 있었는데 미기재가 아니었다 — **진단이 틀린 이상치는 제외가
  아니라 파싱을 고쳐야 한다.** `·` 로는 쪼개지 말 것(`전대·에버랜드`)
- **두 자리 날짜를 `pd.to_datetime` 에 맡기면 뒤집어 읽는다** — `22.05.28` 을 DD.MM.YY 로
  보고 2028년을 준다. `parse_opened_year` 가 `parse_short_year` 로 보낸다
- **역이 하나면 역간격이 없다** — 가덕도신공항(16.5km/1역)이 복선전철 중앙값을
  4.30 → 4.97 로 밀어 올렸다. `spacing_stats` 가 `station_count >= 2` 를 요구한다

**등급 체계 — 381건 (A 42 / B 28 / C 69 / D 242)**
A = 연장+역수+금액(비용 회귀 + 역간격) / B = 연장+금액(회귀만) / C = 연장+역수(역간격만) / D = 보류

- 파생값(`cost_per_km`, `avg_spacing_km`, `data_grade`)은 DB 생성 컬럼 — 직접 INSERT 금지
- 이상치는 지우지 않고 `is_outlier=TRUE`로 제외만 (사유를 보고서에 써야 한다)
- 추정치는 `cost_status='ESTIMATED'` — 회귀 학습엔 `DISCLOSED`만 (순환 오류 방지)
- 원문 표기는 `raw_type_text`에 보존
- 출처 간 동일 사업은 등급 낮은 행 삭제 — `etl.py`의 `SAME_PROJECT`에 명시하고 남는 행
  `note`에 지운 행 원문을 남긴다. 매칭이 어긋나거나 등급이 역전되면 ETL이 멈춘다
- 역수 보강은 `rail_station_seed.csv` (사업계획엔 역수 열이 없어 광역철도가 전부 B등급이었다)

## 비용 모델 (`cost_model.py` → S5)

① log-log 회귀로 규모의 경제를 잡고 ② 연장 5~40km × 역수 0.6~1.4배 격자에서 직선 근사해
`고정비 + 연장×단가 + 역수×역당단가`로 바꾼다. 연장만 훑으면 역수가 연장에 묶여 분리되지 않는다.

`log(사업비) = 6.910 + 0.663·log(연장) + 0.515·지하비율 + 0.257·log(역수) + 수단더미`
(A등급 38건, R² 0.887, 교차검증 1.25배, 기준 수단 = 복선전철. 지하비율 17건 OSM 실측)

**수단×구조별 단가는 `db/seed/S5__cost_standard.sql` 이 원본이다** (2025년 환산 억원,
`source` 에 표본 수). A등급 2건 미만인 수단만 전체 표본 모델 + 구조·역수 보정을 쓴다.

- **역수는 log로 넣어야 분리된다.** 선형이면 연장과 겹쳐 음수(-223±225)로 튄다.
  표본의 역수/표준역수 비가 0.21~1.91로 퍼져 있어 log로는 0.257±0.087로 유의하다
- 복선전철 역당 1,176억은 표본이 GTX 대심도 위주여서다 (역간격도 4.98km로 넓다)
- **기준연도가 2025 를 넘는 행이 A등급 38건 중 19건이다 — 물가 환산이 아예 안 된다.**
  `price_index.csv` 가 1990~2025 뿐이라 `base_year` 가 2029·2032 같은 미래면 그냥 통과한다
  (`base_year_status='ASSUMED'` — 종료연도로 대신한 값이다). **"효과는 미미"를 검정했고
  참이었다**: 미래/과거 두 집단의 잔차 차이가 0.97배(t=−0.36, 검출 한계 1.17배)다.
  다만 미래 집단 **안에서는 연 +4.3% 기울기**(r=0.34, t≈1.5, 10-26 재계산)가 보인다 — 경상가격이라면
  나올 모양이지만 유의하지 않다. 표본이 늘면 다시 볼 것 (`test_cost_model.py` 가 감시한다)
- **`underground_ratio` 40건 중 17건을 OSM 실측으로 바꿨다(2026-10-26, `etl/osm_tunnel.py`).**
  전부 추정치(공식 미공표)였고, **0·1 은 대개 맞았지만 중간값이 틀렸다** — 용인경전철 0.20→0.00
  (선로 99.6% 가 고가), 부산김해 0.10→0.00, 인천2호선 0.95→0.82, 하양연장 0.30→0.15, 진접선
  1.00→0.86. 계수가 **0.575→0.515**(±0.163→±0.152), 지하/고가 배수가 **1.78→1.67배** 로
  줄었다 — 추정치가 지상 구간의 비용까지 「지하라서」 로 설명하고 있었다. 교차검증은 1.25배
  그대로다. 나머지 23건은 공사 중·계획이라 OSM 에 운행 노선이 없어 **못 잰다**(「지상이다」
  가 아니다). 재는 법·거부 규칙은 아래 「지하 비율 실측」
- **남은 추정치가 틀려도 생각만큼 위험하지 않다.** 추정이 틀리면 **계수가 그만큼 흡수해**
  예측이 덜 흔들린다. 표본에 표준편차 0.15 짜리 잡음을 넣고 200번 다시 적합한 결과, 지하
  20km 중전철 비용이 **98.4~106.5%** (5~95%) 범위에 머물렀다. 전 표본을 한쪽으로 0.2 씩
  밀어도 −1.9~+13.5% 다. 다만 **표본 38건 중 19건이 이미 1.00 이라** 위로 미는 교란은
  잘려서 표현되지 않는다 — 위쪽 수치는 과소평가로 읽을 것.
  변수를 아예 빼면 교차검증이 1.25 → 1.28배, R² 0.887 → 0.845 로 나빠진다.
  **쓸 값어치는 있으나 없어도 치명적이지 않은 변수**다 (`etl/cost_model.py` 로 재현 가능)
- 트램 2건·BRT 저급형 3건은 표본 부족 — SQL `source`에 표시

**정확도** 연장+수단 1.45배 → +지하비율 1.29배 → +역수 **1.25배**(현재).
실제 38개 노선 대비 평균 **19% 오차**(|예측÷실제 − 1| 의 평균, 중앙값 비율 0.98 — 10-26 재계산).
큰 오차는 광주 2호선 1단계(저심도) 1.85배, 대구 1호선 하양연장(기존선 병행) 1.64배,
용산~상봉 0.61배 — 공법이 변수에 없어서다. 하양연장은 지하비율을 실측(0.15)으로 바꾼 뒤에도
1.64배라 지하비율 탓이 아니다. **결과는 단일 값이 아니라 범위로 보여주고 이 오차를 보고서에 명시한다.**

### 지하 비율 실측 (`etl/osm_tunnel.py`, 2026-10-26)

**공식 미공표라 전부 추정치이던 지하비율을 OSM 선로의 터널 표시로 쟀다.** OSM 의 대중교통
노선 관계(PTv2)는 선로 조각과 정차역을 **운행 순서대로** 담는다 — 조각을 이어 한 줄로 만들고,
구간 양 끝 역을 그 줄에 찍어 그 사이에서 `tunnel`(또는 `location=underground`)이 붙은 길이의
비율을 낸다. 어느 사업 구간이 어느 관계의 어느 역~역인지는 `data/seed/tunnel_sections.csv` 에
사람이 적는다(숫자 없이 사실만). `etl.py` 가 `underground_measured.csv` 를 읽어 추정치를 바꾸고
비고를 「지하비율 OSM 실측」 으로 고친다.

- **검증** — 「전부 지하」 로 알려진 우이신설 1.00·김포 0.99·신림 1.00, 「전부 고가」 대구3호선
  0.00 이 맞았다. 잰 연장은 대부분 사업 연장의 5% 안이다(우이 11.16/11.4, 용인 18.01/18.14). 가장 크게 다른 것이
  인천1호선 귤현~동막 −11%(21.88/24.60)·다대연장 −7% 다
- **거부 규칙 셋** — ① 잰 길이가 사업 연장과 **15% 넘게** 다르면(역을 잘못 짚은 것) ② 관계가
  **0.5km 넘게 끊겨** 있으면(직선으로 이으면 없는 선로를 센다) ③ 역 이름이 관계에 없거나 둘
  이상이면. 거부된 구간은 추정치로 남고 실행 끝에 크게 찍힌다. 각 가드를 꺼 보고 그 테스트만
  깨지는지 확인했다(`test_osm_tunnel.py` 16개)
- **거부 1건** — 인천1호선 계양역 사업 1.3km 를 1.10km 로 쟀다(−15.4%). 기준을 결과에 맞춰
  늘리지 않았다. **진접선**은 구간명이 「별내별가람~진접」 인데 사업 연장 14.9km 는 당고개(현
  불암산)부터라 출발역을 불암산으로 적었다(별내별가람부터는 10.1km — 이것도 거부 규칙이 잡았다)
- **바뀐 값** — 용인 0.20→**0.00**(OSM 이 선로 99.6% 를 `bridge=yes` 로 적었다. 나무위키도 지하
  「없음」 — 운영사 공식 자료는 못 찾았다), 부산김해 0.10→0.00, 인천2호선 0.95→**0.82**,
  하양연장 0.30→0.15, 진접선 1.00→0.86, 인천1호선 0.90→0.99. **0·1 은 대개 맞고 중간값이 틀렸다**
- **못 재는 23건** — 동북선·신안산선·GTX 삼성 구간처럼 공사 중·계획이라 운행 노선 관계가 없다.
  양산선은 OSM 에 아직 공사 중(`railway=construction`)으로 그려져 있고, 7호선 인천연장은 시작점이
  역이 아니라 행정 경계라 뺐다. **「못 잰다」 이지 「지상이다」 가 아니다** — 개통해 OSM 에 관계가
  생기면 표에 한 줄 더한다
- **공사 중 선형은 참고값으로만 붙인다(2026-11-01)** — 23건 중 14건이 OSM 에 이름 붙은 공사 선로로
  그려져 있다. 계획도를 보고 그렸을 수 있고 「전부 터널」 로 한꺼번에 표시했을 수도 있어 **운행 선로
  실측과 같은 등급이 아니다** — 지하비율 값은 그대로 두고 비고에 「OSM 공사 선형 기준 지하 X.XX
  (참고 — 회귀에 안 씀)」 만 붙인다(`apply_construction_reference`, 사용자 결정).
  - 재는 법 — 노선 관계가 없어 **선로 이름 + 범위 상자**로 모으고 역으로 자르지 않는다
    (`data/seed/tunnel_construction.csv`). 복선이 두 줄이면 길이가 두 배지만 **비율은 그대로**다.
    선로 길이 합이 사업 연장의 **0.5~2.5배** 밖이면 거부 — 용산~상봉(GTX-B)이 5.8배로 걸렸다
    (같은 이름 선로가 상자에 116km 잡혔다). 운행 중인 같은 이름 선로를 빼야 하는 신분당선·경강선·
    7호선은 공사 선로만 센다
  - **추정과 크게 다른 3건** — 도봉산~옥정 0.30→**0.94**, 7호선 청라연장 0.70→**1.00**, 양산선
    0.19→**0.29**. 실측 때처럼 **틀린 쪽은 또 중간값**이다. 나머지(동북선·신안산선·GTX-A·C·
    월곶판교·인덕원동탄·대장홍대)는 1.00 근처로 추정과 같고, 트램(대전 2호선 0.05·위례선 0.02)도 0 근처다
  - **넣었다면** — A등급 표본에서 6행이 바뀌어 계수 0.515→0.549(±0.153), 지하/고가 1.67→1.73배,
    교차검증 1.25배 그대로다. 결정을 바꿀 만큼 크지 않아 참고로 둔 것이 손해가 아니다
  - 같은 이름의 공사 선로가 **운행 구간과 섞인** 노선이 있다 — GTX-C 는 상자 안 선로의 14% 만 공사
    중이다(기존 선로를 같은 이름으로 적은 것으로 보인다). 공사 중 몫(`construction_share`)을 함께 남긴다
- **Overpass 본진이 502 를 자주 낸다** — 관계마다 `data/cache/osm/tunnel/` 에 캐시한다

**공법을 변수로 만들 수는 없다 — 표본이 없다** (다음 할 일 ⑤ 의 답). 저심도 1건 ·
기존선 병행 0건 · 지상 위주 2건이다. 급행 비용 더미도 n=4 라 과적합으로 뺐는데
n=1~2 는 말할 것도 없다. `python cost_model.py --candidates` 가 후보 변수들을 한꺼번에
가려 준다 — **넣고 싶은 변수가 생기면 넣기 전에 여기 먼저 넣어 볼 것.**

**교량·하저터널 할증은 막히는 이유가 다르다 — 표본이 적은 게 아니라 변수를 만들 수가 없다**
(2026-10-17 확인). 위 후보들은 모두 **우리가 가진 열에서 뽑아낸 것**이다 — 저심도·차량기지·
민자는 `note` 문구, 고무차륜은 `mode_type`, 계획 사업비는 `cost_status`, 수도권은
`region_class`, 나머지는 역간격·기준연도다. 그런데 `reference_line` 에는 **좌표도 선형도
없다**(열은 이름·구간명·연장·역수·사업비·지하비율뿐이고 `section_name` 은 `암사~별내` 처럼
양 끝 이름일 뿐이다). "이 노선이 하천을 건너는가" 를 판정하려면 **노선이 지나는 길**을 알아야
하는데 그 자료가 없다.

- 교량 단서를 본문에서 찾아봤더니 `대교` 1회 · `횡단` 2회뿐이고 **셋 다 무관**했다
  (BRT 노선 메모, 입체교차 단독사업 둘)
- 양 끝만 이어 직선으로 강을 건너는지 보는 것은 **174km 짜리 남부내륙선에 쓸 수 없다**
- 노선 이름만 보고 "여기는 한강을 건넌다" 고 손으로 붙이는 것은 **자료가 아니라 기억**이다.
  이 프로젝트가 "열어 보지 않고 적은 기록이 길을 잘못 안내했다" 고 적어 둔 그 함정이다
- **그래서 `cost_standard` 는 수단 × 구조뿐이고, 한강을 건너는 지상 1km 와 평지 지상 1km 가
  같은 값이다.** "다리 vs 우회" 중 무엇이 싼지 이 모델은 답하지 못한다 — 보고서에 그렇게 쓸 것.
  풀려면 **사업별 선형 좌표**가 먼저 있어야 한다

| 후보 | n | 비율 | t | 검출 한계 |
|---|---|---|---|---|
| 저심도 / 지상 위주 / 계획 사업비 | 1·2·2 | — | — | **표본 부족, 잴 수 없다** |
| 고무차륜·모노레일 | 3 | 1.08 | +0.60 | 1.31배 |
| 민자 사업 | 3 | 0.95 | −0.32 | 1.37배 |
| 차량기지 포함 | 6 | 1.12 | +1.68 | 1.14배 |
| 역간격 ≥ 4.5km | 7 | 1.04 | +0.31 | 1.29배 |
| 기준연도가 미래 | 19 | 0.97 | −0.36 | 1.17배 |
| 수도권 | 24 | 1.13 | +1.48 | 1.18배 |

**`MIN_SPLIT_N = 3` 이 작은 표본을 막는다 — 막기 전에 실제로 속았다.** `계획 사업비` 가
붙은 두 노선(7호선 청라연장·송파하남선)의 잔차가 **소수점 5자리까지 같아서**(둘 다
1.3243배, 사업비는 15,828 / 18,356 으로 서로 다른데 비율이 우연히 겹쳤다) 분산이 정확히
0 이 되고 **t 가 7.75** 로 튀었다. 두 값이 log 0.4 만 벌어져도 t 는 1.46 이다 —
"유의함"의 전부가 그 우연이었다. **작은 n 에서는 t 가 아니라 검출 한계를 볼 것.**

**물가 환산** World Bank 한국 GDP 디플레이터(2020=100, 1990~2025). `price_index.csv`가 단일
출처이고 ETL이 S4와 `total_cost_2025`를 만든다. 기준연도는 명시값 → 종료연도 → 개통연도 →
착공연도 순으로 대체하고 `base_year_status='ASSUMED'`로 구분(대부분 ASSUMED라 효과는 미미).
건설공사비지수가 더 적합하나 미적용.

## 수요 모델 (`etl/demand_model.py` → S6)

`log(일이용객) = -2.318 + 0.565·log(인구) + 0.584·log(종사자) - 0.410·경전철`
(운영 노선 42개 — 서울 자료 26 + 운영기관·KRIC 자료 16(인천 1·2·의정부·에버라인·김포골드·신분당선, 대전·부산 1~4·부산김해·대구 1~3·광주), R² 0.890, **교차검증 1.32배**. 인구·종사자는 그 노선의 역 둘레 1km 를 **겹침 없이** 합친 값이다.
경전철 항은 0/1 변수라 경전철 행에만 쓴다.)

**11-08 에 경전철을 따로 뒀다**(research-log 「수단에 따라 수요가 다른가」, 사용자 결정 B). 경전철 두 노선(우이신설 1.77배·신림 2.25배)과
표본 밖 **부산 4호선**(공식 역별 승하차, 2025)도 같은 도시 중전철(1~3호선 0.65~0.93배)보다 높은 1.40배라 약 1.8배 과대다. 더미 계수 −0.777±0.303(×0.46) — 표본을 넓힌 뒤 −0.638±0.202(×0.53, 아래).
(처음엔 에버라인·의정부·김포골드의 **보도된 「이용객」** 과 견줘 「다섯 노선이 모두 2배」 라 적었다 — 모델은 승하차 합이고 보도는 대개 승차라
**단위가 두 배 다를 수 있었다.** 기사에 정의가 없어 그 비교는 버렸다.)
더미 없이 경전철 두 노선이 다른 계수를 끌어당기고 있어서, 넣으니 나머지 수단의 이용객도 약 4% 올랐다(서울시청~잠실 28.7만 → 30.0만).
**11-08 에 표본을 수도권 밖으로 넓혔다**(`regional_ridership.py`, research-log 「수도권 밖으로 표본을 넓힌다」). 대전교통공사·부산교통공사·대구교통공사가
공공데이터포털에 올린 역별 승차·하차(자동개집표기)가 서울 자료와 단위가 같다. 대전 1·부산 1~4·대구 1~3 = 8개 노선을 더해 26 → 34개, 경전철은 2 → 4개
(부산 4호선·대구 3호선). 「수도권 밖」 0/1 변수는 +0.146±0.155 로 표준오차보다 작아 지역을 따로 두지 않았다. 계수는 거의 그대로이고(인구 0.49→0.53,
종사자 0.64→0.62) 경전철 배수가 ×0.46 → ×0.53, 교차검증 1.39 → 1.34배. 광주 1호선은 처음엔 발매 통계만 찾아 빠졌다가 11-09 에
「역일시간대별 승하차량」(15060048)을 찾아 더했다(35개) — 모델이 1.46배 과대로 보는 노선이다(단일 노선·자가용 의존). 경전철 ×0.54.
**같은 날 수도권의 다른 운영기관도 더했다**(39개) — 인천교통공사(1·2호선)·의정부시(경전철)·용인시(에버라인). 서울 열린데이터광장에 없던
노선이라 역 좌표는 `station_master.csv` 에서 가져온다(`with_master_coords`). 경전철이 4 → 7개가 되어 배수가 ×0.63(±0.159)으로 덜 깎인다. 이어 KRIC 표로 김포골드라인·신분당선(강남~광교)을 더해 41개, 경전철 8개 ×0.65(±0.151), 부산김해경전철·신분당선 신사~신논현(새서울철도)을 더해 42개, 경전철 9개 ×0.66(±0.144)
**용인 파일의 2025 하차는 15개 역 모두 2024 하차와 같아(베낀 오류) 2024 를 쓴다** — 파서가 그런 해를 건너뛴다.
의정부(승차 4.4만)·에버라인(3.7만)은 11-08 에 쓰다 버린 보도값(4.1만·3.47만)과 맞는다 — 그 보도는 **승차** 기준이었다
**트램은 보정하지 않았다** — 국내 운영 노선이 없다(위례선은 2027 로 밀렸다). 경전철 배수를 넓히면 근거 없는 추정값이 된다.
**BRT 는 자료가 있었다** — 세종 B0·B1·B2 노선별 연간 이용객(행복청 2024)과 견주면 4.8~8.5배, 축 전체(B1+B2+B4)로는 2.84배 과대다.
**BRT 행에 축 배수 0.3545 을 곱한다**(`demand_brt_factor`, 11-08 사용자 결정). `demand_model.py` 가 같은 계수로 축 예측을 내 계산하므로
재학습하면 따라간다 — 세종 BRT 선형 캐시(`data/cache/brt`, `sejong_brt_speed.py`)가 없으면 BRT 배수 없이 S6 를 쓴다.
화면은 패널의 이용객 줄에 「승하차 합이라 편익은 이용자 수로 · 경전철 0.66배 · BRT 0.35배 · 트램은 수요 자료 없음」 을 적는다. 계수가 DB 에 없으면(옛 시드) 배수 1 이다.

**11-07 에 역 단위에서 노선 단위로 바꿨다.** 전에는 514개 역으로 학습하고(R² 0.552, 1.75배) 그 식에 **찍은 점 둘레** 인구를 넣었다 — 선의 1/2~1/8 만
잡히고 경유점을 찍을수록 수요가 늘었다(강남~잠실 추정 7.9만, 2호선 7개 역 실측 합 66.4만). 역별로 돌려 더하면 탄력성이 0.43 이라 같은 인구를 쪼갤수록
합이 커져 서울시청~잠실 BRT 가 B/C 23 이 됐고, 겹침을 없애도 18 이었다(research-log 「노선 인구는 꼭짓점 둘레뿐이다」). 노선 단위는 탄력성 합이 1.16 이라
역 수에 안 흔들리고 수요가 다시 모든 수단에 같다(11-08 부터 경전철만 따로). 강남~잠실은 29.9만이 됐다(경전철 보정 뒤 31.0만). **변수** — 인구만 R² 0.710, 1.60배 / +종사자 0.834, 1.44배 /
+도심거리 0.839, 1.47배(계수가 표준오차보다 작아 뺐다 — 지방·장거리를 크게 깎던 항이기도 하다) / 연장은 도움이 안 됐다. 아래 함정은 원자료를 받을 때의 것이다.

입력은 `seoul_ridership.py`(승하차 621역·좌표 784)와 `sgis_population.py`(집계구 52,584개 인구 +
행정동 종사자, 응답은 `data/cache/sgis` 캐싱). 첨두율은 `seoul_peak.py`(월 단위 613역)와
`seoul_weekday_peak.py`(일별로 평일 분리), 단면 환산계수는 `seoul_congestion.py`(혼잡도 1,671행).

**API 함정**
- **시간대별 API(`CardSubwayTime`)는 월 합계만 준다.** 비중 계산엔 지장 없다
- **같은 역이 두 번 오는 달이 있다** — 2026-07 은 621역이 두 번씩 실려 1242건으로 왔다(값은 동일).
  그대로 더하면 그 달만 두 배 가중되므로 중복을 지운다. 값이 다른 중복이면 멈춘다
- 이용객이 거의 없는 12개 행(7호선 까치산 1명 등 노선 오배정)은 자료 오류로 제외
- **일별 시간대별은 `subwSttn`** — 날짜가 있어 평일/주말을 가른다. 2024년(1~199,423행)과
  2023년이 각각 날짜 오름차순으로 붙어 있고 **날짜로 거를 수 없다** — 이분 탐색으로 원하는
  달의 시작 위치를 찾는다. **공휴일 없는 달을 골라야 한다**(기본 2024-11)
- **혼잡도는 `subwConfusion`** (같은 키). 평일/토/일 · 상하선 · 30분 단위. **1~8호선만** 있어
  9호선·경전철·광역철도는 없다
- 1량 정원 160명은 혼잡도 100% 기준. 좌석 54석 → 54/160 = 33.75% 가 데이터셋 정의
  ("좌석만 차면 34%")와 맞는 것으로 교차검증했다
- `train_operation.csv` 의 편성당칸수는 `보유칸수 ÷ 편성수` 와 맞는지 ETL 이 검사한다
  (베껴 적다 틀리는 것을 막는다). **퇴근 시격 열이 없어** 출근 시격을 대신 쓴다
- **수집 범위는 역 위치가 정한다.** `station_ridership.csv`(수도권)에 `regional_station.csv`
  (지방)를 더해 집계구 52,584 → **70,840**개로 넓혔다. 이게 없으면 지방 노선은
  "인구 자료 없음"으로 수요·B/C 가 안 나오고 정차역 이름도 번호로 떨어진다.
  **11-07 에 전국으로 넓혔다**(`all_sgg`, 시군구 111 → 252곳, 집계구 **104,630**개, 동별 종사자 3,554곳, 캐시 679MB, 수집 약 15분) — 수요가 선 전체를
  세면서 빈 구간이 곧 과소 추정이 됐다. 서울~부산의 이름 없는 역이 206개 → 0개, 인구 72.4만 → 85.7만, 이용객 46.8만 → 53.9만, 광역급행 고가 B/C 0.73 → 0.86 이다.
  모르던 곳이 사람 없는 곳으로 밝혀져 역이 빠지기도 해서 건설비는 줄었다(중전철 지하 37.3조 → 34.2조). 수도권 노선 값은 그대로이고 회귀 계수도 넷째 자리까지 같다
- **환승 노선 수는 이름이 아니라 위치로 센다.** 이름만으로 묶었더니 지방 역이 들어오면서
  서울 `시청` 이 부산·대전 `시청` 과 묶여 환승이 2 → 4 로 뛰었다. 400km 떨어진 역은
  환승이 아니다. 하필 **기여가 가장 큰 변수**(계수 1.08)라 회귀가 바로 흔들렸다
  (R² 0.551 → 0.555). 같은 이름이면서 **1km 안**인 노선만 센다
- **도심거리의 기준점은 가장 가까운 광역시 도심이다** (`CBDS` — 서울·부산·대구·광주·대전).
  서울시청 하나로 고정했더니 부산 역이 326km 로 잡혀 표본 범위(0.1~88.7km)를 3.7배
  외삽했고, 도심거리 항만으로 예측이 **0.02배**로 깎여 부산 B/C 가 0.019 처럼 **숫자는
  나오지만 뜻이 없는 값**이 됐다. 고친 뒤 부산 이용객이 2,202 → 96,480명/일이 됐다.
  천안·아산 11개 역은 대전시청이 더 가까워 값이 줄지만(서울 통근권이라 논란의 여지가 있다)
  R² 0.551 → 0.552, 교차검증 1.7454 → 1.7450 으로 모델 품질은 그대로다.
  **`CostCalculator.CBDS` 와 같은 목록이어야 한다** — 어긋나면 학습과 예측이 다른 기준을 쓴다
- SGIS 는 자체 행정구역 코드를 쓴다 (11110 = 노원구). 인구·종사자 API 가 같은 체계라 이어 붙는다
- 인구가 적은 집계구는 `N/A` 로 가려서 온다. 0 으로 채우지 말고 제외해야 합산이 왜곡되지 않는다

## B/C 산출 (`backend/.../calc`)

`PopulationIndex`가 집계구 인구·행정동 종사자 CSV를 0.01° 버킷에 올리고 `CostCalculator`가 선을 0.5km 마다 잰 점의 둘레 1km 를 겹침 없이 합산하고,
`BenefitCalculator`가 수요 모델로 일이용객 → 첨두 수요 → 통행시간 절감편익을 매긴다.

**편익은 이용객이 아니라 노선 이용자 수로 센다**(11-08). 이용객은 역 승차 + 하차의 합이라 한 통행을 두 번 센다. 첨두는 이것을 알아 단면 환산 상한
0.395 에 0.5 가 들어 있는데, 편익은 그대로 곱해 **B/C 가 1.3~2배** 였다. 서울교통공사 2025 역별 일별 수송인원 한 파일로 (승차 + 환승유입) ÷ (승차 × 2) 의
8개 노선 중앙값 0.777 를 곱한다(`users_per_ridership`, S7, `etl/seoul_line_users.py`). 「하차 ≈ 승차」 는 2024 승하차 파일로 0.979~1.025.
처음(11-08)엔 보도된 2024 수송인원을 열린데이터광장 2026 승하차로 나눈 0.745 였다 — 두 출처·두 해라 한 파일로 다시 쟀다. 환승이 없는 노선이면 0.5 다 — 새 노선에 환승이 얼마나 붙을지 몰라 서울 평균을 쓴다.
`CostCalculator`가 수단×구조 전부를 돌려 비교표(`scenario_result`)를 만들고 B/C 최대안을 추천한다.

**원단위는 「교통시설 투자평가지침」 제7판**(국토교통부 지침 2022-500호). S7 참고.

| 값 | 적용 | 근거 |
|---|---|---|
| 시간가치 7,231원/인·시 | 2025년 기준 | 표 4-44 **광역도시철도** 5,768원(2013) × CPI 1.2537 |
| 할인율 4.5% / 3.5% | 개통 후 ~30년 / 31~40년 | 6.2.1 — 철도사업 예외 |
| 분석기간 40년 | 철도 (일반 교통시설은 30년) | 6.2.2 |
| 공사기간 5년 | 투입비율 10·20·30·30·10% | 6.2.2, 표 6-1 |

- **시간가치는 등급을 맞춰 골라야 한다.** 광역도시철도는 업무통행이 4.14%뿐이라 비업무
  5,033원이 값을 지배한다. 고속철도(10,197)·일반철도(6,830)를 쓰면 과대계상이다
- **환산 지수는 CPI다**(6.2.3 (4)) — 건설비의 GDP 디플레이터와 다른 계열이다. 지침이
  2013→2020에 쓴 107.5가 World Bank 한국 CPI 비와 정확히 일치해 환산을 검증했다
- **B/C는 편익·비용 모두 현재가치**(6.3.1). 기준시점이 공사 착수 직전이라 편익은 5년 뒤부터
  시작하고 사업비는 5년에 나눠 투입된다(명목 총액의 0.874배). 화면의 건설비는 명목값이라
  표에서 편익÷건설비로 B/C가 나오지 않는다 — 각주로 안내한다
- 지침값 적용으로 B/C가 자리표시자 대비 **0.84배**가 됐다
  (시간가치 0.80 × 할인 0.91 ÷ 비용 현재가치 0.87)
- **전환 전 수단 속도는 시내버스 21.3km/h** — 국가지표체계「광역시별 승용차 및 시내버스
  평균 통행속도」(승인통계 제20109호) 2025년 6대 광역시 중앙값(`road_speed.csv`).
  서울만 보면 17.1로 느려 편익이 커지고, 승용차 기준(27.2)이면 크게 줄어든다
- **1인당 절감은 평균 통행거리 `avg_trip_km`(13.6km)만큼이다** (`BenefitCalculator.benefitTotal`).
  전에는 이용객 전원이 노선 끝에서 끝까지 탄다고 봐서 1인당 절감이 연장에 비례해 커졌다.
  서울시 2019년 교통 빅데이터의 지하철 1회 이동 13.6km 를 상한으로 둔다(S7, 근거는
  research-log). 노선이 더 짧으면 노선 전체를 탄다
  - 서울시청~강남(8.8km)은 **그대로**, 서울시청~수원(33.4km)은 수단마다 **0.38~0.41배** —
    광역급행 고가 1.86 → 0.76 으로 1.0 아래로 내려간다. 같은 노선 안의 **수단 순위는 그대로**다
  - 기존 수단은 노선 전체의 문앞~문앞 시간을 km 당 시간으로 나눠 쓴다. 역까지 걷는 몫을
    거리에 고르게 나눈 근사라 기존 수단을 조금 빠르게 본다 — 신설안 편익을 덜 세는 쪽이다
- **전환 전 시간은 시내버스와 기존 수단 중 빠른 쪽이다** — 단 **짧은 이동에 탈 수 있는**
  수단만이다(`Option.servesShortTrips`). 도시철도는 역이 1km 마다라 늘 들어가고, **KTX 는
  역이 수십 km 마다라 통행이 노선 전체를 덮을 때만** 들어간다(지금 값이면 사실상 안 들어간다
  — KTX 판정은 35km 넘는 노선에만 하고 평균 통행거리는 13.6km 다).
  서울시청~부산시청에서 광역급행 고가가 **229분·13조 9,623억에 B/C 3.86** 으로 나왔다 —
  기존 KTX 는 164분이다. 기준이 시내버스(349km 를 약 16시간)뿐이라 KTX 를 타던 사람도
  12.6시간을 아낀 것으로 셌다. KTX 시간은 **문앞~문앞**이다 — 그린 양 끝에서 두 역까지의
  직선 거리를 시내버스 속도로 더한다(`ExistingOptions.Option.doorToDoorHours`). 표의
  164분은 역에서 역까지라 그대로 쓰면 KTX 가 유리해진다. 직선은 실제 도로보다 짧아
  이 값은 짧은 쪽으로 치우친다 — **신설안의 편익을 덜 세는 방향**이다
  - **경과** — KTX 를 처음 넣었을 때(이용객이 끝까지 탄다고 보던 때) 서울~부산은 문앞~문앞
    약 190분(역까지 9.2km = 26분 + 164분)이 되어 신설안 11개가 전부 B/C 0 이었다. 평균
    통행거리를 넣자 **13.6km 이동에 KTX 의 km 당 시간을 쓰는 모순**이 생겨("KTX 보다 느려
    절감 없음") KTX 를 기준에서 뺐다. 그때 서울~부산 광역급행 고가가 **3.86 → 0.15** 가 됐고, 11-07 수요 재학습·전국 자료 뒤 0.86, 11-08 경전철 보정 뒤 0.89, 편익 이용자 환산 뒤 0.67, 표본 확장 뒤 0.68, 산 구간 터널비를 넣은 뒤 0.57, 이용자 배수를 한 출처로 다시 잰 뒤 0.71, 광주 1호선을 더한 뒤 0.70, 김포골드·신분당선을 더한 뒤 0.69 다.
    **11-22 에 0.56 으로 내려간 원인은 갈랐다** — 같은 노선(서울역~부산역, 고가)을 자료 파일만 바꿔(`ROAD_FILE`·`WATER_FILE`·`COAST_FILE` 을
    없는 경로로) 네 번 쟀다. 도로 켬+물 켬 **0.561**(도로 393.3km·역 41·비용 16.87조), **도로 끔 0.690**(직선 328.6km·역 30·13.71조),
    물·해안선만 끔 0.561(같음), 둘 다 끔 0.686. 편익은 네 번 모두 82,703 이다. **도로 따라가기(11-12, 광역급행 포함은 사용자 결정)가 노선을
    19.7% 늘리고 역을 11개 더하는데**(비용 +23%), 편익은 `tripKm = min(노선 길이, avg_trip_km 13.6)` 라 노선이 13.6km 를 넘으면 길이에
    **무관하다** — 길어진 만큼이 고스란히 B/C 하락이다. 버그가 아니라 설계의 귀결이다(실제로 도로를 따라 놓으면 그만큼 길고 역도 늘어 돈이 든다).
    **물 위 역 제외(11-21)의 몫은 작다** — 도로를 끈 쌍(둘 다 끔 → 도로만 끔)에서 역 31 → 30개, B/C 0.686 → 0.690(+0.004, 역이 줄어 오히려 오른다).
    도로를 켠 쪽(A·C)은 도로 규칙(다리·터널 위 중간역 제외)이 같은 역을 먼저 빼서 물 규칙의 몫이 갈리지 않는다(C 의 경고에도 「물·다리·터널 위」 4곳이 그대로다). **되돌리려면** 광역급행을 `CostCalculator.ON_ROAD` 에서
    빼면 된다(0.69) — 그러나 아파트를 뚫는 직선이 싫다는 요청이 이유였다. **이 실험을 다시 할 때** 윈도우 `java` 는 껍데기→JVM 자식 구조라
    `Popen.terminate()` 로는 서버가 안 죽는다 — 남은 서버가 같은 포트를 잡아 뒤 변형이 앞 서버의 대답을 받으니(네 번이 전부 같은 값으로 나왔다) **듣는 PID 를 직접** 끈다.
    끝에서 끝까지 가는 사람에게는 KTX 가 더 빠르다는 것은 표의 소요시간이 말한다
  - **소요시간을 모르는 구간은 시내버스만 본다**(지금과 같다). 0 이나 추정값을 넣지 않는다
  - **도시철도도 같다.** 2호선을 따라 지하철을 그리면 2호선을 타던 사람도 시내버스 대비
    절감으로 셌다. 시각표 대신 **공표 표정속도**(`rail_speed.csv` 의 실측 행,
    `UrbanLineSpeed`)로 그린 길이를 환산한다 — 신설안 행의 소요시간과 같은 계산이다.
    강남~삼성~잠실(6.7km)은 2호선 12분이 되어 지하철·경전철·트램·BRT 신설이 B/C 0,
    광역급행(4.4분)만 1.18 로 남는다
  - **편익에는 반올림하지 않은 탑승 시간을 쓴다**(`Option.rideHours`). 표의 칸은 정수 분인데
    그 값을 쓰면 **기존 노선과 속도가 같은 신설안**이 시간을 아끼는 것처럼 나온다 —
    신분당선(47.6)을 따라 복선전철(47.6)을 10km 그리면 둘 다 12.6분인데 13분으로 올림돼
    편익 36억이 생겼다(테스트로 고정)
  - **역 좌표 49개 노선 중 22개만 속도가 이어진다.** 9호선·코레일 광역선·대구·대전·
    부산김해·GTX-A(`수도권 광역급행철도`) 27개는 비고 시내버스 기준이다. 광주 1호선은
    광주교통공사 역간 소요시간 파일로 계산해 더했다(31.63km/h, `use_for_median=0` 이라
    수단별 중앙값·R² 회귀에는 안 들어간다 — research-log). 이름 표기가
    파일마다 달라(`2호선`↔`서울 2호선`, `부산 도시철도 1호선`↔`부산 1호선`) 공백·
    `도시철도`·앞의 `서울`·괄호 꼬리를 떼고 맞춘다. **실측만 쓰고, 한 노선에 실측 값이
    둘이면 고르지 않는다**(대전 2호선은 설계값, GTX-A 는 구간마다 값이 다르다)
  - **짧은 노선은 버스가 이길 수 있다.** 역까지 최대 1km 씩을 버스 속도로 더하므로 3km
    노선이면 버스 8.5분 vs 2호선 5.5분 + 걷는 몫 최대 5.6분이다. 그래서 화면은 "기존
    2호선보다 느림" 이라고 단정하지 않고 "시내버스와 기존 2호선 중 빠른 쪽" 이라고 쓴다
- **B/C 0 인 안은 추천하지 않는다.** KTX 를 처음 넣었을 때 서울~부산 신설안이 전부 0 인데
  복선전철이 추천됐었다. 지금도 2호선을 따라 그리면 11개 중 7개가 0 이다. 백엔드 추천·표의 굵은 행·지도 그림·시나리오 비교의 추천안 **네 곳이 같은
  규칙**이다(`frontend/src/scenario/gainsNothing.js`). 전부 0 이면 표 위에 "추천할
  신설안이 없습니다" 를 한 줄 적는다
- **기준 속도보다 느린 수단은 편익 0이다.** BRT 저급형(18)이 시내버스 21.3보다 느려 B/C 0으로
  찍힌다. 오류가 아니라 "시내버스보다 느리면 시간을 절감하지 못한다"는 결과지만 **BRT 속도가
  아직 가정값**이라 확정할 수 없다 — 숫자를 맞추려고 올리지 말 것. 트램은 실측 22.06으로
  기준을 겨우 넘어 편익이 양수지만 km당 절감이 경전철의 13% 수준이라 B/C 가 매우 낮다
- 비교표에서 **B/C 0.00 은 계산 실패처럼 보인다** — 숫자를 흐리게 하고 이유는 표 위 한 줄로
  말한다("B/C 0.00 인 N개 안은 … 보다 느려 아끼는 시간이 없습니다"). 행마다 꼬리표를 달았더니
  48px B/C 칸에서 숫자 밑으로 내려가 **짧은 「절감 없음」 조차 7행을 두 줄로** 늘렸다
- **BRT 고급형 B/C가 15배까지 튄다**(실사업은 10을 넘지 않는다). 도로 용량 잠식을 빼지 않고
  철도 시간가치를 그대로 쓰기 때문이다. 수단 간 **순위**는 의미가 있어도 절대값은 아니다
- 수요는 모든 수단에 동일하게 적용한다 (수단별 수요 탄성 모델이 없다)
- 인구 CSV 경로는 `app.census-file`·`app.worker-file`. 없으면 기동은 되고 경고만 남는다

### 첨두 단면 — 세 번 보정한다

수요 모델이 내놓는 것은 **주말이 섞인 일 평균**이라 평일 설계 첨두까지 세 단계가 필요하고,
**셋을 따로 재 둬야** 하나만 고쳐도 나머지가 조용히 어긋나지 않는다.

| 계수 | 값 | 근거 |
|---|---|---|
| `weekday_factor` | 1.1041 | 평일 일수요 ÷ 전체 평균 (주말이 평일의 68.6%) |
| `peak_hour_ratio` | 0.1159 | 평일 첨두 1시간 비중 (주말은 0.0834). 광역철도는 공휴일 없는 달 월 기준 서울의 0.96배 — 안 바꿨다(research-log) |
| `peak_direction_coef` | 10.06 | K = 이 값 ÷ 연장km (아래) |
| `peak_direction_max` | 0.395 | K 의 상한 = 0.5 × 0.79(방향 쏠림 실측) |

- 앞의 둘은 `seoul_weekday_peak.py`(서울 1~8호선 평일 21일, 2024-11) 실측이다.
  **첨두 시각이 평일 8시·18시, 주말 16시로 갈린다** — 월 단위 자료로는 이게 안 보인다
- **`peak_direction_ratio` 는 방향 비중이 아니라 환산계수**다. 혼잡도는 교통카드 O/D 기반
  **재차인원**이라 역 승하차가 아니라 단면 통행량이다 (`seoul_congestion.py` → `line_congestion.csv`).
  `pphpd = 혼잡도/100 × 160 × 편성당칸수 × (60÷출근 시격)`, `K = pphpd 최대 ÷ (일 승하차 × 첨두율)`
- **직결 운행 노선(1·3·4·7호선)은 K 산출에서 뺀다** — 다른 기관 역에서 승차한 승객이 단면에
  실리지만 분모에 없어 과대로 나온다. 남은 4개(2·5·6·8호선)의 중앙값이 0.2441 이다
- **K 는 상수가 아니라 연장의 함수다** — `K = min(0.395, 10.06 ÷ 연장km)`.
  통행이 노선보다 짧으면 한 지점을 지나는 통행의 비율이 대략 (평균 통행거리 ÷ 연장)이다.
  상수로 두면 **30~60km 노선에서 잰 값을 5~35km 노선에 적용**해 짧은 노선을 과소 추정한다.
  교차검증(LOO) 오차가 상수 0.0784 → 0.0437 로 낮아졌다. 계수 둘짜리(`a + b/L`)는
  표본 4개에 과적합이라 교차검증이 오히려 나빴다(0.0737) — 한 개짜리를 쓴다
- **노선별 첨두율을 써야 관계가 보인다.** 공통 첨두율을 쓰면 노선마다 다른 첨두 쏠림
  (0.1035~0.1298)이 K 에 섞여 r=0.775 에 그친다. `seoul_weekday_peak.py` 가 노선별로
  내놓는 `line_weekday_peak.csv` 를 쓰면 **r=0.865** 로 또렷해진다
- **25.5km 아래는 전부 상한에 걸리는 외삽이다.** 표본이 30.6~59.8km 네 개뿐이라 그보다
  짧은 구간을 실측으로 받치지 못한다. 상한 0.395 는 모든 통행이 최대 단면을 지날 때의
  이론값이라 물리적으로 넘을 수 없어, 1/L 이 발산하지 않게 잡아 주는 뚜껑이 된다
- 노선별 K 값과 분해 과정(이론값 0.395 대비 단면 집중 0.62)은 `docs/research-log.md` 참고
- **실측 최대 단면은 20,403(8호선)~57,754(2호선)명/시다.** 상한 80,000 은 2호선 57,754 가
  안에 들어와 타당성을 확인했다

## 추천 기준값

**국토부 운영현황은 낡을 수 있다 — 세어 봤더니 스물한 줄 중 하나였다.** 인천 1호선이
30.3km/30역로 들어 있는데 검단연장(6.825km·3개소)이 2025-06-28 개통해 지금은 37.1km/33역이다.
같은 방식으로 여덟 노선을 의심해 봤지만 나머지는 **역수가 이미 연장분을 세고 있거나
(부산1·대구1) 아직 미개통(서울3)** 이었다. **고치지 않았다** — 중앙값이 1.065 → 1.068 로
0.003km 움직일 뿐이고, 우연히 확인한 한 줄만 바꾸면 나머지 스무 줄과 섞여 더 고르지 않다.
**여럿을 묶어 중앙값을 낼 때는 한 출처만 쓰고, 하나를 콕 집어 쓸 때는 최신을 쓴다** —
역간격·속도 자가 그래서 `rail_speed.csv` 의 운영사 값을 쓰고
`crosscheck_spacing()` 이 두 출처가 다른 노선을 매번 보고한다.

**역간격(중앙값)** 중전철 1.06km(표본 21) / 경전철 1.06km(7) / 트램 0.45~0.86km(2) /
복선전철 **2.62km**(6) / 광역급행 **6.92km**(4). **복선전철 하나였던 것을 둘로 갈랐다** —
분포가 쌍봉이라 전체 중앙값 4.30km 가 아무 노선도 없는 틈이었다(아래 「급행 분리」).
운영현황 **한 출처만** 쓴다 — 같은 노선이
여러 출처에 중복돼 전체로 집계하면 2~6번 잡힌다(`spacing_stats`). 평균이 아니라 중앙값을
쓴다(공항철도 63.8km/14역 같은 특수 노선에 끌려감).

**수송능력 상한(`pphpd_max`)** 지하철 8만 / 경전철 6.6만 / BRT 3.5만. 넘으면 탈락한다.

**수요 하한(`pphpd_min`)은 수송능력이 아니라 실제 운영 노선의 최저 단면이다.**
수송능력 범위의 하한을 "이 수단을 지을 최소 수요"로 쓰는 것은 **범주가 다른 값**이었다.
실측해 보니 6호선 21,677 · 8호선 20,403명/시로 운영 중인 중전철이 옛 하한 40,000에 못 미쳤다 —
서울 6·8호선이 "지하철을 지을 이유가 없는 노선"으로 판정됐던 셈이다.

| 수단 | 하한 | 근거 |
|---|---|---|
| 중전철 | 20,000 | 실측 — 8호선 20,403 |
| 경전철 | 4,700 | 추정 — 우이신설 4,735 / 신림 4,821. 짧아서 K 상한 구간이라 **외삽**이다 |
| 복선전철·단선전철 | NULL | 단면을 세울 근거가 없다 (아래) |
| 트램·BRT | NULL | 더 싼 철도 대안이 없어 경고가 무의미하고 국내 실측도 없다 |

NULL 이면 경고를 띄우지 않는다. **근거 없이 경고하지 않는다.**

**복선전철 하한을 세우려면 상하행 승하차가 필요하다.** 공식 자료 3종을 모두 확인했고 전부
막혔다 — **재조사 전 `docs/research-log.md` 를 볼 것.** `K` 환산은 연장에 반비례해 100km 넘는
광역철도의 단면을 과대평가하므로 쓰지 않는다. 경고 남발보다 NULL 이 낫다.

**BRT와 경전철의 구간이 겹치는데 건설비는 10~20배 차이난다** — "이 구간은 BRT면 충분한데
지하철을 지으면 B/C가 0.4로 떨어진다"를 보여주는 것이 이 프로젝트의 핵심 가치다.

**노선 길이 상한(권장 연장)** 지하철 60.2km / 경전철 29.1 / 트램 25 / BRT 30 (`max_length_km`).
넘으면 복선전철을 후보에 추가하고 도시 수단은 "권장 연장 초과"로 표시만 한다 — **상한은 금지선이
아니라 경고선**이다. 지하철·경전철은 **운영현황 노선의 최장 연장**(서울 2호선 · 인천 2호선)이다 —
수요 하한이 "실제 운영 노선의 최저 단면" 이듯. 트램·BRT 는 가정값이다(운영 노선이 없거나, 최장이
`is_outlier` 행·다른 노선과 겹치는 행이다 — S1 주석). `etl/test_mode_capacity.py` 가 감시한다.
- **35km 였을 때는 근거가 없었다(2026-11-04 까지).** 실습일지에 이유를 적으려고 실제 노선 길이를
  늘어놓으니 운영 중인 지하철 21개 중 **9개가 35km 를 넘었다**(2호선 60.2 · 5호선 59.8 …) —
  처음 기준값을 만들 때 넣은 값이 경고·추천·KTX 판정 세 곳에 쓰이고 있었다
- **KTX 문턱은 떼어 냈다.** 권장 연장의 최댓값을 KTX 판정 문턱으로 같이 썼는데, 상한을 60.2 로
  올리면 문턱도 60km 가 되어 같은 KTX 노선의 역이 35~60km 떨어진 **79쌍**(동대구~경주 46.9 ·
  부산~울산(통도사) 49.2 · 수원~천안아산 53.2 …)에서 KTX 안내가 사라진다. 뜻이 다른 두 값이라
  KTX 문턱은 `IntercityRailFinder.MIN_ROUTE_KM`(35km, 판단값 — 전과 같은 값)으로 옮겼다
- 한계 — 운영현황 연장은 지선을 포함하고(2호선·5호선, 한 줄 최장은 더 짧다), 거꾸로 한 노선을
  갈라 적기도 한다(9호선 1단계/2·3단계, 7호선 연장이 「인천 7호선」). 반대 방향이라 두었다

**표정속도(`speed_kmh`)** 중전철 32.4 / 경전철 29.3 / 트램 22.1 / 복선전철 47.6 /
광역급행 91.8.
노선별 표본·출처·중앙값 포함 여부는 **`data/seed/rail_speed.csv` 가 원본**이다. 평균이 아니라
중앙값을 쓴다. **트램 22.1 은 대전 2호선 설계값**이다 — 국내 운영 노선이 없다.
출처는 서울·부산교통공사 공공데이터(표정속도 직접 공표)와 각 운영사 공식 페이지다. 국토교통부
운영현황에는 속도 열이 없다. 소요시간이 있는 노선은 연장÷소요시간이 공표값과 ±0.05 안에서 맞았다.
**급행(GTX)은 이제 별도 수단이다** — 아래 「급행 분리」 참고.

**역간격이 표정속도를 설명한다** — `속도 = 18.56 + 12.65 × 역간격` (노선 18개, **R² 0.925**).
역간격 0.71~2.36km 에서 수단을 구분하지 않아도 93% 가 설명된다. **기술이 아니라 정차 횟수가
속도를 정한다.** 자는 `mode_speed_check.py` 가 만들고, **실측만** 쓴다(`FIT_BASIS`) —
설계값을 넣으면 자가 가정을 재게 된다.

**복선전철 2.62 를 운영 중 광역철도로 교차검증했다.** 한국철도공사 광역열차 운영정보
(기준일 25.1.1) 12개 노선의 역간격 중앙값이 **2.21km** 다(1.35~8.84). 우리 2.62 는
**사업계획** 6건 중앙값이라 19% 넓은데, 신설 노선이 기존선 전환보다 역을 띄엄띄엄 놓는
것으로 설명된다. **값은 바꾸지 않았다** — 두 집단은 성격이 다르다.

**역간격 2.36~4.98km 는 여전히 비어 있다 — 찾아봤고 막혔다.** 그 구간에 중앙선(2.579)·
경춘선(4.035)·경강선(4.750)·대경선(8.843)이 있지만 **코레일은 소요시간을 공표하지 않는다**
(국토부 운영현황에 속도 열이 없는 것과 같다). 2차 자료에는 있으나 기준에 못 미친다.
**재조사 전 `docs/research-log.md` 를 볼 것** — 어디를 보면 되는지 값어치 순으로 적어 뒀다.
특히 **중앙선(2.579)은 S1 의 2.62 와 거의 같아 47.6 을 직접 검증할 수 있다.**

**구간 위쪽 두 점이 어긋난다 — 설명하지 못했다.** 김포 골드라인(2.36km)이 신분당선
(2.09km)보다 **역간격이 넓은데 더 느리다**(45.08 vs 47.60). 차량 한계인가 찾아봤더니
**둘 다 운행 최고속도 80km/h** 로 같아 가설이 틀렸다. 전에 적었던 R² 0.958 은 노선 16개
짜리였고, **구간이 2.09km 에서 끊겨 있어서 나온 값**이다. 넓히니 0.925 로 내려갔다.

**신분당선 검증은 표본 밖에서 해야 뜻이 있다.** 전에 "직선에서 0.04km/h 벗어났다"고 적은
것은 **표본 안 잔차**였다 — 자기를 포함해 그은 선과의 거리다. 제대로 **빼고 적합해 예측**하면
16개 자에서 47.71 vs 실측 47.60(**+0.2%**)으로 오히려 더 강한 검증이었다. 다만 18개 자에서는
−7.9% 다 — 위 어긋남 때문이고, 검증이 **좁은 구간에서만 성립했다**는 뜻이다.

**단 포화한다 — 급행은 이 직선 위에 없다.** 역간격 6.92km 에서 예측 106.2 vs 실측 91.8
(**0.86배**). BRT 기울기(+10.6)가 철도(+12.7)보다 완만한 것도 같은 방향으로 읽힌다.
다만 **차량 최고속도로 설명하려던 시도는 실패했다**(위 참고) — 포화의 기제는 아직 모른다. **급행을 적합 표본에 넣지 말 것** — 포화를 보이려면 포화한 점이
표본 **밖**에 있어야 한다. `mode_speed_check.load_pairs` 가 `SATURATED_MODES` 로 빼고
`express_speed()`/`express_spacing()` 이 따로 내놓는다(테스트가 감시한다).

### 급행 분리 — 복선전철을 둘로 갈랐다 (다음 할 일 ②·⑧ 완료)

**복선전철 한 행이 세 곳에서 온 값을 갖고 있었다.** 역간격은 10개 노선 전체 중앙값
4.30km, 속도는 신분당선 하나(47.6, 그 노선 역간격 **2.09km**), 비용은 A등급 11건 회귀.
역을 4.30km 간격으로 놓고 2.09km 간격 노선의 속도를 쓴 셈이라 회귀식과 **−35%** 어긋났다.
뿌리는 **쌍봉 분포**다 — 중앙값은 "가운데 값"이지 "대표값"이 아니다. 봉우리가 둘이면
가운데는 골짜기이고, 4.30 자리에는 **아무 노선도 없었다**.

| | 역간격 | 속도 | 회귀와 | 근거 |
|---|---|---|---|---|
| 복선전철(일반 광역) | 2.62 | 47.6 | **−8%** (전 −35%) | 신분당선 — 이제 같은 집단 |
| 광역급행(`EXPRESS_RAIL`) | 6.92 | 91.8 | −14% (포화 구간) | GTX-A 두 구간 중앙값 |

**전체 이야기는 `db/seed/S1__mode_capacity.sql` 주석에 있다** — 쌍봉 분포 그림, 비용을
가르지 않은 이유, `EXPRESS_RAIL` 이 `reference_line` ENUM 에 없는 까닭, 급행 속도 n=2 의
기준이 섞인 사정까지. **값을 고칠 사람이 실제로 여는 파일이 거기다.** 요약하면 —
비용은 안 갈랐고(잔차 1.02배, t=+0.08), **검출 한계가 1.50배라 이 검정은 어느 쪽도 가리지
못한다.** 안 가른 진짜 이유는 표본 4개에 더미를 붙이는 과적합이다. 역간격 2.1~4.9km 에
실측 속도가 없어 "봉우리가 둘뿐"임은 확인할 수 없다.
검사·재현 `cd etl && python mode_speed_check.py` (값은 고치지 않는다).

**`cost_model.SPACING` 은 S1 의 `spacing_km` 과 같아야 한다 — ETL 이 검사해 멈춘다.**
실제로 4.98 vs 4.30 으로 어긋나 있었다. 막는 이유는 정확도가 아니라(직선 근사 오차가
0.79% vs 0.95% 로 둘 다 1% 안이었다) **같은 값이 두 곳에서 다르면 어느 쪽이 맞는지 알 수
없기 때문**이다.

**S5 는 지우지 않고 내린다**(`is_active=FALSE`). `scenario_result.standard_id` 가 FK 로
참조해 `DELETE` 도 `TRUNCATE` 도 막히고, 내려 두면 **저장된 B/C 가 어느 기준값으로
계산됐는지** 남는다. 백엔드는 `findByActiveTrue()` 로 읽으므로 계산에는 안 쓰인다.

### BRT 표정속도 — 아직 가정값이다

고급형 25.0 / 저급형 18.0 이 **가정값**이고, 저급형이 기준 수단(시내버스 21.3)보다 느려
**편익이 항상 0** 으로 찍힌다. 공식 실측을 6곳에서 찾아 전부 막혔고, 세종시 시간표는
기점 출발시각만 있고 정류장별 도착시각이 없다 — **옮겨 적을 소요시간 자체가 없다**
(전에 "이미지라 못 읽는다"고만 적고 될 것처럼 남겨 뒀던 길이다).

그래서 **실시간 차량 추적으로 직접 재고 있다**(`etl/sejong_brt_speed.py`). 세종 BIS 가
차량 위치와 노선 선형을 줘서 연장까지 직접 계산된다(B1 편도 51.9km 가 `brt_seed.csv` 의
53.0km 와 2% 안에서 맞았다). **측정 방법·함정·바꿀 기준은 `docs/research-log.md` 에 있다 —
재조사 전에 볼 것.**

- **바꿀 조건 넷을 결과 보기 전에 정해 뒀다** — 대표성(평일 첨두 대조군이 공표 대전 21.6
  의 ±20% 안) / 표준오차 3% 이하 / 평일 첨두·보통 채움 / 구간 표본을 묶을 수 있음.
  **넷을 모두** 만족해야 바꾼다. 핵심은 **모델이 필요한 것은 연평균인데 이 측정은 시간대
  조각**이라는 것이고, 대조군이 공표 연평균으로 달리는 시간대가 곧 평균적 교통 조건이다
- **아직 `speed_kmh` 에 넣지 않았다.** 가정값을 실측값으로 바꿔 적으면 출처가 "실측" 이
  되어 다음 사람이 의심하지 않는다 — 가정값으로 남겨 두는 것보다 나쁘다
- **"측정 BRT ÷ 일반버스 치우침" 보정은 쓸 수 없다.** 그러려면 둘이 혼잡에 똑같이 민감해야
  하는데 그건 BRT 의 존재 이유를 부정한다. 빈 도로에서는 전용차로가 아무것도 사 주지
  않는다 — **BRT 편익은 혼잡 구간에서만 나온다. 이것 자체가 보고서에 쓸 발견이다**
- **같은 전용도로에서 역간격이 표정속도를 지배한다** — 1km 늘 때 **+10.6km/h**
  (B5 0.63km→28.2 … B3 2.73km→56.3). 노선마다 신호·차로가 달라 상한으로 읽을 것.
  **이 발견을 철도에 옮겨 보다가** `rail_speed.csv` 가 역간격으로 거의 완전히 설명된다는
  것(R² 0.925)과 복선전철의 역간격·속도가 서로 다른 노선 집합에서 왔다는 것을 찾았다 —
  BRT 를 재려다 모델의 더 큰 문제를 찾은 셈이다
- **판정은 코드가 한다** — `--report` 끝의 「바꿀 조건 판정」(`verdict()`). 사람이 격자를 보고
  맞춰 보면 결과에 맞춰 기준을 읽게 된다. 기준값(±20%·3%)은 미리 적은 그대로 상수다.
  **최종 판정(2026-10-26, 평일 보통까지 채움): 두 등급 모두 가정값 유지.** BRT_HIGH 는
  정밀도 1.0%·격자·묶기를 통과하고 **대표성 하나**에서 막혔다 — 평일 첨두 대조군 29.41 이
  공표 21.6 의 1.36배이고, 평일 보통(27.59)까지 넣어도 시간대별 대조군이 27.6~35.9 라 21.6 은
  **외삽**이다. BRT_LOW 는 정밀도(3.9%)·묶기도 미달. **더 모아도 안 바뀐다** — 칸이 비어서가
  아니라 재는 방식이 달라서다. 그래서 수집을 멈췄다(표는 research-log 「최종 판정」)
- **수집을 걸기 전에 `--preflight` 를 돌릴 것.** 수집은 2~3시간짜리 예약 작업이라
  **API 나 선형이 바뀐 것을 새벽 6시 50분에 알면 그날을 날린다.** `--report` 는 요일 ×
  시간대 격자의 빈 칸을 보여 준다. **대조군(1005)은 BRT 와 같은 시간대에 함께 돌릴 것**
- 남은 길은 **운영기관 문의**(세종도시교통공사 044-850-0125)다 — 공표값이 있으면 특정
  시점 실측보다 그쪽이 낫다. **숫자를 맞추려고 추정값을 넣지 말 것.**

**구조 형식(지하/고가/지상)** 수단보다 비용을 더 크게 가르는 변수다(같은 경전철이 고가 401억,
지하 637~836억/km). `cost_standard`는 "수단 × 구조" 조합. 기본값은 수도권 도심 지하, 그 외
고가(`preferred_structure`). 트램은 지상 전용. **어떤 구조도 막지 않는다** — 지방에서 지하를
골라도 고가 대비 얼마가 더 드는지 보여준다. **선택을 막는 대신 대가를 보여주는 것**이
이 서비스의 방식이다.

**규제 구역(`restricted_zone` 12건)** 문화재·상수원 `REVIEW`, 군사 통제보호구역 `BLOCKED`.
**좌표·반경 모두 근사치**라 단정하지 않고 "확인 필요"로만 안내한다.
**11-12 사용자 화면에서 세 가지가 함께 깨져 있었다** — 서대문구청 쪽에서 한성대입구 쪽으로 점 둘(지하)을 찍어 선이 경복궁 중심 0.4km·창덕궁 0.7km 를
지나는데 아무 말이 없었다. ① 경고(`zoneWarning`)가 **찍은 점**만 원과 견줬다(양 끝은 3km 밖) → 선분과 중심의 거리로(`RestrictedZones.crossed`,
노선을 따라 닿는 순). ② 지도의 원이 **화면 픽셀 크기**(줌 14 에서 26px ≈ 170m)라 반경 1km 구역이 작게 보여 선이 원 사이로 비껴가는 것처럼 보였다 →
64각형 면으로 실제 반경. ③ 산 안내가 **구조 선택창(지하)**을 따라 꺼져, 표에서 터널비 530억이 든 트램 행을 골라도 말이 없었다 → 지도에 그린 행의
구조로 가른다(묻기는 땅 위 기준으로 한 번). 그리고 사용자 결정으로 **피해 가는 선형을 제안한다**(`/api/route/zones`) — 호수 우회(`WaterDetour`)에
원을 48각형으로 넘기고 문구만 바꾼다(「물」 이 아니라 「구역」). 둘레 구역을 모두 막아 돌아간 길이 옆 구역(덕수궁)으로 들어가지 않는다. 같은 노선은
+0.3km 로 두 궁 북쪽을 돈다(그 길은 북악 기슭이라 산 안내가 새로 뜬다). **지하도 제안한다** — 호수는 물 밑으로 지나면 되지만 문화재·상수원은 굴착이
문제다. 화면을 붙이다 `api.zones`(지도 원 목록)를 같은 이름으로 덮어 원이 하나도 안 그려졌다 — 객체 키가 겹치면 오류 없이 뒤의 것이 이긴다
(`client.test.js` 가 이름 중복을 막는다). 철도보호지구는 넣지
않는다 — 신고·협의 대상이지 금지가 아니고, 넣으면 도심 대부분이 막힌다. 정식 경계는
국가문화유산포털·물환경정보시스템·국토정보플랫폼에서 받아 교체할 것.

**경고 문구(`scenario_result.warning`)** 경고는 계산을 막지 않는다. 유일한 탈락 조건은
수송능력 초과(`is_feasible=FALSE`)이며 이때도 행은 남긴다.

| 상황 | 문구 |
|---|---|
| 연장 > `max_length_km` | 권장 연장 초과 — 복선전철 대안 참고 |
| 첨두 수요 > `pphpd_max` | 수송능력 초과 (`is_feasible=FALSE`) |
| 첨두 단면 < `pphpd_min` | 과잉 투자 검토 — 실제 운영 노선 최저 수준 미달 |
| 지하 선택 | 고가 대비 +N억 / B/C 변화 |
| 규제 구역 반경 내 | 규제구역 인접 — 확인 필요 |

### 정차역 자동 배치 (`StationPlanner`)

**반경 500m 안에 한 명도 없으면 역으로 세지 않는다 — 강·호수·바다가 그렇다.**
집계구가 없어 **이름도 못 짓고**(`name` 이 null) **이용객도 0** 인데, 창 안 모든 후보가
0 점이라 "동점이면 이상 위치" 규칙이 걸려 **수면 한가운데 이름 없는 역**이 그대로 찍혔다.
송도~영종도(바다 14km)를 그리면 15역 중 **8역**이 그랬고, 좌표가 완벽히 균등한 것
(37.42193 → 37.42971 → 37.43750)이 "한 번도 안 움직였다"는 증거였다.

- **옮기는 게 아니라 빼는 것이 맞다.** 창이 역간격의 ±35%(중전철 ±370m)뿐이라
  넓은 수면에서는 **밀어낼 뭍이 창 안에 없다.** 실제 교량·하저터널에도 중간역이 없다.
  고친 뒤 송도~영종도 15 → **7역**, 춘천~양구(소양호) 32 → **8역**이 됐다
- **종점은 뺄 수 없다.** 사용자가 찍은 설계 의도이고 양 끝이 사라지면 노선이 아니다.
  그래서 양구 쪽 종점은 인구 0·이름 없음인 채로 남는다 — 이건 결함이 아니다
- **"인구 0" 과 "인구를 모름" 은 다르다 — 그리고 지역 단위로도 갈라야 한다.**
  - 파일이 아예 없으면 모든 자리가 0 이라, `hasCensus()` 가드가 없으면 **종점 둘만 남고
    역이 전부 사라진다** (변이로 확인 — 이 가드를 빼면 테스트 4개가 깨진다)
  - **집계구는 (11-07 전까지) 기존 역 주변으로 모은 자료였다.** 서울~부산 직선의 10~90% 구간에는 반경
    500m 집계구가 **한 칸도 없다** — 사람이 없어서가 아니라 안 모아서다. 처음엔 이걸
    구분하지 않아 **318곳을 빼 놓고 화면에 "수면·무인 구간" 이라고 적었다.** 단정할 수
    없는 말이었고, 역을 빼면 비용이 **낮아지는 쪽**이라 더 나빴다
  - 그래서 **반경 10km 안에 집계구가 하나라도 있을 때만** 뺀다(`COVERAGE_RADIUS_KM`).
    같은 반경에서 인천 앞바다 854칸 · 소양호 405칸(자료를 모은 지역의 물)인데
    서울~부산 중간은 **0칸**이라 또렷하게 갈린다. 한강은 양안 집계구가 반경 500m 안에
    들어와(마포대교 7칸 · 잠실 36칸) 애초에 이 가지를 타지도 않는다 — **그래서 물 면을 직접 본다**(11-21, `StationPlanner` 의 `wet` —
    호수·강 `WaterBodies.contains` · 바다 `Coastline.isSea`). 이 한계 그대로 도로를 따라가는 행(역을 선 위 그대로 둔다)에서 여의도~마포 BRT 의 「용강동」
    역이 마포대교 위 한강 물 위에 놓였다(실제 서버로 한강 4노선 8행을 계산해 1행). 중간역이 물 위면 사람이 있어도 빼고, 종점은 그대로 둔다.
    **다리·터널·진출입로도 같다**(11-21) — 도로를 따라가는 행은 큰길로 옮기는 단계(그런 간선을 피한다)를 건너뛰어, 한남동~명동 트램 역이 고가 위·BRT 역이
    남산1호터널 안에 놓였다(터널·고가 6노선 12행 중 2행). `RoadNetwork` 가 그런 토막을 따로 담아 「8m 안에 금지 간선이 있고 허용 간선은 없다」 면 뺀다
    (고가 밑 지상 도로·터널 입구 교차점은 역 자리). 뺀 역의 경고는 까닭별로 나눈다 — 물 위 역을 직접 빼기 시작하자 「인구가 없어」 가 틀린 말이 됐다
  - 고친 뒤 서울~부산이 **9역 → 32역**, 뺀 역이 **318 → 14** 가 됐다
  - 문구도 **확인한 사실만** 적는다 — `N곳은 반경 500m 안에 인구가 없어 역을 놓지
    않았습니다`. 왜 비었는지는 단정하지 않는다
- **비용은 추정 역 수가 아니라 실제로 놓인 역 수로 매긴다.** 짓지도 않을 역의 값을 물리면
  안 되고 화면의 역수와도 어긋난다. 무인 구간도 같이 걸러지는데 그 역시 역 자리가 아니다
- **왜 역이 적은지 화면에 적는다** — `N곳은 인구가 없어 역을 놓지 않았습니다 (수면·무인
  구간)`. 33km 노선에 역이 8개뿐인 결과가 실제로 나오는데, 말해 주지 않으면 "계산이
  덜 됐나" 로 읽힌다. `warning` 이 **VARCHAR(200)** 이라 짧게 쓴다(최악 168자)
- **못 하는 것 둘** — 교량·하저터널 **할증이 없다**(`cost_standard` 는 수단 × 구조뿐이라
  한강을 건너는 지상 1km 와 평지 1km 가 같은 값이다). 그래서 **"다리 vs 우회" 중 어느 쪽이
  싼지 견줄 수 없다.** 그리고 **우리가 선형을 바꾸지는 않는다** — 그린 선이 설계 의도이고,
  우회할지는 사용자가 정할 일이다. 그래서 아래 「호수·저수지 우회 제안」 은 **제안만** 한다

### 정차역을 큰길로 붙인다 (`RoadNetwork`, 2026-11-12)

**역이 아파트 단지 한가운데에 놓였다**(사용자 화면 — 노량진2동, 동 사이). 인구 봉우리로 끌고(창 ±35%), 옆으로 0.5km 까지 비키니
사람이 가장 많은 자리 = 단지 한복판이다. 실제 역은 큰길 밑(지하철)·위(고가)나 도로 위(BRT·트램)에 있다. 사용자 결정(11-12):
**노선도 같이 꺾여도 된다** — 역 표시만 옮기지 않고 역 자리를 옮긴다.

- **큰길** — `etl/osm_roads.py` 가 OSM 에서 trunk·primary·secondary·tertiary 를 받는다. residential·service 는 뺀다(단지 통로·골목 —
  옮겨 봐야 또 단지 안), motorway·`motorroad=yes`(자동차전용도로)는 역을 둘 수 없어 뺀다, **교량·터널 토막도 뺀다**(한강 다리 위·산
  터널 속으로 역이 가면 안 된다). 한국 OSM 은 **인도가 거의 없어**(`sidewalk` 태그·`footway=sidewalk` 선) 중심선에 붙인다. 5m 오차로
  줄이고 소수 5자리(≈1m)로 `data/build/road_graph.csv.gz` 에 적는다(처음엔 모양만 담은 `roads.csv.gz` 였고, 도로를 따라가는 기능을 붙이며 교차점 번호가 든 도로망으로 바꿨다)
- **붙이기** — 인구 자리를 다 고른 뒤 가장 가까운 큰길 **선분 위** 점(꼭짓점이 아니다)으로 옮긴다. **보조간선 이상 0.3km(판단값) → 집산도로
  0.3km → 둘 다 없으면 먼 한도 0.6km(판단값, 11-13) 안에서 가까운 쪽 → 그래도 없으면 그대로** 둔다. 0.3km 뿐이던 때는 빽빽한 주택가에서 가장 가까운 길이
  474m(부천 고강본동)·562m(서울 아현)라 역이 건물 블록에 그대로 남았다(사용자 화면 11-13) — 같은 노선 21개 역 중 11개가 보조간선 이상이 300m 밖이었다. 종점도 옮긴다(찍은 점이 건물 위일 수 있다). 옮긴 뒤의 자리로 이름·인구·「반경 500m 무인이면
  뺀다」 를 다시 잰다
- **비용** — 옮긴 몫은 옆으로 비킨 길이(detourKm — 옮긴 역을 이은 선 − 선 위 자리를 이은 선)에 든다. 모든 역이 같은 쪽으로 평행하게
  옮겨지면 역 사이 길이가 그대로라 0 이다(테스트가 그렇게 박는다)
- **지도** — 빨간 선은 찍은 양 끝이 아니라 **종점역에서 시작하고 끝난다**(`routeLine.js`). 찍은 점까지 그리면 단지 안의 점에서 길 위의
  역으로 꺾여 들어간다
- **함정 ① 수도권 1°×1° 칸은 18MB 에서 끊겼다**(IncompleteRead) → 0.5° 로 4등분, 교량·터널·자동차전용도로는 Overpass 쪽에서 거른다.
  **서울 0.5° 칸은 502 가 거듭 났다** → 두 번 실패하면 넷으로 더 쪼갠다(0.125° 까지)
- **함정 ② float 좌표** — 처음엔 메모리를 아끼려 float 로 담았는데 경도 127° 에서 한 칸이 1.5×10⁻⁵°(1.3m)라 길 위로 옮긴 점이 길에서
  비켜났다. 자료가 소수 5자리라 **도 × 10⁵ 정수**로 담으면 같은 4바이트로 그대로 담긴다
- **파일이 없으면 꺼진다**(「큰길 없음」 이 아니다) — 역은 예전처럼 인구 자리에 남는다
- **측정(11-12)** — 0.5° 칸 72개(서울·대구 등 몇 칸은 0.25° 로 쪼갬), way 146,914개 · 점 81만 개 · 처음 받은 모양 자료 4.2MB — 도로망(`road_graph.csv.gz`)은 교차점 26만·간선 34만·8.2MB(저장소에 둔다, 전국 72칸 모두 — 제주·남해안 13칸은 첫 받기가 끝난 뒤 들어왔다),
  백엔드가 읽으면 선분 66만 개. 사용자가 짚은 노량진2동역(116번 「호수테스트」 복선전철)은 단지 쪽 (37.51124, 126.94613) → 서쪽 약 145m
  삼익아파트 앞 길 모퉁이 (37.51094, 126.94455), 양 끝 종점역은 약 50m·65m 옮겨졌다

### 트램·BRT·광역급행은 기존 도로를 따라간다 (`RoadRoute`, 2026-11-12)

**사용자 지적** — 땅 위 도로를 쓰는 수단이 그린 직선 그대로라 다리 없는 한강을 건너는 도로를 새로 놓고, 아파트 단지를 뚫고 지나는 셈이었다.
**자동 적용**(사용자 결정), 광역급행도 포함(사용자 결정 — 앱의 광역급행은 GTX 같은 철도라고 확인한 뒤 골랐다). 설계는
`docs/superpowers/specs/2026-11-12-road-following-design.md`.

- **도로망** — `etl/osm_roads.py` 가 way 를 교차점(두 way 이상이 쓰는 node·양 끝)에서 잘라 간선으로 만든다(`out body geom` 의 node 번호 — 처음
  받은 「모양만」 자료는 이음이 없어 다시 받았다). trunk~tertiary 와 진출입로, **다리·터널 포함**, 자동차전용도로·motorway 제외. 표시 1 다리 · 2 터널 ·
  4 진출입로 · 8 집산도로 — 정차역은 1·2·4 가 아닌 간선에만, 보조간선 이상을 먼저
- **길 찾기** — 그린 점마다 1km(판단값) 안의 가장 가까운 교차점끼리 A*(도로 중심선 길이, 어림 = 직선). 방향·회전은 보지 않는다. 펼칠 교차점 300만 한도
- **판정** — 구간마다 도로 길이 ≤ 직선 × **2.0**(판단값, `RoadRoute.MAX_RATIO`)이면 도로. 처음엔 1.5(호수·산 우회와 같은 가정값)였고 **물을 건너는 구간은 11-21 에(사용자 결정 — 새 다리는 1km 에 약 451억이라 돌아가더라도 기존 다리가 낫다), 땅 위 구간은 11-22 에 같은 값으로 넓혔다**: 도로망이 큰길(trunk~tertiary)만 담고 자동차전용도로·이면도로를 빼 도심에서 돌아가는 길이 길어, 서울(37.47~37.64°N, 126.86~127.14°E) 1~6km 391구간 중 26% 가 1.5배를 넘어 건물 블록을 대각선으로 뚫는 「새 도로」 가 됐다(강남역 근처 2.8km 노선 — 사용자 위임으로 조사 기록의 선택지 ②를 적용). **실측**(진짜 도로망, 양 끝이 큰길 위로 옮겨지고 물을 안 건너는 서울 600구간): 새 도로 5.3%(32개), 도로를 따를 때 평균 도로/직선 1.37, 강남 2.8km 노선은 새 도로 2.8km → 도로 4.46km. 근거가 약한 값이다 — 돌아가는 시간 값을 비용에 넣으면 이 문턱을 비용으로 갈라야 하고, 되돌리려면 상수 하나다. 아니면 직선 새 도로(이유: 「기존 도로가 N배라」·「잇지 못해」). **단 그 직선이 물(호수·강·바다)을 건너면 육지는 도로, 물 위만 새 다리다**(11-19 사용자 요청,
  `RoadRoute.acrossWater`) — 전에는 한강 0.9km 를 건너는 4.6km 노선(잠실)이 통째로 직선 새 도로(땅 위 3.7km 「모름」)였다. 구간을 「육지 – 다리 – 육지 …」 로 쪼개고
  (물 토막은 호수·강·바다를 합쳐 선 위 순서로 정렬, 겹치거나 20m 안에 맞닿으면 하나로, **50m 미만은 개울이라 다리로 안 친다**) 육지 토막은 양 끝을 큰길 위로
  옮겨 도로 경로 ≤ 직선 × 1.5 면 도로, 아니면 이웃한 다리에 붙여 새 도로로 둔다. 100m 미만 육지는 도로로 잇지 않고 다리에 붙인다. **도로로 잇는 육지가 하나도 없으면
  예전처럼 직선 한 토막**이다(혼합이 아니다). **왜 새 도로인지는 조각마다 이유로 남긴다**(11-19, `Piece.reason` — 「기존 도로가 1.7배(7.6km)라 육지는 도로를 따르고 물 위만 새 다리」 ·
  「… 물 위와 도로로 못 이은 육지만 새 도로」 · **물이 없는 조각은 「… 도로로 못 이은 육지만 새 도로」**(11-21 — 「물 위」 라 적으면 사실과 다르다) · 「… 물을 건너지만 양쪽 육지도 도로로 이을 수 없어 직선 그대로」 · 물 없는 직선은 「… 새 도로」). 저장 문자열의 새 도로 조각 뒤에
  탭(`	`)과 이유를 붙이고(`|`·공백과 안 겹친다), 이유 없이 저장된 옛 결과는 null 로 읽혀 화면이 줄을 안 그린다(지어내지 않는다). 응답은 `routeLine[].reason`. **저장 조각이 깨졌으면(좌표가 아닌 토큰·점 하나뿐) 읽을 때 그 조각만 건너뛴다**(11-21, `RoadRoute.parsePiece`) — 한 조각 때문에 시나리오 상세 조회가 통째로 실패하면 안 된다. 구분자는 소스에 실제 탭 문자가 아니라 `	` 이스케이프로 적는다(편집기가 공백으로 바꾸면 저장 형식이 깨진다 — `소스에_탭_문자가_없다` 가 막는다). 앞 다리는 도로 위(옮긴 점)에서 끝나 조각이 끊기지 않는다. **실측**(한강 남북 9곳, 진짜 도로망·물 파일): 직선이 되던 4곳 중
  3곳이 혼합이 됐다(11-19) — 잠실 4.58km 전부 새 도로 → 도로 3.95 + 새 다리 1.44(물 0.91 — 다리 조각이 둑에서 둑이라 물 아닌 0.5km 가 낀다)이고 경고가 「새 도로 3.7km」 → 「0.5km」
  로 줄었다(나머지 하나는 양쪽 둑의 도로를 못 이어 그대로 직선). 이미 도로를 따라가던 4곳은 변화가 없다. **11-21 에 물 건너는 문턱을 2.0배로 올리자** 그 4곳이 달라졌다 —
  상암~염창 4.42km(가양대교로 돌아 8.18km, 1.85배)는 통째로 새 다리였던 것이 **도로 8.18km** 로, 잠실(1.66배)은 혼합이던 것이 전부 도로 7.62km 로 바뀌었다. 3.02배(일산 쪽)·
  도로로 못 이은 곳은 그대로다. 한강 다리까지 먼 곳(방화~가양 사이)에서는 육지가
  도로가 되는 대신 새 다리 한 토막이 남는다 — 그 다리를 놓을 수 있는지는 이 판정이 보지 않는다(가정값).
  **둑 점을 큰길로 옮기는 `roads.snap` 은 건너편으로 옮겨지기도 한다 — 그래도 가드를 안 넣었다**(11-21 측정, 진짜 도로망·물 파일, 서울·경기 짧은 선 6천 개 중 물을 건너는 1,546개): 둑 점을
  옮긴 2,712번 중 400번(15%)이 물을 가로질렀다. 틀린 노선이 되는지 따로 봤다 — 새 도로 조각에 물이 전혀 없는 혼합 22개(혼합 208개의 10%)를 풀어 보니 전부 폭 30~90m 개울을 도로의 기존 다리가
  건너고 시작점 쪽에 도로가 없어 육지만 새로 놓는 정상 결과였다(건너편으로 옮겨져 기존 다리를 쓰는 길이 오히려 합리적이다). 가드(옮긴 선이 물을 가로지르면 그 육지는 도로로 못 잇는다고 보기)는
  그런 결과를 지우므로 넣지 않았다. 실제 결함은 문구였다 — 물이 없는 새 도로에도 「물 위와…」 라 적혔다. 새 도로의 **땅 위** 공사비는 KDI 도로부문에 km 표준이 없어(토공은 물량 × 단가로 쌓는다, PDF
  55~58쪽) 판정은 길이로만 하고 비용엔 「모름(미포함)」 경고. 새 도로가 **물을 건너는 몫**은 표 Ⅲ-14 일반국도 교량 편도 2차로 PSC Box(아래)
- **숫자** — 그 행의 연장 = 도로 경로 + 새 도로(+ 역이 비킨 몫), 역은 그 선 위에, 소요시간·편익도 그 길이로. 산 구간 터널비는 새 도로 구간에만(기존
  도로는 이미 뚫려 있다). 광역급행은 철도라 새 도로 다리값·땅 위 경고가 없다. `scenario_result.road_cost`(0 = 새 다리 없음, NULL = 철도·도로망 없음)·
  `route_line`(R 도로 / N 새 도로 구간, 20m 오차로 줄인 좌표). 기존 DB 는 `ALTER TABLE scenario_result ADD COLUMN road_cost BIGINT NULL AFTER tunnel_cost,
  ADD COLUMN route_line MEDIUMTEXT NULL AFTER road_cost`
- **도로망 파일이 없으면** 트램·BRT·광역급행도 예전처럼 그린 직선으로 센다(「도로 없음」 이 아니다)
- **새 구간이 실제로 있는 노선으로 확인(11-15)** — 팔당(37.525,127.28 → 37.548,127.34, 5.9km): 트램이 새 도로 1구간, 팔당호 1.1km·강 0.8km 위 → 다리값 845억, 새 구간 터널 0.5km → 147억,
  팔당 상수원보호구역 경고. 카드는 새 구간 기준(「새로 놓는 구간의 물 위」·「새로 놓는 구간에 산 구간 1곳」), 광역급행은 「교량 할증은 넣지 않아…」, 지하철 고가(그린 직선)는 예전 그대로.
- **바다 위 새 도로도 다리값을 매긴다(11-18, `Coastline`)** — 전에는 물 파일(`water_bodies.geojson`)이 호수·강뿐이라 인천 송도~영종(그때는 도로 문턱이 1.5배라 도로로 돌면 33km(1.83배)여서
  직선 새 도로 17.3km — **인천대교는 자동차전용도로라 도로망에 없고, 영종대교는 하층 일반도로(`청라하늘대로`, `highway=trunk` `motorroad=no`, 편도 3차로)만 있다**(11-22 원본 태그로 확인 — 처음엔 둘 다 빠진다고 적었다))이 「땅 위 공사비 모름」 으로만 적히고 바다 위 다리값은 0 이었다. **지형 타일(DEM)로는 바다를 못 가른다**(11-15 측정, research-log 「바다를 DEM 으로 가를 수 없다」) —
  연안 바다가 수심이 아니라 거의 정확히 0m 이고 간척지·매립지도 0~1m 라, 「≤0m = 바다」 로 보면 송도 신도시 땅이 2.9km 중 2.35km, 새만금 간척지가 9.7km 중 9.05km 바다로 잡힌다.
  그래서 OSM 해안선(`natural=coastline`, `etl/osm_coast.py`)으로 가른다 — **점에서 서쪽 바다(경도 123°)로 쏜 선이 해안선과 만나는 횟수의 짝홀**(홀수 육지·짝수 바다). 가까운 선분의 방향으로
  가르면 오목한 만에서 틀려서(`CoastlineTest` 의 C 자 섬) 쓰지 않았다. **반개구간으로 센다** — 닫힌 구간으로 세면 해안선 꼭짓점을 두 번 세어 마름모 섬 안의 점이 바다가 된다(처음 테스트는
  사각형 섬만 써서 이 실수를 못 잡았다 — 가드를 꺼 보고 알았다). 자료 범위(북위 33~38.7°)·파일 없음은 「바다 아님」(꺼짐)이다.
  **짝홀의 전제 — 점에서 서쪽으로 쏜 선이 지나는 칸은 모두 받아야 한다**(11-21 코드 점검에서 걸림). 섬 칸이 빠지면 그 섬 안만 틀리지만 해안 칸이 빠지면 그 위도의 내륙 전체가
  바다가 된다 — 북위 38° 칸을 127·128° 만 받아 북한 서해안(124~126°)이 없었고, 철원·화천·인제·속초 시내가 「바다」 로 읽혔다(파일이 생기면 강원 북부 새 도로에 바다 다리값이 붙을 뻔했다).
  받을 칸은 육지 칸(`osm_water.TILES`)마다 그 위도의 124° 부터 끌어낸다(`osm_coast.RAY_TILES` — 손으로 적은 목록이 빠뜨렸다).
  **연결**: `CostCalculator.roadPart` 가 새 구간의 바다 길이를 물 길이에 더해 같은 451억/km 로 `road_cost` 를 매기고(**하한** — 지침은 바다 다리가 더 든다고 한다), 땅 위 「모름」 길이에서 뺀다.
  `/api/route/detour` 의 `waterKm` 에도 이름 「바다」·종류 `sea` 구간으로 들어가 패널의 「물 위」 줄과 파란 토막이 그대로 쓴다(프론트 무변경).
  **이중 계산 금지** — 강 하구에서 물 파일과 겹치는 토막은 강으로만 센다(`WaterBodies.contains`). 이걸 `within()` 으로 만들었다가 **`within` 이 호수만 돌려줘** 강이 빠져 하구 다리값이 두 배가 됐다(테스트가 잡았다).
  **실측**(받은 칸 12개, 인천·영종·송도·시화): 확인 가능한 열 곳을 모두 맞혔다 — DEM 이 바다로 읽던 송도 매립지·안산 간척지는 육지, 인천대교 해역·용유도 앞바다는 바다.
  **해안선 파일(`data/build/coastline.csv.gz`, 976KB)은 저장소에 있다**(11-22 전국 수집 완료 — way 6,050개 · 선분 171,999개, 읽기 0.23초 · 힙 +6.9MB · 판정 1.9µs). 없으면 꺼진다 — 이전과 같은 값이다.
  **전국 검증**(11-22) — ① 손으로 고른 33지점(도심·한강 위·매립지·간척지·38° 위 내륙(철원·화천·인제·속초)·제주·울릉도·거제·먼바다)이 모두 맞다. 신안 섬 안(34.7,126.2)은 닫힌 해안선 159점 안이라 「육지」 가 맞다(처음 내 기대가 틀렸다).
  ② **독립 검증** — 사람이 사는 집계구 10만 4천 개(`census_population.csv`)는 전부 육지여야 한다: **309개(0.295%)만 「바다」** 로 읽혔다. 시도별로는 11·22·24·25·29·33 이 0, 전남 108(2.9%)·제주 31(2.2%)·경남 56·인천 23·부산 14 등 섬·해안이 많은 곳에 몰린다.
  틀린 칸은 **전부 가장 가까운 해안선에서 1km 이내**(표본 48개: 중앙값 70m, 최대 0.97km)다 — 해안선 조각이 빠진 자료 결함이라면 몇 km 안쪽에서도 틀렸을 것이다. 해안 가장자리 집계구의 중심점이 물가에 걸치는 경계 오차(간척지·갯벌·섬 가장자리, 단순화 오차)로 보고 허용한다.
  **갯벌**은 가르지 못했다 — 강화 남단(37.56,126.48)은 「바다」, 고창(35.48,126.48)은 해안선에서 0.8km 안쪽 「육지」 로 읽혀 OSM 이 조간대를 어디에 그렸는지 현장 기준 없이는 맞다 틀리다를 못 가른다(참고로만 둔다).
  **실서버 확인**(재빌드 jar, 로그 「해안선 — way 6050개 · 선분 171999개」) — 목포~제주 트램: 직선이 바다 115.8km 를 건너 새 도로 135.7km 조각이 되고 도로(다리)비가 5조 3,893억(= 바다 115.8 + 호수 3.7km × 451억/km, 정확히 맞는다), 지도에 바다 위 파란 선이 제주까지 그려진다. 김포~강화는 바다 1.4km + 강 0.1km 로 따로 나와 하구 이중 계산이 없다.
  **송도~영종은 이제 바다 다리값이 안 켜진다** — 도로 문턱이 2.0배가 되자(11-22) 직선 18.1km 에 기존 도로 33.1km(1.83배)로 돌아가는 길이 새 바다 다리 10.8km 보다 우선해 도로 한 조각이 된다. 일관된 결정이지만 이 기능의 출발점이던 사례가 이제는 안 닿는다는 점을 적어 둔다. 파일은 Overpass 본진이 서울·경기 연안 칸에서 502 를 거듭 내 **받는 데 몇 시간이 걸릴 수 있다**(칸마다 캐시라 이어 받는다)
- **화면에서 찾은 두 가지(11-12)** — ① 처음엔 선만 도로를 따랐고 **역은 예전처럼 인구 쪽으로 최대 0.5km 비키거나 다른 큰길로 붙어** 선 밖에 떠
  있었다(화곡1동·화곡2동) → 도로 위 노선은 역을 선 위에 둔다(`planWithDetour(…, onRoute=true)`). ② 찍은 끝점이 건물 안이면 그 점에서 가장 가까운
  교차점(최대 1km)까지 직선이 뚫렸다 → 끝점·경유점을 가까운 큰길 위로 옮겨(`RoadNetwork.snap`) 시작한다. 같은 노선(강서 오정동~신도림): 트램 13.5km,
  BRT 고급형 B/C 3.4 · 광역급행 고가 4.5, 역은 선에서 14m 안
- **서버를 다시 띄워야 반영된다** — 코드를 고치고 도로망 파일을 만든 뒤 서버를 안 띄웠더니 사용자 화면이 계속 직선이었다. 저장된 옛 결과에는 `route_line` 이
  없다(다시 계산해야 도로를 따라간다 — `CHANGED_AT` 알림이 뜬다)

### 호수·저수지 우회 제안 (`WaterDetour`, 2026-10-26)

그린 선이 저수지 한가운데를 지나도 아무 말이 없었다(역은 반경 500m 에 사람이 없으면 안 놓지만
**선은 물 위를 그대로 지났다**). 이제 점이 바뀔 때마다 `/api/route/detour` 에 묻고, 물을 지나면
패널에 "○○저수지 위를 지납니다" 와 **「돌아가는 선형으로 바꾸기」** 를 띄운다. **누를 때만**
점이 바뀐다 — 저장·계산은 평소처럼 사용자가 한다.

**지하는 우회를 제안하지 않는다(2026-10-29).** 지하철은 호수 밑을 그대로 지나면 된다 — 돌아가라고
하면 틀린 안내다. 화면이 구조(`structure`)를 함께 보내고 `UNDERGROUND` 면 서버가 그린 선 그대로,
지나는 호수 목록을 비워 돌려준다. 고가·지상은 물 위를 지나려면 다리가 필요하므로 지금처럼 제안한다.
**구조가 비어 오면 지상 쪽으로 본다** — 예전 요청이 조용히 제안을 잃지 않게(테스트가 고정한다).
판정을 화면이 아니라 서버 한 곳에 둔 것은 추천 규칙과 같은 이유다(부르는 곳마다 같은 답).
- 화면의 구조 기본값이 **지하**라, 구조를 고가·지상으로 바꾸기 전에는 우회 제안이 안 뜬다.
  대신 「물 아래 구간 … 지하라 물 밑으로 지나므로 우회를 제안하지 않습니다」 를 적어 왜 안 뜨는지
  알린다. 구조를 바꾸면 다시 묻는다(답을 맞춰 보는 `key` 에도 구조를 넣었다 — 안 넣으면 지하로
  바꾼 직후 고가 때 받은 제안이 남는다)
- **지하에서 물을 지나는 몫은 다리가 아니라 하저터널이다** — 이것도 할증이 없다(위 「못 하는 것」)

- **자료** `etl/osm_water.py` 가 OSM Overpass 에서 `natural=water` + `water=lake|reservoir`
  를 받아 `data/build/water_bodies.geojson` 에 둔다. **넓이 1km² 이상**만, **바깥 경계만**(섬은
  빼고 호수를 통째로 막는다). 넓이·단순화는 UTM-K(EPSG:5179) 미터 좌표로 하고, 경계는 **25m**
  오차 안에서 줄인다 — 소양호 경계점이 27,989개였다
- **강은 넣지 않았다.** 한강·낙동강은 돌아갈 수 없고 건너야 한다. 그래서 **돌아간 길이 강을
  건널 수 있다** — 의암호는 강을 막은 호수라 위쪽이 소양강인데, 의암호를 가로지르는 10.5km
  노선을 돌리면 호수 끝 바로 위에서 강을 건너 14.5km 가 됐다. 넓은 호수보다 좁은 강목에서 건너는
  셈이라 자연스럽지만 "물을 완전히 피했다" 로 읽히지 않게 화면에 적는다
- **방법** 물을 지나는 구간 둘레를 100m 격자로 나눠 물 칸을 막고(스캔라인으로 칠한다 — 칸마다
  점-다각형 판정을 하면 소양호 × 36만 칸이라 느리다) A* 로 가장 짧은 길을 찾은 뒤, 막힌 칸을
  지나지 않는 한 멀리 곧게 이어 경유점 몇 개로 줄인다. 둘레의 **다른 호수도 함께 막는다** —
  지나는 호수만 막으면 돌아간 길이 옆 호수로 들어간다
- **물가 한 칸(100m)을 더 막는다.** 빼면 마름모꼴 호수에서 곧게 이은 선이 모서리를 스치고 경유점이
  물가 **7m** 에 붙었다(있으면 135m 이상). 테스트(`물가에서_떨어진다`)가 그 경우를 고정한다
- **경계선이 지나는 칸도 막는다(2026-10-29).** 스캔라인은 「칸 가운데가 물 안」 인 칸만 칠해서,
  한 칸보다 가는 물줄기·뾰족한 끝은 어느 칸 가운데에도 안 걸려 **통째로 빠졌다** — 그러면 위의
  한 칸 여유도 시작할 칸이 없다. 신갈저수지를 남북으로 가로지르면 우회 선이 동쪽 끝을 **2.5m**
  차이로 스쳐, 「돌아가는 선형으로 바꾸기」 를 눌러도 「저수지 위를 지납니다」 가 남았다(4m 라 물 위
  구간 줄은 50m 기준에 걸려 사라지는데 판정은 남는다 — 화면이 서로 다른 말을 했다). 손으로 만든
  네모·마름모 호수는 꼭짓점이 굵어 몰랐고 **실제 파일**로 고정했다(`돌아간_선은_다시_걸리지_않는다`).
  - 처음 세운 가설은 「끝점 a·b 가 칸 가운데에서 비켜 있다」 였다. 곧게 펼 때 실제 경계선으로도
    검사하게 했는데 **고쳐지지 않았다** — 문제 구간이 바로 옆 칸으로 가는 한 걸음이라 그 검사를
    안 탔다. 경로를 찍어 보고서야 뾰족한 끝이 보였다
  - 무작위 노선 1,600개(신갈·왕송·광교·일산호수 둘레)로 견줬다 — 칸 막기를 끄면 우회 398건 중
    **24건**이 물에 닿고, 켜면 390건 중 **0건**. 실제 경계선 검사는 켜도 꺼도 0건이라 **뺐다**
    (테스트가 지키지 못하는 코드를 남기지 않는다)
- **돌아가는 길이 원래 구간의 1.5배를 넘으면 제안하지 않는다** — "건너는 편이 낫습니다" 로
  알린다. 소양호처럼 가지가 길게 뻗은 저수지를 끝까지 돌면 수십 km 를 더하는데 실제 철도는 그런
  곳을 다리로 건넌다. **1.5배는 가정값이다** — 교량 단가 자료가 없어(위 「못 하는 것」) 다리와
  우회를 견줄 수 없다. 화면에도 가정값이라고 적는다
- **전국 120개**(1km² 이상, 645KB) — 새만금호 197.9 · 충주호 51.6 · 시화호 50.8 · 대청호 50.5 ·
  소양호 47.3km² … 임남저수지(금강산댐, 북한)도 칸에 걸려 들어왔지만 노선을 그릴 곳이 아니라 둔다
- **수도권에서 확인** — 신갈저수지를 가로지르는 7.1km 는 남쪽 끝(기흥역 부근)으로 돌아 7.9km
  (+0.8km, 경유점 2개). 시화호를 가로지르는 12km 는 돌아가면 2.2배라 **건너는 편**으로 둔다 —
  실제로도 시화방조제가 건너간다
- 저장할 수 있는 경유점은 50개라, 우회점을 끼워 넣다 넘으면 제안하지 않는다

### 물 위 구간 길이 (`WaterBodies.onWater`, 2026-10-26)

**교량 할증을 못 넣은 몫이 얼마나 되는지 드러낸다.** `cost_standard` 는 수단 × 구조뿐이라
한강을 건너는 1km 와 평지 1km 가 같은 값이다 — 할증은 단가 자료가 없어 여전히 넣지 않는다.
대신 패널에 "물 위 구간 한강 1.2km — 교량 할증은 넣지 않아 건설비가 그만큼 낮게 잡혔을 수
있습니다" 를 적는다. 우회 API(`/api/route/detour`)가 `waterKm` 으로 함께 준다.

- **강도 받는다** — `natural=water`+`water=river` 와 옛 표기 `waterway=riverbank`(`osm_water.py`
  의 `KINDS['river']`). 강은 여러 조각으로 그려져 **0.05km² 조각까지** 남기고, 강폭(수백 m)을 재야
  해서 **10m** 오차로 줄인다(호수는 25m)
- **강은 우회하지 않는다** — 우회 판정(`crossing`)에도, 우회 길을 막는 데(`within`)에도 넣지 않는다.
  막으면 강으로 이어진 호수는 돌아갈 길이 없어진다(테스트 `강은_막지_않는다`)
- **수면이 면으로 그려진 강만 잰다.** 작은 강은 OSM 에 중심선(선)으로만 있어 폭이 없다 — 그런 강을
  건너는 노선은 "물 위 구간" 이 안 뜬다. **"안 건넌다" 가 아니라 "못 잰다"** 다
- 재는 법 — 구간을 경계와 만나는 점으로 나누고, 조각의 가운데 점이 물 안이면 그 조각을 센다.
  이름별로 더한다(같은 강을 두 번 건너면 합). 50m 미만 조각은 화면에서 뺀다(물가를 스치는 잡음)
- **받은 결과 (10-26)** — 호수 120개 + 강 조각 **1,002개**, 파일 2.3MB. 서울시청~강남역이 「한강
  0.8km」(화면에서 양쪽 물가와 맞음), 서울~부산 3점 노선도 0.02초 안에 답한다. 강 넓이의 **48%** 는
  이름이 없어 「이름 없는 강」 으로 뜬다. **OSM 이 강으로 적은 호수가 둘** — 팔당호(한강 댐이라
  건너는 게 맞다)·대호지(방조제 담수호, 애매하다). 손으로 고치지 않았다 — 대호지는 우회 제안이
  안 뜨고 물 위 길이만 뜬다
- **물 위 토막의 양 끝(`pieces`)도 준다** — 지도가 그 토막만 파랗게 덧그린다. 끝점은 위의 "만나는
  점" 그대로라 물가에서 정확히 끊긴다(신갈저수지로 화면 확인). 토막을 안 넣으면 `물_위_토막`·
  `이름별로_더한다` 만 깨진다(가드를 꺼 봤다)
- **Overpass 에서 또 데였다** — User-Agent 가 없으면 **406**, 본진은 502·504·시간 초과가 잦고
  **바다뿐인 칸도 몇 분씩 붙잡는다.** 그래서 육지가 있는 18칸만 칸마다 캐시하며 묻고,
  `--from-cache` 로 받은 칸만으로도 파일을 만들 수 있다(빠진 칸을 크게 알린다)

① 역수만큼 노선을 균등 분할해 이상 위치를 잡고 ② 그 주변 창에서 **반경 500m 인구가 가장 많은
지점**으로 옮긴다. 균등 분할만 하면 역이 논밭 한가운데 놓인다. 창은 역간격의 ±35%이고 앞 역과
최소 50% 간격을 지킨다 — 풀면 역이 한 덩어리로 뭉친다. 실제 간격은 0.6~1.9km로 퍼진다.
인구는 **고정 반경 안의 합**으로 센다(집계구 크기가 제각각이라 밀도 비교가 되게).

- **역수는 `연장 ÷ 역간격`이다.** 역간격 자체가 `연장÷역수`로 측정됐으므로 같은 정의를 뒤집어
  쓴다. `+1`(간격 수 기준) 공식도 시험했으나 실제 역수를 더 잘 맞히지 못했다
  (중전철 평균오차 9.55 vs 10.07). 배치 간격은 `연장÷(역수-1)`이라 명목보다 조금 넓다
- **역명은 집계구의 행정동명**이다. 경계 응답(`adm_nm`)에 이미 있어 추가 호출 없이
  `census_population.csv`에 담았다. 같은 동에 역이 둘이면 뒤에 번호를 붙인다
- 예상 이용객은 노선 전체 이용객을 **역세권 인구 비율로 나눈** 근사다 (역별 회귀가 아니다)
- **종점은 사용자가 찍은 점에 고정**한다. 출발·도착은 설계 의도라 옮기지 않는다
- 역 배치는 역간격이 같으면 같으므로 **수단당 한 번만 계산**해 지하·고가가 함께 쓴다
- **인구 점수는 계단 함수다.** 봉우리가 이미 반경에 들어와 있으면 더 다가가도 점수가 같고,
  그때는 이상 위치에 머문다. 창 안을 0.1km 간격으로 훑되 **이상 위치를 먼저 재 둔다** —
  그러지 않으면 격자가 이상 위치를 비껴가 인구가 없는 구간에서도 역이 수십 m 밀린다(테스트 고정)
- 한계: 환승·지형·용지를 보지 않는다. 인구 자료가 없으면 균등 분할 그대로다.
  업무지구 종점(시청 등)은 거주 인구가 적어 이용객이 낮게 배분된다

### 산 구간 — 뚫는 안과 돌아가는 안 (`MountainProfile`·`MountainDetour`, 2026-11-05)

설계: `docs/superpowers/specs/2026-11-05-mountain-detour-design.md`. 서울~부산을 그리면 직선이 소백산맥을
그대로 가로질렀다 — 이제 **35‰ 보다 가파른 곳**을 찾아 두 안을 나란히 보여 준다. 바꾸는 것은 사용자다.

**11-09 부터 뚫는 비용은 비교표 건설비에 든다**(사용자 요청). 처음엔 패널에만 제안으로 적어, 산을 많이 지나는 노선의 표 건설비가 터널 없이
나왔다(서울~부산 광역급행 고가 13.8조 — 소백산맥 148km 를 땅 위로 지나는 값). 표는 **그린 노선 그대로**이므로 산을 지나면 뚫어야 한다 —
`TunnelKm`(`MountainTunnelKm` 이 산 구간 캐시 `MountainPlans` 를 같이 쓴다)이 터널 길이를 주고 `CostCalculator.tunnelCost` 가 행마다 더한다.
`scenario_result.tunnel_cost` 에 따로 둬 비용 구성 차트가 「산 구간 터널」 몫을 그린다(0 이면 막대 없음). 지형 판정이 실패하면 「모름」(NULL)이지
0 이 아니다. 패널 문구는 「뚫는 비용 N억 — 비교표 건설비에 들어 있습니다」(추가분이 0 이면 「산악 터널이 고가와 km당 공사비가 비슷해 더할 비용이
없습니다」), 돌아가는 안은 **표와의 차액**이다.

**같은 날 단가를 KDI 표준공사비로 바꿨다**(사용자 결정, research-log 「산악 터널 단가」). 처음엔 우리 「지하 − 고가」 km단가 차(도심 지하철 사업 —
개착이 섞였다)로 매겨 서울~부산 광역급행 고가에 +2.9조(0.69 → 0.57)가 붙었고, 트램·BRT 는 「모름」 이라 빠져 서울~부산 BRT 고급형(0.67)이
광역급행(0.57)보다 높게 읽혔다. KDI 2021 세부지침(2019 토목공사비)으로는 **산악 NATM 터널이 철도 교량(고가)과 km당 비슷하거나 더 싸다** —
`MountainCost.extraPerKm` = (터널 − 기준 구조) × 1.1686(S4 2019 GDP 디플레이터 배수, 테스트가 대조한다), 음수면 0:
중량 복선 319 − 복선 교량 직접기초 317 → +2.3 · 경량전철 265.6 − 교량 190.8 → +87.4 · 복선전철 192 − 317 → 0 · 트램 265.6 − 노면전차 13.4 → +294.7
억원/km. **BRT 는 도로 기울기로 따로 잰다** — 도로는 철도보다 가파르게 오른다(도로규칙 제25조 간선도로 산지 80km/h 7%, 설계속도는 가정값),
`MountainProfile.sections(…, ROAD_GRADE)` 로 잰 터널 km × (도로 2차로 터널 145.84 × 1.1686 − 그 행 km단가). 손익분기도 이 값에서 나와
**약 0.004 — 철도는 사실상 돌지 않는다**(산악 터널이 고가와 비슷하므로 도는 것이 늘 손해다). 11-12 부터 트램은 따로 따지고 공통 중앙값에서
빠져 약 0.002 다(아래 「돌 수 있어도 손해면 뚫는다」).
측정 — 서울~부산(철도 148.1km·도로 약 105km) 광역급행 고가 터널비 2.9조 → 0(B/C 0.69), BRT 고급형 +1.5조(0.67 → 0.26), 트램 +4.4조(0.03),
경전철 고가 +1.3조. 서울시청~잠실 광역급행 0 · 트램 +118억 · BRT +15억. 추천 셋 다 그대로.
기존 DB 는 `ALTER TABLE scenario_result ADD COLUMN tunnel_cost BIGINT NULL AFTER total_cost` 한 줄이 필요하다(새로 만들면 V2 에 있다).

- **35‰ 는 법령이다** — 도시철도건설규칙 제15조 ①(본선, 2025-08-08 시행), 경전철 제76조·노면전차 제86조는
  시·도지사가 달리 정할 수 있다. 철도의 건설기준에 관한 규정 제10조(국토교통부고시 제2025-244호): 여객전용선
  V≤400 35‰(연속 10km 평균 25‰ 이하 — **1차에서 판정하지 않는다**), 전기동차전용선 35‰. 우리 철도 수단 전부의
  상한이라 하나만 쓴다. 정거장 안 8‰·종곡선·기울기에서의 속도 저하는 뺐다
- **지형** — AWS Terrain Tiles(Terrarium, z11 ≈ 62m/픽셀), `etl/dem_tiles.py` 가 1,312장 · **35.6MB** 를 받는다
  (계획의 80MB 는 틀렸다 — 바다 타일은 한 색이라 작다). 받는 중 DNS 가 끊겨 64장이 빠졌다 — 다시 돌리면
  빈 칸만 받는다. 테스트는 저장소의 추풍령 타일 2장(1752/802·803)만 쓴다(CI 에 캐시가 없다).
  **타일이 없는 칸은 0m 가 아니라 「모름」** 이고, 모르는 칸에 닿는 터널은 판정하지 않는다
- **선로 높이** — 지면 아래로만 35‰ 를 지키는 선(하한 포락선, 터널 안)과 위로만 지키는 선(상한, 교량 안)을
  O(n) 로 구하고, 흐트러진 구간마다 **땅과 덜 어긋나는 쪽**을 고른다(산은 깎고 골짜기는 돋운다). 처음엔 하한만
  썼는데 깊은 골짜기 옆 고원 밑에 수백 m 가짜 터널이 생겼다. 「대칭 완화」 는 반복이 산 폭의 제곱이라 버렸다.
  교량 할증은 여전히 없다
- **함정 ① 건물이 산이 된다** — SRTM 은 맨땅이 아니라 **건물·숲 꼭대기**까지 잰 표면이다. 화면을 열어 보니
  강남~잠실 평지에 「산 구간 1곳」 이 떴다 — 역삼역 빌딩 숲이 45→80→47m(폭 0.2km)로 튀었다. 땅높이를
  **앞뒤 2칸(0.5km 창) 중앙값**으로 본다(판단값) — 폭 250m 보다 좁은 튐은 지우고 산은 남긴다. 서울~부산
  터널이 158 → 148km 로 줄었다. 테스트 `buildingSpike`
- **함정 ② 바다** — 수심이 음수로 나올 수 있다(단 서해·남해 연안은 거의 0m 이고 5m 보다 깊은 곳이 없었다 — 11-15). 0 으로 자르지 않으면 선로가 바다 밑으로 꺼져 해안 절벽이 터널로 잡히고,
  0 인 칸을 막지 않으면 해안 산을 **바다 위로** 돌아간다(테스트 `sea`·`notOverSea`)
- **덮개 20m(가정값)** — 그보다 얕으면 깎기로 본다. **0.5km 이하로 떨어진 토막은 합친다**(가정값) — 안 합치면
  산맥 하나가 0.1km 토막 수십 개가 된다. 터널 길이는 터널 표본만 센다(틈은 넣지 않는다)
- **돌아가는 안** — 산 구간 앞뒤 1km 를 붙인 창마다 100m 격자에서 **이웃 칸 사이 높이차가 35‰ 를 넘는 이동을
  막은** A*. 길은 골짜기·등고선을 따른다. **격자는 1.5배 타원만 본다** — 1.5배 이하 길은 두 끝을 초점으로 하는
  타원 안에만 있으니, 그 안에 길이 없으면 곧 「1.5배 안에 길이 없다」 다. 8방향 격자라 스위치백·나선은 없다.
  찾은 길을 `MountainProfile` 로 다시 재서 터널이 남으면 버린다(테스트 없는 안전망 — 격자가 굵어지는
  40km 넘는 창에서만 뜻이 있다). 호수는 막지 않는다 — 돌아간 길이 호수를 지나면 바꾼 뒤 호수 안내가 뜬다
- **비용** — 앱의 건설비는 (수단×구조) 직선식이라 **뚫기 = T × km당 추가분**, **돌아가기 =
  늘어난 km × km단가 + 못 돌아간 구간의 터널값**(설계서의 `exp(0.515·T/L)` 는 단가를 만든 회귀 안쪽 계수라
  쓰지 않았다). km당 추가분은 처음엔 「지하 − 그 행 km단가」(도심 대심도 표본의 외삽)였고 11-09 부터 KDI 산악 NATM
  표준공사비다(위). BRT 는 도로 기울기 7% 로 잰 터널을 쓴다
- **돌 수 있어도 손해면 뚫는다(`MountainCost.breakEven`, 11-06 사용자 요청)** — 처음엔 돌 수 있는 곳을 다 돌아서
  서울~부산 광역급행이 돌아가기 +2조 9,642억(+3.0분)으로 뚫기 +2조 9,176억보다 비싸고 느렸다. 터널 할증(중전철
  325억/km)이 고가 1km(550억)보다 싸서 **터널 1km 를 피하려 0.59km 넘게 돌면 손해**다. 돌면 시간은 늘 늘어나므로
  비용까지 더 들면 돌 이유가 없다 — 구간마다 늘어난 km ÷ 터널 km 를 (지하 − 구조) ÷ 구조 와 견준다. 철도 네 수단이
  0.588~0.591 로 거의 같아(같은 지하 계수에서 나왔다) **중앙값 하나로 선형을 정한다** — 수단을 고르기 전에도
  선이 하나다. 지금은 6곳 중 1곳만 돌아 **돌아가기 +2조 9,035억(+0.8분), 경유점 45 → 8개**다. 경유점 50개
  검사보다 먼저 견주므로 손해인 우회가 자리를 차지하지 않는다. (11-06 의 이야기다 — 11-09 KDI 단가로는 손익분기가
  약 0.004 라 철도는 사실상 돌지 않는다.) 시간 가치는 넣지 않았다(건설비만 견준다)
- **트램은 따로 따진다(`MountainCost.OWN_PLAN`, 11-12 사용자 요청)** — KDI 단가로 철도 중앙값이 약 0.004 가 되자 중앙값 하나로 정한 선형이
  트램에 이득인 우회까지 버렸다. 트램은 땅 위 단가(273억/km)가 싸 산악 터널 추가분(295억/km)이 km단가를 넘는다 — 손익분기 약 1.08.
  `/mountain` 이 트램 행만의 손익분기로 한 번 더 따져 `modePlans` 에 싣고, 화면은 비교표에서 트램 행을 고르면 지도 점선·문구·「바꾸기」 를
  모두 그 안으로 바꾼다(`mountainFor`). **공통 중앙값에서 트램을 뺀다** — 철도 행이 하나뿐이면 트램이 중앙값을 0.54 로 끌어올려 지하철까지
  손해인 우회를 받았다(테스트가 잡았다). 지금 공통값은 약 0.002(복선전철·급행 0, 지하철 0.004, 경전철 0.25 의 중앙값). **표 건설비는
  바뀌지 않는다** — 표는 그린 노선 그대로 뚫은 값이고, 돌아가는 안은 사용자가 바꿔야 다시 계산된다. 추풍령 1.8km(36.14°N 128.03→128.05°E):
  철도 「돌아가는 편이 비싸 뚫습니다」, 트램 「뚫는 비용 177억 / 돌아가면 건설비 −135억 · +0.4분」. 경전철 고가(약 0.25)도 공통값과
  다르지만 사용자가 정하지 않아 넣지 않았다. 계산이 산이 있는 노선마다 한 번 더 들지만 Redis 키에 손익분기가 들어 있어 따로 담긴다
- **속도** — 서울~부산 판정 0.5초 · 탐색 0.7~1.2초(jshell), API 3초(첫 호출). `/mountain` 도 1,000km 상한

### 기존 노선 활용 (`ExistingLineFinder`)

예타도 신설안만 보지 않고 기존 시설 활용안과 비교한다. 이미 전철이 다니는 길에 또 짓는 안이
비교표 1위로 올라오면 그 결과는 쓸모가 없다.

**좌표 출처가 둘이고 섞지 않는다.** 신뢰도와 갱신 주기가 달라 파일을 따로 두고 각각 읽는다
(`app.station-file`, `app.regional-station-file`). 한쪽이 없어도 나머지 범위는 그대로 동작한다.

| 범위 | 파일 | 출처 |
|---|---|---|
| 수도권 39개 노선·784역 | `station_master.csv` | 서울 열린데이터광장 (`seoul_ridership.py`) |
| 지방 10종·271역 | `regional_station.csv` | **OpenStreetMap** (`osm_regional_stations.py`) |

**OSM 은 집단 편집 자료라 그대로 믿지 않는다.** 국토교통부 운영현황 역수와 대조해
±2 를 넘게 어긋나는 노선은 **저장하지 않는다**. 실제로 첫 수집본은 10개 노선 전부가
미달이었다(99역 / 공식 271역) — 관계 멤버만 긁어서 생긴 일이고, 검증이 없었다면
반쪽짜리 좌표가 들어가 판정이 조용히 빗나갔을 것이다. 수집에서 밟은 함정 네 가지는
`etl/osm_regional_stations.py` 머리말에 적어 뒀다.

공공데이터포털·국가철도공단의 전국 역사 정보는 **서비스키가 필요**해 쓰지 못했다
(`.env` 의 `KAKAO_REST_KEY` 도 비어 있다). 키가 생기면 OSM 보다 그쪽이 낫다.

**Overpass 본진이 자주 504 를 낸다.** 슬롯이 비어 있어도 나므로 속도 제한이 아니라 질의
비용 문제다. 그래서 검증을 통과한 노선을 `data/cache/osm` 에 노선별로 캐싱하고, 다시
돌리면 못 받은 노선만 묻는다 — **한 번에 안 끝날 수 있고, 여러 번 돌려 캐시를 채우는 것이
정상 사용법이다.** 산출물(`regional_station.csv`)은 저장소에 넣는다. 받기만 하면 자료는
정확한데 받는 과정이 불안정해서, 쓰는 사람이 이 고생을 다시 할 이유가 없다.

판정은 **두 가지를 모두** 만족해야 한다 — 출발·도착이 그 노선 역에서 1km 안이고,
노선을 0.5km 간격으로 훑은 점의 **80% 이상**이 역 1km 안.
양 끝만 보면 전혀 다른 경로로 돌아가는 노선까지 걸리고, 겹침 비율만 보면 일부만 스치는 노선이
걸린다. **겹침 기준을 0.6 으로 뒀다가 테스트에서 걸렸다** — 반경 1km 역 무리가 양 끝에만
있어도 4km 노선의 67%가 덮인다. 실제로 겹치는 노선은 0.9를 넘어 0.8이면 둘을 가른다.

단정하지 않고 "활용 검토"까지만 안내한다 — 선형이 아니라 역 위치로만 재고, 지방 좌표는
집단 편집 자료에서 왔기 때문이다. 지방 신설 노선과 미개통 노선은 범위 밖이다
(운영현황 명단에 없으면 받지 않는다 — 없는 노선을 활용하라고 할 수는 없다). 버스는 범위 밖. 검증: 2호선 강남~잠실 위에 그리면 "기존 2호선 활용 검토(100%)",
시청~삼성~강남 대각선(여러 노선 가로지름)은 안내가 뜨지 않는다.

**수정 저장(`PUT`)이 늘 500 이었다.** `route_point` 에 `uk_point_seq(scenario_id, sequence)`
가 있는데 Hibernate 는 한 flush 에서 **INSERT 를 DELETE 보다 먼저** 보낸다 — 옛 0번 점이
남은 채 새 0번을 넣어 1062 가 났다. 재계산(`uk_result_mode`)과 같은 함정이라 같은 방법
(지우기 → `flush` → 넣기, `Scenario.clearPoints()`)으로 푼다. **자식 컬렉션을 통째로 바꾸고
그 자식에 유니크 키가 있으면 언제나 이 함정이다.**

### 도시 간 거리 — 기존 KTX (`IntercityRailFinder`)

`ExistingLineFinder` 는 역간격 1km 안팎의 도시철도 판정이라 KTX 에는 절대 안 걸린다.
인천~세종(120km)을 그리면 지하철 역 60개를 찍어 놓고 광명~오송 KTX 가 이미 있다는 말을
못 했다. 노선이 **35km**(`IntercityRailFinder.MIN_ROUTE_KM`, 판단값)를 넘으면
같은 KTX 노선의 두 역을 찾는다 — 출발·도착에서 각각 **20km 안**이고, 두 역 사이가 출발~도착
직선거리의 **절반 이상**. 인천~세종은 "기존 KTX 경부선·경전선·전라선·호남선 활용 검토 —
광명역(출발에서 16km) ~ 오송역(도착에서 16km)". 도시철도 안내가 걸리면 그쪽이 우선이다.

**기존 수단은 비교표의 한 줄이다 (`ExistingOptions`).** 전에는 이 둘의 결과가 **표 위
경고 문구**로만 떠 있었다. 서울~부산(340km)을 그려 보면 그게 왜 모자란지 바로 보인다 —
추천이 **340km BRT 고급형(B/C 7.83)** 이고 그 아래로 트램 396역·지하철 42조가 늘어서는데,
정작 **이미 KTX 가 있고 추가 건설비가 0** 이라는 가장 중요한 비교 대상만 표 밖에 있었다.
**비교는 표에서 일어난다.** `tfoot` 의 참조 행으로 붙이고, 시나리오 비교 화면에는
「이미 있는 수단」 행으로 넣는다.

- **`scenario_result` 에는 넣지 않는다.** `structure_type` 이 `NOT NULL ENUM` 이라
  기존 KTX 에 지하/고가/지상 중 하나를 억지로 붙여야 하고, 건설비 0 이라 수요를 못 구한
  노선에서는 그 행이 **"가장 싼 안"으로 강조**된다. 정렬·행 클릭(정차역 그리기)에도
  끼어든다 — 계산 결과가 아닌 것을 계산 결과 표에 넣으면 생기는 일이다
- **저장하지 않고 응답할 때마다 다시 찾는다.** 구조를 컬럼으로 늘리려면 스키마를 고쳐야
  하고 그러면 `down -v` 가 필요해 **가입 계정과 시나리오가 사라진다.** 판정은 노선 좌표와
  역 좌표 CSV 만으로 정해지는 순수 함수이고 역이 1,124개뿐이라 매번 찾는 편이 싸다.
  `scenario.existing_line`(VARCHAR 150)은 계산 시점 기록으로 그대로 남긴다
- **계산 전에도 나온다** — 저장하자마자 "이미 KTX 가 있다"가 보여야 한다. 계산을 눌러야
  알게 되면 그 전에 이미 수단을 고르고 있다
- **소요시간 칸에는 「빠른 계통의 중앙값」 하나를 넣는다.** 좁은 칸이라 네 숫자를 넣으면
  아무도 안 읽는다. 열차마다 갈리는 폭은 **표 아래 설명 줄**이 받는다 —
  "44편 143~176분(중앙 164분) · 경로가 다른 11편 180~205분(중앙 198분)"
  (`ExistingOptions.spread`). **단위는 표와 같이 분이다** — 칸이 `164분` 인데 설명이
  `2시간 23분~2시간 56분` 이면 읽는 사람이 둘을 잇지 못한다.
  **계통이 둘일 때만 갈라 적는다**(양쪽 3편 이상 + 시간 범위 안 겹침). 한 열차의 시각을
  "KTX 소요시간"으로 적으면 출처만 "공표값"이 되고 기준은 뒤섞인다 — 세종 S-BRT 의
  35km/h 를 쓰지 않은 것과 같은 이유다. 받는 쪽 이야기는 아래 「소요시간은 …」 참고
- **모르는 구간은 0 이 아니라 빈 칸이다.** 직통 KTX 가 없거나 역 이름을 못 맞춘 구간은
  `null` 로 와서 화면이 **빈 칸과 그 이유**를 적는다. `KtxTravelTime.fastestMedian` 이
  `Integer` 를 돌려주는 것이 그래서다 — `int` 면 0 이 되고 화면에 "0분" 이 뜬다
- **B/C 도 비운다.** 이미 지어진 시설에 B/C 를 매기는 것은 신설안과 범주가 다르다
- **거의 같은 거리면 고속선 역을 고른다 (`HIGH_SPEED_SLACK_KM = 2.0`).** 전에는
  서울시청~부산시청의 종점이 **부산역이 아니라 구포역**이었다 — 부산시청에서 구포
  7.67km, 부산역 7.73km 로 구포가 **60m** 더 가깝다. 틀린 답은 아니지만(구포도 KTX
  정차역이다) 좌표가 OSM 에서 와서 **편집 한 번에 답이 뒤집힌다.**
  가장 가까운 역보다 2km 안에 고속선 역이 있으면 그쪽을 쓴다
  - **"무조건 고속선" 이면 안 된다 — 고치기 전보다 나빠진다.** 서울역은 선로 계통이
    `경부선`(재래선)이고 광명역이 `경부고속` 이라, 여유를 없애면 서울시청에서
    **1.5km 떨어진 서울역을 두고 17km 떨어진 광명역**을 안내한다. "가까움" 을 이기지
    않는 **동점 처리**로만 쓴다 (테스트 둘이 양쪽을 다 막는다 — 여유를 없애면
    두 개가 깨진다)
  - 2km 는 판단값이다. 막으려는 것은 정확도가 아니라 **좌표 잡음이 답을 정하는 것**이다
  - 확인: 서울~부산 `부산역` / 서울~광주 `광주송정역` / 서울~대구 `동대구역` /
    인천~세종 `광명~오송`(그대로)
- **소요시간은 이 자료가 아니라 TAGO 「열차정보」(15098552)로 받았다.** 처음에는
  「열차운행정보」(15125762)가 필요하다고 적어 뒀는데, 그쪽은 **열차 하나의 전 구간
  시각표**라 구간마다 열차를 추려야 한다. TAGO 의 `GetStrtpntAlocFndTrainInfo` 는
  **출발·도착역을 주면 그 구간 열차를 전부** 주므로 구간 집계에 바로 맞다.
  받아 둔 결과는 `data/build/ktx_travel_time.csv`(`etl/korail_travel_time.py`).
  - **등급으로 거르지 말 것.** `trainGradeCode=00` 으로 받았더니 **강릉선이 통째로
    빠졌다** — 서울~진부는 전부 KTX-이음이다. `GetVhcleKndList` 에 KTX 계열이 여섯
    있다(00 KTX · 07·0A·10 산천 · 16 이음 · 19 청룡). 등급을 걸지 않고 받아
    **이름이 `KTX` 로 시작하는지**로 거른다 — 계열이 늘어도 코드를 안 고친다.
    SRT 는 운영사가 다르고 출발역이 수서라 세지 않는다
  - **역 이름이 두 자료에서 다르다.** 우리 역 파일은 공식 이름 `울산(통도사)` 를,
    TAGO 는 `울산` 을 쓴다. **정확한 이름을 먼저** 보고, 없을 때만 괄호를 벗긴다 —
    TAGO 는 `판교(경기)`/`판교(충남)` 처럼 괄호로 **다른 역을 가르기도** 해서
    먼저 벗기면 엉뚱한 구간의 시각표를 적게 된다. 벗긴 이름이 겹치면 둘 다 버린다

**노선-역은 공식, 좌표는 OSM 이다** (`etl/korail_ktx_stations.py` → `ktx_station.csv`).

- 노선-역 관계는 「한국철도공사_KTX 노선별 역정보」(공공데이터포털 15127571). **순번을 선형
  순서로 읽지 말 것** — 경부선이 `동대구 > 포항 > 경주 > 울산 > 경산` 처럼 지선을 오간다.
  "그 노선 열차가 서는 역의 모음"으로만 쓴다
- **공식 좌표(「역 위치 정보」 15127532)는 검증용이다 — 품질이 낮다.** 69역 중 51역은 OSM 과
  1km 안에서 맞지만 8역이 크게 어긋나고 **틀린 쪽은 공식 값이다**(`행신` 이 인천 앞바다,
  `구례구` 35.0·127.0 자리표시자, `마산`·`창원` 25km 서쪽). 10역은 공식 좌표가 없다.
  어긋남은 `coord_check` 열에 남는다
- **OSM 운행 계통(`route=train`)은 쓰지 않는다** — 정차역이 크게 빠져 있다(`경부선 KTX
  서울 → 부산` 에 4역). 선로 관계(`route=railway`)에는 경부선·호남선 같은 간선이 아예 없다
- OSM 에서 도시철도 역은 빼되 **`train=yes` 면 남긴다** — Korail `동대구`·`경산` 이 대경선
  때문에 `station=subway` 로 찍혀 있어 처음엔 통째로 빠졌다. 같은 이름이 여럿이면(`판교`
  성남·서천) 같은 노선의 다른 역에 가까운 쪽을 고른다
- **선로 계통은 세 번째 출처에서 온다** — 「KTX 정차역 최초 개통일」(15126723). 역마다
  `선명` 이 `경부고속`/`경부선` 으로 갈려 있어, 노선별 역정보만으로는 안 보이던 **고속선
  13역 / 재래선 56역** 구분이 생긴다. `official_line` 열에 남긴다
  - **`line_name` 을 이걸로 바꾸면 안 된다.** 서울은 `경부선`, 부산은 `경부고속` 이라
    묶음이 갈려 "서울~부산을 잇는 KTX" 를 못 찾게 된다. 타고 갈 수 있는지를 묻는
    데 맞는 묶음은 ①의 "그 노선 열차가 서는 역의 모음" 이다 (테스트가 감시한다)

    말 것** — `덕소` 한 곳만 소문자 `ktx` 라 처음에 "덕소에 KTX 가 없다" 고 잘못 봤다
  - **이 자료의 역명이 더 오래됐다**(2024-02). `신경주`·`물금역`·`판교` 로 적혀 있는데
    ①(2025-11)과 OSM 은 `경주`·`물금`·`판교(경기)` 다. **맞추기만 하고 이름은 ① 을 쓴다**

  - **대표역 선택에 쓴다** — 아래 「고속선 우선」 참고

## 화면

**화면에서만 쓰는 규칙은 `frontend/CLAUDE.md` 로 옮겼다** (선형 클릭, 패널 폭, `BcChart`,
인구밀도 3D 렌더링, `ComparePage`). 아래는 **백엔드와 공유하는 계약**이라 여기 둔다 —
화면 세션에서만 보이면 백엔드를 고칠 때 어긋난다.

**인구밀도 3D 범위 질의** `GET /api/reference/population?minLat..` 이 **화면 범위만** 준다.
집계구 5만 칸을 전부 보내면 수 MB 라, 객체가 아니라 `[위도, 경도, 인구]` 배열로 보낸다
(키 이름이 응답의 절반). 서울 범위 9,618칸 423KB, gzip 166KB (`server.compression`).

**관리자 기준값 CRUD(`/api/admin/**`, ROLE_ADMIN)** 편익 원단위(`benefit_parameter`)와 수단
기준값(`mode_capacity`)을 화면에서 고친다. 저장 즉시 다음 계산부터 적용된다.

- **근거(`source`)를 반드시 함께 받는다.** 비우면 400 이고 화면에서도 저장 버튼이 막힌다.
  이 프로젝트에서 값보다 중요한 것이 출처다 — 숫자만 바꾸면 어디서 온 값인지 모르게 된다
- 추가·삭제는 없다. 목록은 ETL·시드가 만들고, 행이 사라지면 계산이 바로 멈춘다
  (`Params` 가 없는 키에 예외). 바꿀 수 있는 건 값과 근거뿐이다
- **수단 기준값은 빈 칸이 "안 바꿈"이 아니라 "지움"이다** (`pphpd_min` 은 NULL 이 정상)
- `demand_*` 는 회귀 결과다. 손으로 고치면 모델과 어긋나므로 화면에 경고를 띄운다
- 하한 > 상한이면 400 으로 막는다
- **수단 기준값도 막는다**(11-04) — 역간격 0.2km 이상(`MIN_SPACING_KM`, 판단값: 10량 한 편성 약 200m),
  표정속도·권장 연장 0 초과, 수요 하한·수송능력 0 이상. 비우기(NULL)는 된다. 전에는 검사가 없어 역간격
  0·음수는 역 수가 조용히 「종점 2개」 가 되고, 0.0001 이면 10km 에 역 10만 개로 계산이 몇 분 걸렸다
- **원단위마다 허용 범위가 있다**(`AdminController.RANGES`, 11-04). 기간은 **반복 횟수**라 상한을 둔다 —
  분석 1~100년·공사 1~20년(상한은 판단값, 지침은 40년·5년). 할인율 0 이상 1 미만, 첨두율·단면 상한 0 초과
  1 이하, 운영비 비율 0 이상 1 미만, 시간가치·평일 보정·환산계수 분자 0 초과. **수요 회귀 계수는 두지
  않는다**(음수가 정상). 표의 이름이 S7·S6 에 다 있는지 테스트가 본다 — 오타면 그 범위가 조용히 안 걸린다
- **11-09 에 둘을 더했다** — `users_per_ridership` 0 초과 1 이하(환승유입은 하차의 일부라 1 을 못 넘는다, 0 이면 편익이 전부 0),
  `demand_brt_factor` 0 초과. 후자는 `demand_` 로 시작하지만 **계수가 아니라 이용객에 곱하는 배수**라 「수요 값은 범위를 두지 않는다」
  에서 뺐다 — 음수면 BRT 이용객이 음수다. 경전철 항(`demand_light_rail_coef`)은 로그 계수라 음수가 정상이다
- **`avg_trip_km`·`baseline_speed_kmh` 는 0 이하를 400 으로 막는다**(지금은 위 표의 일부).
  평균 통행거리가 0 이면 모든 편익이 0, 기준 속도가 0 이면 0 으로 나눈다 — 화면에는 오류
  없이 B/C 0.00 만 줄지어 찍힌다. 운영비 비율처럼 0 이 정상인 값이 있어 전부에 걸지 않는다
- **저장 실패는 실패한 행에 붙여 보여 준다.** 기준값이 25행(원단위 17 + 수단 8)이라 한 화면에
  안 들어간다. 맨 위에 띄우면 아래쪽 행을 저장했을 때 **화면 밖에 그려져 저장 버튼이 먹지 않는
  것처럼 보인다.** 불러오기 실패만 위에 띄운다
- **근거 칸이 값 칸보다 넓어야 한다.** 같은 폭을 주면 두 자리 숫자가 200px 를 쓰고 문장인
  근거가 잘린다. 값은 고정 폭, 남는 폭은 근거가 먹는다
- '저장함' 표시는 3초 뒤 지운다 — 계속 남으면 '지금 저장했다'는 말이 거짓이 된다

**낡은 결과 알림** 기준값을 고쳐도 **이미 계산해 둔 B/C 는 그대로 남는다** — 아무 말 없이
보여 주면 근거가 바뀐 숫자를 인용하게 된다. `scenario.calculated_at` 과 `mode_capacity`·
`benefit_parameter` 의 `updated_at` 최댓값(`GET /api/reference/updated-at`)을 견줘 기준값이 더
나중이면 "다시 계산해 주세요"를 띄운다. 비교 화면에서는 "다시 계산 필요".

- **계산 규칙이 바뀐 시각도 함께 본다** (`CalculationRules.CHANGED_AT`). 규칙은 DB 에 없어
  코드를 고쳐도 DB 시각이 움직이지 않는다 — 편익의 전환 전 수단에 기존 KTX 를 넣은 뒤에도
  전에 저장한 서울~부산이 아무 표시 없이 B/C 3.86 을 보여 줬다. **편익·비용·추천을 바꾸는
  코드를 고치면 이 시각을 올린다**(서버 시각, KST). 화면 문구만 바꾼 것은 올리지 않는다

### 로그인 횟수 제한 (`LoginThrottle`, 2026-11-06)

공개 서버에 올리기 전의 빈틈이었다 — 비밀번호를 틀려도 제한이 없었다. (이메일, 접속 주소)마다 15분에 10번(판단값), 넘으면 맞는
비밀번호도 429 다.

- **이메일만 묶지 않는다** — 남의 주소로 틀려 주는 것만으로 그 사람을 잠글 수 있다
- **nginx 는 `X-Forwarded-For` 를 덮어쓴다** — 처음 쓴 `$proxy_add_x_forwarded_for` 는 손님이 보낸 값 뒤에 덧붙이고, 백엔드는 맨 앞을
  읽어 헤더를 바꿔 가면 제한을 비켜 간다. 배포 묶음에서 헤더를 매번 바꿔 10번 틀려도 11번째가 429 였다
- **Redis 에는 해시만 담는다** — 이메일이 남지 않는다. Redis 가 죽으면 막지 않고(로그인 200) 경고만 남긴다. 그동안은 제한이 없다
- 소셜 로그인은 해당 없다. ~~가입(`/signup`)에는 제한이 없다~~ — 11-26 에 붙였다(아래)

### 서버 올리기 전 보안 점검 (2026-11-26)

이 PC 에 띄운 서버를 46가지로 두드렸다(토큰 위조·남의 시나리오·권한 상승·주입·입력 견고성·무차별 대입·`X-Forwarded-For` 위조·CORS·계산 폭주).
41가지는 막혔고 남은 넷 중 셋을 고쳤다. 남은 하나는 **HTTPS** — 도메인·인증서가 있어야 해 배포 때 한다(`docs/deploy.md`).

- **로그인 응답 시간으로 가입 여부가 드러났다** — 문구는 같았지만 없는 계정은 해시 비교를 건너뛰어 36ms, 있는 계정은 280ms 였다.
  서비스가 처음 만들어질 때 가짜 해시를 하나 만들어 두고, 없는 계정·소셜 계정(비밀번호 없음)도 그것과 한 번 비교한다 → **282ms 대 293ms**.
  테스트는 시간 대신 **비교 횟수**를 센다(시간은 흔들린다 — `LoginTimingTest`)
- **가입에 제한이 없었다** — 4.4초에 15번 가입됐다. bcrypt 가 가입마다 CPU 0.25초라 쏟아부으면 계정 쓰레기와 함께 CPU 가 바닥난다.
  접속 주소마다 한 시간에 10번(판단값, `SignupThrottle`) — 15번 중 10번 200, 나머지 429. **중복(409)도 센다** — 「이미 가입된 이메일」 로
  가입 여부를 캐는 속도를 막는다. **409 자체는 남는다** — 없애려면 이메일 인증(가입 메일)이 있어야 해 이번 범위 밖이다.
  검증 도구(`tools/verify`)는 실행마다 가입하므로 `SIGNUP_MAX_PER_HOUR=1000` 으로 연다. 시험 뒤엔 Redis 의 `railfeas:signup:*` 를
  지워야 같은 PC 의 개발 화면에서 한 시간 동안 가입이 안 막힌다
- **nginx 가 무방비였다** — 보안 헤더·속도 제한이 없어 인구 API·VWorld 프록시를 마음껏 두드릴 수 있었고 다른 사이트가 화면을 iframe 에 넣을 수 있었다.
  헤더(`X-Frame-Options DENY`·CSP·`nosniff`·`Referrer-Policy`·`Permissions-Policy`, `server_tokens off`)와 `limit_req`(API·로그인/가입·타일을
  따로)를 걸었다. 배포 이미지로 띄워 API 120번 몰아치기 → 63번 200·57번 429, 로그인 25번 → 11번 401·14번 429. 429 는 백엔드와 같은
  `{"message": ...}` 모양이라 화면이 문구를 띄운다. **CSP 는 화면으로 확인했다** — MapLibre 작업자가 `blob:` 이라 `worker-src blob:`, React 인라인 스타일 때문에
  `style-src 'unsafe-inline'`, OpenFreeMap 은 `img-src`·`connect-src`. 첫 화면이 비어 보였는데 타일 로딩 전이었다(위반 0건)
- **덤으로 찾은 것** — VWorld 키 없이 배포하면 nginx 가 `Referer ;` 로 설정 오류가 나 web 이 안 켜졌다(11-06 시험은 키가 있었다). 따옴표로 고쳤다

### Redis 캐시 (`MountainPlans`, 2026-11-06)

**제안서는 인구 집계를 담으라고 했지만 담지 않았다** — 메모리 색인이라 329km 도 1.5~5ms 로, Redis 왕복과 비슷하거나 더 걸린다.
실제로 느린 **산 구간**을 담는다. 서울~부산 첫 계산 1.47초 → 다시 0.08초, 구조만 바꿔도 0.05초(답이 구조와 무관해 키에 없다).

- **캐시는 보조다** — Redis 를 멈춰도 0.8초에 정상 응답이다. 예외는 `MountainPlans` 가 잡아 계산으로 넘어가고, 깨진 값도 다시
  계산한다. 연결은 처음 쓸 때 맺어 Redis 없이 서버가 뜬다(CI 도 그렇다). timeout 300ms
- **키** = 판정 버전 + 손익분기 + 좌표(소수 7자리) 해시. 손익분기가 키에 있어 단가를 고치면 자동으로 새 답이다. 비용 차이(`deltas`)는
  단가로 매번 계산해 담지 않는다. 지형은 받은 뒤 안 바뀐다. **판정 코드를 고치면 `PLAN_VERSION` 을 올린다** — 안 올리면 7일간 옛 답이 나온다
- 담는 값은 지형 판정뿐이라 개인정보가 없다. 비밀번호 없는 Redis 라 `127.0.0.1` 에만 연다

### API 문서 (springdoc, 2026-11-06)

`SWAGGER_ENABLED=true` 일 때만 `/swagger-ui.html`·`/v3/api-docs` 가 열린다(기본 닫힘, 끄면 401). 관리자 경로까지 전부

공개되는 일이 없다. 화면의 Authorize 에 로그인 응답의 `accessToken` 을 넣는다. `@AuthenticationPrincipal` 인자는 문서에 안 나온다.
**`.env.example` 의 값은 `false` 다** — 빈 값이면 boolean 변환이 위험하고, 비밀값이 아니라 적어도 된다.

**compose 포트 감시가 없었다** — CLAUDE.md 는 `test_no_secrets` 가 DB 포트를 본다고 적었는데 그런 검사가 없어서, 비밀번호
없는 Redis 가 `6379:6379` 로 다 열려 있는 것을 몰랐다(11-06). 지금은 compose 의 모든 포트를 본다.

### 단가 관리 (`AdminCostController`, 2026-11-06)

제안서 기능 8 의 「단가 기준값 관리」. 스키마는 그대로다.

- **덮어쓰지 않고 새 행을 만든다** — `scenario_result.standard_id` 가 참조해, 덮어쓰면 과거 B/C 의 근거와 비용 구성
  (`CostParts`)이 함께 바뀐다. 스키마 주석과 S5 시드가 이미 같은 규칙이었다. 추가·삭제는 없다(다른 기준값과 같고, 외래키가 삭제를 막는다)
- **낡은 결과는 시각이 아니라 「쓴 단가가 내려갔나」 로 본다** — 단가에는 `effective_from`(날짜)뿐이라 `updated-at` 에
  못 넣는다. 날짜로 견주면 같은 날 계산한 결과를 놓친다. 칸을 늘리려면 스키마를 바꿔야 해서 `standardChanged` 로 풀었다.
  **시드를 다시 넣어도 걸린다** — 11-06 에 결과 165개 중 88개가 내려간 단가를 쓰고 있었는데 그때까지 알림이 없었다
- **동시 수정** — 활성 행이 둘이 되면 결과의 (시나리오, 수단, 구조) 유일 제약에 걸려 계산이 깨진다. 「활성일 때만 내린다」 를
  쿼리 한 번(`deactivate`)으로 하고 내린 행이 0 이면 409 다
- **지하 km단가는 같은 수단의 지상·고가보다 낮을 수 없다** — 낮으면 산 구간의 「뚫기」 가 음수 비용이 된다. 둘 다 바꾸려면 순서를
  맞춰 고친다. km단가 0 은 손익분기가 0 으로 나뉘어 막는다
- **값은 회귀 결과다** — 손으로 고치면 `etl/cost_model.py` 와 어긋나고, S5 를 다시 넣으면 새 값으로 내려간다. 화면에 적는다
- **실제 DB 로 시험할 때** — 시드를 다시 넣으면 활성 단가가 전부 내려가 저장된 결과가 모두 낡음이 된다. 표 전체를 찍어 두고
  시험 계정·새 행을 지운 뒤 이전 행을 올려 글자까지 같은지 견줬다

### 대시보드 — 비용 구성·역별 이용객 (`CostParts`·`RowBreakdown`, 2026-11-06)

제안서 「비용 구성 비율, 역별 예상 이용객, 유형별 B/C 비교를 차트로」 의 앞 둘이다.

- **비용 구성은 저장하지 않고 되짚는다** — 결과에는 합계만 있지만 `standard_id` 가 남아 있다. 고정비·역 몫은 그 단가로,
  연장 몫은 나머지로 구해 **합이 늘 합계**다(역이 비켜 서 늘어난 연장도 든다). 스키마를 안 바꿔 `down -v` 가 필요 없다.
  두 노선 22행 모두 합이 건설비와 같았다. 단가 행이 없거나 나머지가 음수(시드가 바뀐 옛 결과)면 **모름**이다
- **회귀식의 항이지 공종별 내역이 아니다** — 「기본 고정비」 를 토목비로 읽으면 안 되므로 차트 아래에 적는다. 긴 노선은
  고정비가 1% 도 안 되어 `<1%` 로 찍는다(0% 면 없는 것으로 읽힌다)
- **역별 이용객은 근사다** — 노선 전체를 역세권 인구 비율로 나눈 값이지 역별 회귀가 아니다. 역이 수백 개라 상위 10개만
  그린다. **이름 없는 역은 뺀다** — 집계구 자료가 없는 곳이고 백엔드는 모를 때도 0 을 싣는다. 서울~부산 복선전철은
  이름 있는 역이 24개뿐이다. 지도 역 표시(`MapView`)와 같은 규칙이어야 한다
- **쌓은 막대를 쓰지 않았다** — 항목이 셋이라 나란한 막대에 비율을 적는 편이 읽기 쉽고, 색으로 구별할 일이 없어 범례·
  팔레트가 필요 없다(`BcChart`·`CostChart` 와 같은 한 색)

### 회원 관리·시나리오 통계 (`AdminUserController`, 2026-11-06)

제안서 기능 8 의 「회원 관리, 시나리오 생성 통계 조회」. 스키마는 그대로다 — 시나리오·결과는 외래키의
`ON DELETE CASCADE` 로 회원과 함께 지워진다.

- **자기 자신은 바꾸거나 지울 수 없다** — 마지막 관리자를 따로 세지 않아도 관리자가 0명이 되지 않는다(행동하는
  사람이 늘 남는다). 자기 삭제 가드는 「관리자는 못 지운다」 가 먼저 막아 **안전이 아니라 문구**를 맡는다 —
  없으면 「일반 회원으로 내린 뒤」 라는 따를 수 없는 안내가 뜬다. 가드를 꺼도 아무 테스트가 안 깨져서 알았다
- **삭제는 204** — `client.js` 의 `request` 는 204 가 아니면 본문을 JSON 으로 읽어, 빈 200 이면 성공이 오류로 뜬다
- **권한은 요청마다 DB 에서 읽어** 올리고 내린 즉시 그 회원의 API 가 200/403 으로 바뀌고, 지운 회원의 토큰은 401 이다
  (시험 계정으로 실제 왕복 확인)
- **통계는 지금 남아 있는 것만 센다** — 생성 기록을 따로 남기지 않아 지운 시나리오는 세지 못한다. 화면에 적는다
- **계산 수는 결과 표로 센다** — 추천 수단은 전부 B/C 0 이면 비어서, 수단별 합과 계산 수의 차이를 「추천 없음」 으로 드러낸다
- **지역별 통계는 뺐다** — `scenario.region_class` 를 채우는 코드가 없어 16건이 전부 NULL 이었다(스키마 주석은
  「비용·수요 모델 설명변수」 지만 쓰이지 않는다). 좌표로 나누려면 시도 경계 판정이 따로 필요하다

## 프로젝트 한계 (보고서에 명시)

**한계를 적을 때는 "무엇을 모르는지"와 "그래서 결과를 어떻게 읽어야 하는지"를 함께 쓴다.**
"표본이 적다"만 적으면 읽는 사람이 결과를 얼마나 믿어야 할지 모른다.

**모델 구조**
- 통행배정모형·OD 설문 대신 인구밀도 기반 회귀 근사 → **상대 비교 지표**로만 의미
- 편익은 통행시간 절감 중심 (차량운행비·사고·환경비용 제외)
- **비용은 건설비뿐이다 — 운영비·대체투자비가 빠져 B/C 가 높게 나온다.** KDI 예타(2021 세부지침)로는
  연간 운영비가 총사업비의 중전철 1.98%·경전철 1.58~1.68% 이고, 우리 할인 규칙으로 B/C × 0.75~0.79 다.
  수단마다 같은 근거가 없어(복선전철은 옛 지침 사례뿐, 트램은 예타 없음) 넣지 않았다 — **일부 수단에만
  넣으면 그 수단만 불리해져 비교가 기운다**. 화면의 B/C 옆에 적는다(research-log 「운영비」)
- 지역별 지가 보정계수 미적용 / 공법(저심도·기존선 병행) 변수 없음
- **산악 터널 단가는 KDI 2021 표준공사비(토목)다** — 환기·방재 설비가 빠지고, 교량(골짜기를 돋운 몫) 할증은 없다.
  철도 고가는 산악 터널이 교량과 km당 비슷해 터널비가 거의 0 이다. BRT 의 도로 기울기 7% 는 설계속도 80km/h 가정에 기댄다
- **지형은 표면 높이(SRTM)다** — 0.5km 중앙값으로 건물을 지웠지만 넓은 숲·단지는 남을 수 있고, 연속 10km
  평균 25‰(광역급행) 조건은 판정하지 않는다
- BRT의 도로 용량 잠식 효과 미반영 — BRT의 B/C가 유리하게 나오므로 결과 화면에 표시
- 수요는 모든 수단에 동일 적용 (수단별 수요 탄성 모델이 없다)
- **1인당 통행거리는 분포가 아니라 한 값(13.6km)이다.** 서울 지하철 1회 이동(환승 포함,
  2019)이라 한 노선 안의 탑승보다 길 수 있다 — 새 노선 하나에는 절감을 **크게** 잡는 쪽이다.
  지방 도시의 값은 없다. 분포를 쓰려면 O/D 자료가 필요하다(K 의 `peak_direction_coef` 를
  평균 통행거리로 읽으면 25.5km 라 이 값과 맞지 않는다 — research-log)

**오차 크기** — 비용 1.25배 / 수요 1.75배 (둘 다 교차검증). **절대값이 아니라 순위를 읽는다.**
수단 비교에서는 같은 수요를 모든 수단에 적용하므로 **수단 선택 결과는 이 오차에 안 흔들린다.**

**"없다"가 아니라 "못 본다"인 것들** — 이 구분이 보고서에서 중요하다
- **급행 비용을 복선전철과 가르지 않은 이유**는 차이가 없음을 보여서가 아니다.
  급행 n=4 라 **검출 한계가 1.50배**이고, 그보다 작은 차이는 이 표본에서 보이지 않는다.
  안 가른 진짜 이유는 표본 4개에 더미를 더 붙이는 것이 **과적합**이기 때문이다
- **공법 변수를 넣지 않은 이유**도 같다 — 저심도 1건·기존선 병행 0건·지상 위주 2건이라
  변수가 아니라 그 노선 한 줄이 된다 (`python etl/cost_model.py --candidates`)

**표본이 얇은 값** — 쓰되 얇다고 적는다
- **BRT 2종(고급 25.0 / 저급 18.0)은 가정값**이다. 저급형이 기준 수단(시내버스 21.3)보다
  느려 **편익이 항상 0** 으로 찍힌다 — 오류가 아니라 가정값의 결과다
- **트램 22.1 은 대전 2호선 설계값**이다. 국내 운영 노선이 없다
- **광역급행 91.8 은 n=2** 이고, 그중 운정중앙~서울역 90.14 는 발표 시점에
  **영업시운전 중**이라 운행 실적이 아니다 (둘이 3.6% 안에서 맞긴 한다)
- `underground_ratio` 40건이 **전부 추정치**(공식 미공표). 민감도를 재 보니 예측 흔들림은
  ±7% 수준이다

**물가 환산** — A등급 38건 중 **19건의 기준연도가 2025를 넘어**(종료연도로 대신한 `ASSUMED`)
물가지수 범위 밖이라 **환산이 일어나지 않는다.** 두 집단의 잔차가 갈리지 않는 것은 확인했다
(t=−0.36). 건설공사비지수가 더 적합하나 미적용.

**역간격-속도 관계의 유효 범위** — `속도 = 18.56 + 12.65 × 역간격` 은 **0.71~2.36km 에서만**
성립한다(R² 0.925). 그 밖은 포화해 예측이 과대하다(급행 0.86배). 구간 **위쪽 두 점끼리도
어긋나는데**(김포 2.36km 가 신분당선 2.09km 보다 느리다) 까닭을 설명하지 못했다 —
차량 최고속도는 둘 다 80km/h 로 같았다. **역간격 2.36~4.98km 에 실측이 없다.**

**자료 신선도** — 국토부 운영현황이 연장 개통을 늦게 반영한다(인천 1호선이 검단연장 전
기준이었다). 여럿을 묶어 중앙값을 낼 때는 **한 출처만** 쓰고, 하나를 콕 집어 쓸 때는 최신을
쓴다. 총사업비 미공개 노선은 역간격 산출에만 쓴다.

- `WaterDetourTest` — 호수 우회. 새 선의 **어느 구간도** 물을 안 지나는지, 1.5배 상한, 물가 여유
  (마름모 호수), 그리고 **실제 `water_bodies.geojson`** 에서 신갈저수지를 알아보는지 — GeoJSON 은
  [경도, 위도] 라 뒤집어 읽는데, 틀려도 오류 없이 "어떤 노선도 호수를 안 지나는" 상태가 된다
- `RouteControllerTest` — 응답의 위도·경도 순서. 바뀌면 우회선이 바다 한가운데 그려진다
- `./mvnw package` 가 테스트를 돌린다 (실행 중인 백엔드를 먼저 끌 것)

**프론트엔드** `cd frontend && npm test` — `node --test` 라 의존성이 없다. 화면 표기 중
**뜻이 갈리는 것**만 고정한다(`format.test.js` — B/C 0 과 작은 양수).

**ETL** `cd etl && python -m pytest`. 파서가 조용히 빗나가면
**데이터가 썩은 채로 회귀까지 흘러간다.**

- `test_etl.py` — 파싱·판정 규칙. "원본의 이런 표기를 이렇게 읽기로 했다"는 약속들
- `test_brt_speed.py` — 표정속도 측정 규칙. 틀려도 그럴듯한 숫자가 나오는 곳을 막는다.
  회차 노선 왕복 선형의 전진 투영, 종점 대기 잘라내기, 부분 관측 배제
- `test_mode_speed_check.py` — 역간격·속도 자. 이름 오매칭, 설계값 배제, 자기 출처 역간격
- `test_korail_ktx.py` — KTX 역 좌표. 다른 도시의 같은 이름 역, 지하철 역, 공식 좌표의 오류를
  집으면 틀려도 그럴듯한 좌표가 나온다
- `test_docs_match_code.py` — **이 파일(CLAUDE.md)의 숫자가 코드·자료와 맞는지 본다.**
  이 프로젝트가 되풀이해 겪은 사고가 "같은 값이 두 곳에 있고 한 곳만 바뀌는 것" 이다
  (`cost_model.SPACING` 4.98 vs S1 4.30, `mode_speed_check` 에 박혀 있던 90.14).
  **CLAUDE.md 는 보고서의 바탕이라 틀린 숫자가 그대로 옮겨 적힌다.** 회귀식 한 번
  바뀌는 데 문서 열 곳 넘게 고쳐야 했고, 하나 빠뜨리면 조용히 남는다.
  깨지면 둘 중 하나다 — ① 값이 바뀌었는데 문서를 안 고쳤다(문서를 고친다)
  ② 문장을 다듬어 정규식이 못 찾는다(정규식을 고치되 **숫자도 같이 바뀌지
  않았는지 확인한다**). 못 찾으면 일부러 실패시킨다
- `test_cost_model.py` — **계수가 아니라 "무엇을 변수로 넣을지"를 박는다.** 계수는 자료가
  바뀌면 바뀌어야 하지만, "근거 없이 변수를 늘리지 않는다"는 규칙은 작은 표본에서 조용히
  뒤집힌다. `MIN_SPLIT_N`, 급행이 계수를 빌리는 방식, S5 가 지우지 않고 내리는 것,
  `source` 가 150자를 넘지 않는 것(넘쳐서 시드가 중간에 죽은 적이 있다)
